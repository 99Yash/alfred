# ADR-0075 — Produce-artifact capability: the agent generates artifacts (PDF/slides/sheets/docs) and renders them inline, agent-authored not Google-exported (DESIGNED — v1 in progress, see docs/plans/artifact-sidebar-v1.md)


**Decision (framed, not designed).** "Make me a PDF / slides / a report" is a distinct capability from reading a file into context (ADR-0071's read-in tool) — the agent **generates artifact content** and the web app **renders it inline for the user to view and edit**, on the Dimension model: agent emits content via create-artifact tools → a **resizable right-side artifact sidebar** (drawer on mobile) → self-built renderers (sandboxed `<iframe srcDoc>` for slides/PDF with inlined fonts/CSS + a `postMessage` ready-signal; a spreadsheet component for sheets; a markdown editor for docs) → content stored **in-house** (Postgres + R2), streamed during generation, **inline-editable** so the user can suggest changes in place. Explicitly **not** Google→PDF binary export (which Dimension never uses, and which ADR-0070/0071 forbid inlining anyway).

**Why.** The boss's "prepare a PDF" misuse (#267) exposed that there is *no* produce-artifact path — it reached for a read-text tool and poisoned persistence. The owner wants this as a first-class capability (PDF/slides/sheets), and judged Dimension's inline-editable UX the better target ("user can see it inline and suggest edits"). Recon of Dimension's web app confirms the proven shape: agent-authored HTML/markdown/rows in self-built renderers, stored locally, streamed into a sidebar — not cloud preview URLs. Deferred because it doesn't touch the poison bug and is a real epic (renderers, streaming, a new synced artifact entity, create-artifact tools).

**The shape (when picked up).** A synced `artifact` entity (Replicache, per the add-an-entity recipe) carrying type + content + run scope; create-artifact tools (`create_slide`/`create_pdf_page`/`create_spreadsheet`/`create_document`-style) the boss calls; an `artifact-sidebar` surface in `apps/web` borrowing renderers from Dimension's web app; R2 for any heavy binary (reusing the ADR-0065 file infra). The boss rubric (ADR-0071 #4) bridges until then: when asked for a downloadable artifact it can't yet produce, deliver a live shareable Google Sheet/Doc link (which already works) rather than failing.

**Alternatives.** (a) **Google export → R2 → download link** — rejected as the model: Dimension proves agent-authored inline rendering is the better artifact (editable, live), and binary export is the path that broke. (b) **Build it in this batch** — rejected: out of scope of the bug class, and a full epic. (c) **Google Docs embed/preview iframes** — rejected: ties artifacts to cloud preview URLs and forecloses inline editing.

**Cross-ref.** Sibling to ADR-0074 (that is invocation breadth; this is output rendering). Bridged by ADR-0071's "share a live Doc/Sheet link" rubric until built. Reuses ADR-0065 (R2 file infra) and the Replicache entity recipe. UX target: Dimension's artifact sidebar.

**Design (v1, 2026-06-26).** The framed shape survives intact, with one forced adaptation to Alfred's stack and three scope cuts. Full plan: `docs/plans/artifact-sidebar-v1.md`.

- **Content lives in a synced `artifacts` row, not in the tool-call stream.** Dimension streams partial tool-call JSON (slide content token-by-token) into its sidebar. Alfred's chat SSE (`chat.tool` events) carries a tool call only as `started`/`succeeded`/`failed` with `argsPreview`/`resultPreview` capped at 2000 chars — there is no partial-args delta channel, and the cap forbids content riding the payload regardless. So v1 stores artifact content in a new synced `artifacts` entity (Postgres → Replicache, standard recipe), written **complete** per the entity invariant; the `chat.tool` event only signals "artifact created/updated → open the sidebar," and the sidebar renders from the synced row.
- **Streaming is page/step-granular, not token-granular.** The boss authors via `system.create_artifact` then N × `append_artifact_page` / `update_artifact`; **each call writes the row and pokes**, so pages appear as produced. Token-level streaming is **deferred** — it would need a new `chat.artifact-delta` SSE event kind and an ephemeral preview buffer; the v1 types leave that seam. This is the one honest UX divergence from dimension.
- **v1 kinds = `document` (markdown) + `pages` (ordered HTML, `format: slides|pdf`).** `pages` reuses the existing `ArtifactPageFrame` (scaled sandboxed `<iframe srcDoc>`). **`spreadsheet` deferred** (needs Univer, a heavy commercial dep) — kept in the type union, no renderer/tool ships.
- **Postgres-only storage in v1.** Content is markdown text / HTML strings in a `content` jsonb column; R2 (the ADR-0065 infra cited above) is only needed for heavy binary, which v1 never produces — a nullable `storage_key` column is the seam.
- **Editing goes through chat in v1.** "Suggest an edit" prefills the composer → boss calls `update_artifact` → re-render. True in-place WYSIWYG editing is deferred.
- **No Zustand.** Dimension's store maps to the synced entity + a small local UI store (open/width/selected-id). Lean: no `re-resizable`/`framer-motion`/`zustand`/`partial-json` deps for v1 — build on the existing CSS-utility + Replicache stack.

Build order (phases, each independently verifiable): (1) substrate — table + migration + synced entity + client hooks; (2) authoring tools — `create_artifact`/`append_artifact_page`/`update_artifact`, verified by replay-diff per the agent-change-verification lesson; (3) sidebar UI on live `/chat` (promote the styleguide-only `ArtifactPanel` to read a real `SyncedArtifact`); (4) generating state + edit-in-chat + polish, and the token-streaming go/no-go.
