# ADR-0092 — Notification dedup keys on the real-world referent, projected from the observation log; Graphiti is a dev-only oracle, never a store

**Decision.** Every email that is *about something* (a CloudWatch alarm, a tracker task, a PR and its CI run, an invoice, a deploy, a newsletter issue, a delivery) is keyed on the **real-world thing it is about**, not on the Gmail `threadId` and not on a per-vendor subject grammar. The scope is not ops mail. It is every message whose claim on the user's attention depends on what it refers to, how often that thing recurs, and what the user has said or done about it. Evidence about one referent **converges** from every source: a GitHub email, a Linear email, and a GitHub webhook that all report one CI failure land on one node and yield at most one action item. The triage classifier, which already runs one cheap-model call on every email, emits one more field: `about` — the referent's name and a free-text descriptor. No taxonomy. That field is persisted as an ADR-0067 observation of a new kind and projected into a new `entity_nodes` kind, **`referent`**. A referent node carries **many identities**: every hard cross-source key found in the message (PR URL, `owner/repo#786`, `ENG-123`, commit SHA, alarm ARN, invoice number) as an `integration_object_key`, plus the sender-scoped canonicalized name as the fallback identity. Two observations that share one hard key are one node, the same rule that merges a person on a shared email — though the primitive that enforces it is new machinery this ADR only partly builds (D3). Todo dedup, briefing continuity, and the sender-kind floors read the referent node id as the loop key, and read the node's **significance** — recurrence, cadence, audience, what the user did with it, and any **standing instruction bound to it** — instead of asking what kind of thing it is. The per-vendor regex tables in `packages/contracts/src/loop-key.ts` (`TRACKER_SENDER_PATTERNS`, `MONITORING_SENDER_RE`, `githubLoopEntityRef`, `issueLoopEntityRef`) become a deterministic **fallback floor** that runs only when the projection has no node, and they are deleted one by one as the projection covers their cases.

**Graphiti runs in dev only, as an oracle.** It calibrates the resolution thresholds and lends two prompts. It holds no product truth and never ships. ADR-0058 stands unchanged.

**Extends ADR-0067** (a new observation kind, a new node kind, hard-key identity bridges for non-person nodes, and the first node that carries more than one identity). **Amends ADR-0066** (the `monitoring_alarm` floor reads the projected referent instead of its own sender regex). **Partially un-defers ADR-0060 / ADR-0067 P4** (one subject binding: standing instruction → entity node). **Reaffirms ADR-0058** with a recomputed cost table. Resolves the recurrence half of #353. #355 is already closed — PR #916 shipped the interim content/shape key on 2026-08-28 — so the durable form is tracked as #917. Motivated by the structural review of PR #916.

## Why this is its own ADR

PR #916 (2026-08-28) fixed nine duplicate `ALARM: Baserow response time alarm` todos by adding a monitoring-alarm branch to `deriveLoopEntityRef`. The fix is correct line by line and structurally wrong by the test in [structural-review.md](../reference/structural-review.md): one domain change ("the next noisy automated sender appears") requires coordinated edits in two packages with nothing that forces them to agree.

| Domain claim | Code mechanism today | Coordinated edits on the next vendor | Enforcement |
| --- | --- | --- | --- |
| Two emails are about the same real-world thing (identity) | Gmail `threadId`, patched by per-vendor subject parsers in `loop-key.ts` | `loop-key.ts` regex, `floors/sender-kind.ts` regex, two test files | Tier 5 |
| This sender is an automated service (source) | `MONITORING_SENDER_RE` duplicated in `packages/contracts/src/loop-key.ts:79` and `packages/assistant/src/triage/floors/sender-kind.ts:261` | Both copies, by hand | Tier 5 |

The duplication is worse than a copied constant. `MONITORING_SENDER_RE` is byte-identical in both files, and the two copies **compose it differently**: `loop-key.ts:197` requires the monitoring sender AND the `ALARM:` subject shape, while `sender-kind.ts:264-266` accepts sender OR subject. So a subject-only `ALARM:` from an unrecognised sender demotes the category but yields no loop key — the two owners already disagree about what an email is about, and no test states which is right.

The `loop-key.ts` header already calls itself "the interim content/shape key" and promises that "the durable form derives the entity identity from the ADR-0067 observation-log projection." Four vendors later, that promise had no ADR, no owner, and no closing PR. This ADR is the closing PR's charter. The question "should we adopt Graphiti/Zep now that cheap models exist" was also re-asked on the same day; recording the answer here stops the re-litigation.

## The domain map

- **Identity.** The entity that persists across a re-notification is the referent: the alarm named `baserow-response-time`, the ClickUp task titled `Netsmart: Save view issues`, PR `owner/repo#786`. The Gmail thread is transport. The subject line is a lossy rendering of the referent by the vendor, and each vendor renders it differently: GitHub says `[owner/repo] Fix login (PR #786)`, Linear says `ENG-123 blocked by failing check on #786`, the webhook says `check_run.conclusion=failure` on the same PR. The referent is the one thing all three point at.
- **Source / derivation.** The projection already knows that `no-reply@sns.amazonaws.com` is a `group` at 0.99 confidence. The dedup path today ignores that fact and re-derives "is this a service" from a regex. Canonical state exists; the consumer does not read it.
- **Authority.** Today three owners decide what an email is about: the `loop-key.ts` grammar, the `sender-kind.ts` floor grammar, and the classifier's `todoSuggestion`. After this ADR one owner decides: the classifier extracts, the projection resolves, every consumer reads the node.
- **Representation.** `ENTITY_NODE_KINDS` (`packages/contracts/src/user-model.ts:927`) admits `person, organization, group, service, repository, project, unknown`. There is no kind for the object a notification is about. `IDENTITY_KINDS` already has `integration_object_key`, "the ADR-0062 object-key shape", which is the correct anchor.

## The adjudications

**D1 — Extraction lives in the triage classifier, at zero added model cost, and emits a name, not a kind.** `triageClassificationSchema` (`packages/assistant/src/triage/classify.ts`) gains `about: { name: string; descriptor: string } | null`, `.nullable().optional()` in the same shape as `collabActivity`. `name` is the referent as the vendor names it (`Baserow response time alarm`, `Netsmart: Save view issues`, `owner/repo#786`). `descriptor` is free text in the model's own words (`CloudWatch alarm`, `ClickUp task`) and is stored as evidence only; it is never part of a key and never switched on. There is deliberately **no closed `kind` enum**: a declared list can only recognise the case someone declared, which is the exact failure of the vendor regex this ADR replaces, and a model forced to choose from a list splits a node whenever it picks a different label for the same thing. If a consumer ever needs a label, a later projection version derives it from the accumulated descriptors, the way `entity-kind-classifier.ts` derives `EntityNodeKind` from evidence with `unknown` as the honest bucket. The rubric states the principle, not vendor examples: "the durable object this notification reports on; null when the email is about a person or has no object" (per the feedback rule: principles over exemplars). The second pass and the deterministic floors may veto but never mint. No new model call exists anywhere in this design.

**D2 — The referent is an observation, then a projection, never a direct upsert — and the two evidence classes take two different write paths.** A projection reducer mints or resolves the `referent` node from observations. Which observation depends on where the evidence comes from, because the existing `email_message` observation cannot carry the classifier's output.

- **Hard keys ride the observation that already exists.** `reduceGmailDocument` (`packages/assistant/src/knowledge/gmail-reducer.ts:57`) already writes `subject` and the parsed `headers` into the `email_message` payload. A hard key is a deterministic function of that payload, so the fold derives it at projection time and needs **no** new observation, no payload change, and no re-hash of an existing family. This is what makes the deterministic slice replayable over today's log.
- **The classifier's `about` needs its own observation kind.** It cannot ride `email_message` for three independent reasons. `gmailEmailMessagePayloadSchema` is `.strict()` at both levels and is hard-bound to the kind by a `superRefine` (`user-model.ts:561-585,699-712`), so adding a field is a breaking contract edit that also changes the reducer's `evidenceHash` inputs and supersedes every existing family on the next replay. Triage is an **unordered sibling consumer** of `gmail.documents_ingested` (`gmail-ingested-consumers.ts:441` against `:462`), so the observation is already written before any classification exists, and the log is append-only. And the grains differ: `email_triage` is keyed `(user_id, source_thread_id)` while observations are per message. So `OBSERVATION_KINDS_BY_SOURCE.gmail` gains a second kind, `email_interpretation`, with its own payload schema and its own family key. Source stays `gmail`, because the evidence is Gmail content; rank is unchanged. Order does not matter: the fold reads both kinds, and neither mutates the other. This follows ADR-0067's "observation log is the system of record; everything else is replayable." A wrong extraction is fixed by a new projection version and a replay — but **only for `entity_profiles`**. `entity_nodes` and `entity_identities` are unversioned and are never deleted, so a wrong mint leaves a permanent `ent_*` row that no replay removes. That asymmetry is the reason the deterministic slice ships first and the model-extracted field ships last: a bad regex is cheap to correct, a bad mint is not. ADR-0057's direct-upsert path is not used.

**D3 — A new node kind `referent`, with many identities; hard cross-source keys are the bridge.** `ENTITY_NODE_KINDS` gains `referent`. It joins `NON_PERSON_ENTITY_KINDS`, so it is never person-scored and never promoted into the social graph. A referent node carries N `entity_identities` rows, all of kind `integration_object_key`:

- **Hard keys**, extracted deterministically from headers, URLs, and body text: a GitHub PR/issue URL or `owner/repo#N`, a Linear/Jira key, a commit SHA, a CloudWatch alarm ARN, a Stripe/Brex invoice id, a tracking number. Each is written in the **legal `integration_object_key` shape** — `IDENTITY_VALUE_FORMATS` requires `^[a-z0-9_-]+:[a-z0-9_-]+:.+$` (`user-model.ts:346`), so a PR is `github:pull_request:owner/repo#786` and an alarm is `aws:cloudwatch_alarm:<arn>`. The **reducer lowercases the value itself** before it mints: `canonicalizeIdentityValue` deliberately does not case-fold `integration_object_key` (`user-model.ts:272-296`), and nothing downstream would catch the omission, so `Owner/Repo#786` and `owner/repo#786` would otherwise split into two nodes. **Two observations that share one hard key are one node**, the ADR-0067 auto-merge rule applied to non-person nodes. This is what makes the GitHub email, the Linear email, and the `github_pull_request` webhook observation converge on one PR node without any of them knowing about the others.
- **The fallback identity**, `alfred:referent:<sender node id>/<lowercased about.name>`, for a referent with no hard key (an SNS alarm whose email carries no ARN, a newsletter issue). The `alfred:referent:` prefix is not decoration — a bare `<sender node id>/<name>` fails the format regex above and is rejected at both `identityRefSchema` and `computeStableEntityId`. Scoped by the projected sender node so `baserow-response-time` from SNS and the same string from a human never collide.

**The identity kind does not identify the node kind, so the `kind` SEGMENT does.** `integration_object_key` already anchors `project` nodes, and `classifyEntityKind` read that identity kind as `project` unconditionally (`entity-kind-classifier.ts`), which would label every referent a project. The fix is one shared table, `INTEGRATION_OBJECT_KIND_SEGMENTS` in `user-model.ts`: the middle segment of `provider:kind:externalId` maps to an `EntityNodeKind`, every minter takes its segment from that table as a TYPE (`IntegrationObjectSegmentFor<"referent">`, so an unregistered segment does not compile), and the classifier reads the same table. The provider is not part of the key — `github:issue:…` and `linear:issue:…` are the same kind of thing. An unregistered segment classifies as `unknown` with `bestGuess: "project"`, never as a guess: `kind` lives in the versioned `entity_profiles`, so a replay fixes it once the segment is registered, while the permanent half — the identity value — is not decided by this table.

The key carries no kind, so the same referent always lands on one node regardless of how the model described it. A referent that first arrives with only a fallback identity and later gains a hard key keeps its node and gains an identity row; a later observation that carries both a known fallback and a hard key already on another node is a **merge proposal** (ADR-0062 propose-dispose), not an auto-merge, because two weak signals are not one strong one.

**The multi-identity node is new machinery, and this ADR does not build all of it.** Today the gmail fold mints exactly one node per identity key (`gmail-kind-fold.ts:315,98`), every node it has ever minted is anchored on an `email` identity, and `recordEntityIdentity` **throws** `EntityIdentityConflictError` the moment a second node claims a live `(kind, value)` (`packages/assistant/src/knowledge/entities.ts:180-187`). `entity_nodes.supersedes_entity_id` and `entity_identities.supersedes_id` are declared and have **zero writers**. So "two observations that share one hard key are one node by construction" is a claim about a primitive that does not exist yet. Three consequences, adjudicated here rather than discovered later. First, the reducer picks **one anchor** per referent — the highest-ranked hard key by `identityAnchorRank` (`user-model.ts:850-889`, currently called by nothing) — mints on it, and links the remaining keys with `recordEntityIdentity`, which is already idempotent for a same-node relink. Second, when the link **throws** because another node holds that identity, the reducer catches the error and records a **merge proposal**; it never auto-merges and never re-anchors. Third, the supersession writer that would actually collapse two nodes is **out of scope** for this ADR and is the first thing a later slice needs. The consequence is honest and acceptable: until it lands, a referent that two sources reached by different routes can persist as two nodes with an open proposal between them, which repeats a todo — today's behavior — instead of hiding one.

**D4 — Resolution is deterministic first, embedding second, model last, and the model band is measured before it is enabled.** For a new `about`, the reducer resolves against existing `referent` nodes:

1. Any hard key or the fallback identity matches an existing identity row → same node. (Tier 1: the unique index on `entity_identities` enforces it.)
2. pgvector nearest neighbour over the node's name embedding above a **high** threshold → same node.
3. A band between a low and the high threshold → a `gemini-2.5-flash-lite` judge call, `same | different`, with the two names and the last observation summary as context. Result recorded as a reversible **proposal** (ADR-0062 propose-dispose), not an auto-merge.
4. Below the low threshold → new node.

**Steps 2 and 3 are both deferred, and step 1 alone is the first shipping form.** Step 2 has no substrate: no entity table carries an embedding column, and pgvector exists in this repo only on `memory_chunks` and `document_chunks`. Adding it is a migration, an embedding writer on the mint path, and an ANN index — the one item in this ADR that is not migration-free. Step 3 is **off** until the dev oracle (D6) reports the false-merge rate for the band. Over-merge is the failure that matters: two distinct alarms collapsing onto one todo hides an incident. Under-merge only repeats a todo, which is today's behavior. The asymmetry sets the default.

**D5 — Consumers read the node id; the regex grammar becomes a floor that shrinks.** `gmailTodoSources` carries `{ provider: "entity", kind: "referent", id: <node id> }` when the projection has a node, and falls back to today's `deriveLoopEntityRef` output when it does not. `todoSourcesOverlap` is unchanged. Briefing continuity (#283) reads the same node. The `monitoring_alarm` floor in `sender-kind.ts` drops `MONITORING_SENDER_RE` and stops asking what kind of thing the email is about. It asks the projection about the **node** (D8): is the sender `group|service`, is the user outside To/Cc, has this referent recurred, has the user acted on it. Category demotion becomes a significance floor over the referent, the same shape as ADR-0066's significance-weighted category. Each vendor branch in `loop-key.ts` is deleted when a prod probe shows the projection covers its rows; the deletion PRs are the debt clock this ADR opens. That clock is cheap to run: `TRACKER_SENDER_PATTERNS`, `MONITORING_SENDER_RE`, `githubLoopEntityRef`, and `issueLoopEntityRef` are all **module-private**, the whole exported surface is `deriveLoopKey`, `deriveLoopEntityRef`, and `LoopEntityRef`, and `deriveLoopEntityRef` has exactly **one** production call site (`packages/contracts/src/todos.ts:178`). Deleting a branch has no external blast radius. The vocabulary ledger ends negative: two regex tables and one duplicated sender list leave; one field and one node kind arrive.

**D6 — Graphiti is a dev-only oracle under `docker/graphiti/`, time-boxed, with a written exit.** The spike ingests 200 to 500 real triaged emails into Graphiti over FalkorDB with `gemini-2.5-flash-lite` as the LLM. It answers three questions the code cannot: does a cheap model resolve the nine Baserow emails to one node without merging it with ElastiCache; what is the false-merge rate on the ClickUp tail; which of Graphiti's five prompts change the outcome. The output is an eval fixture for D4's thresholds and two ported prompts (extraction, resolution) rewritten against our schema. The exit is a findings doc under `docs/research/` and the removal of the compose stack, or its retention as a documented dev tool like Langfuse. No `packages/*` code imports it. No prod environment runs it.

**D7 — No rewrite.** The two things a graph database is wanted for here — many sources converging on one node through shared identities, and edges from an instruction to a node — are graph **model** features, and the substrate already has both. The Graphiti model maps one-to-one onto it:

| Graphiti | Alfred |
| --- | --- |
| Episode | `observations` row |
| Entity node | `entity_nodes` + `entity_identities` |
| Edge / fact | `entity_edges`, `user_facts` |
| Bi-temporal validity | `valid_from` / `valid_until` / `supersedes_id` (ADR-0019) |
| Embedding search | pgvector |

The store is built. The graph model is built. Only the extraction of non-person referents and the resolution step are missing. Both are logic over the substrate. This is the exact "build the intelligence, don't buy the store" line of ADR-0058.

**D8 — Referent significance is a projection over `referent` nodes, and it is what the todo producer reads.** Every notification about a referent is an observation on its node. Every user action on a todo that carries the node (`done`, `dismissed`, left in `suggested` past the window, opened from the rail) is a `user_*` observation on the same node (`OBSERVATION_KINDS` already has `user_confirmation` / `user_rejection`). A projection folds them into per-node significance: recurrence count, cadence, audience position, accept rate, last user action. `todoSuppressionReason` and the sender-kind floors read that, so "the user dismissed this referent three times and is never in To/Cc" suppresses the tenth todo with no rule that names alarms, ClickUp, or SNS. This is the user-model the #353 producer lacks, applied to the object of the notification rather than to the sender. It reuses the significance machinery ADR-0067 built for `person` nodes; only the evidence sources differ. The hand-written floors stay as the cold-start path for a node with no history and shrink as history accrues. Significance is source-agnostic: an email observation and a webhook observation about the same referent count once each, so a CI failure reported by three channels reads as one event with three receipts, not three events.

**This slice must say which existing recurrence mechanism it replaces.** The briefing pipeline already carries a *second*, unrelated recurrence vocabulary: `attention.ts:297` groups on `<sender address>` plus `normalizeSubjectForRecurrence(subject)` (`attention.ts:175-190`), gated on `isBulkSender`, and drives demand decay for both the briefing and the inbox rail. That is a third subject normalizer, independent of `deriveLoopKey` and unaware of it. Node significance is meant to subsume it. Until a slice states that explicitly and re-points `scorePriorityEmailDemand`, this ADR **adds** a fourth vocabulary rather than removing one, and the vocabulary ledger in D5 does not end negative.

**D9 — A standing instruction binds to an entity node, and the producer reads the binding.** ADR-0060 defines standing instructions captured from chat as `user_standing_instruction` observations; ADR-0067 deferred binding them to a subject (P4). This ADR un-defers exactly one binding: instruction → `entity_nodes` row, stored as an `entity_edges` row of a new relation `instructs`. The subject may be a `referent` ("stop suggesting todos for the Baserow alarm"), a `group`/`service` ("never mint todos from SNS"), or a `person`. Chat capture resolves the subject through the same D4 ladder a notification uses, and records a **proposal** when the band is ambiguous; the user confirms in the ADR-0056 changelog. `todoSuppressionReason`, the sender-kind floors, and briefing read `instructs` edges on the node and on its sender before minting. The reverse read is the chat answer to "what happened with Baserow this week": the node's observations in time order. Nothing here needs a graph engine; it is one relation on an existing edge table and one lookup by node id. **But the edge table is a projection, not a record.** `entity_edges` is versioned and run-scoped, with a four-column foreign key into `projection_runs` (`packages/db/src/schema/user-model.ts:676-685`), and it is rebuilt on every replay. It also has **no production writer at all** today — `instructs` would be the first. So the binding cannot live in the edge alone: a user-confirmed instruction must not be re-decided by a resolver on the next replay. The resolved node id is therefore recorded **in the `user_standing_instruction` observation payload** at capture time, and the `instructs` edge is the replayable projection of that fact. Replay then reproduces the same edge without re-running the D4 ladder. A new writer must also supply `validFrom`, which is `NOT NULL` with no default. The rest of P4 (facts with arbitrary subjects, fact-to-fact supersession across subjects) stays deferred.

## Why not adopt Graphiti/Zep now that models are cheap

The cost objection in ADR-0058 is now weak and the other two objections are unchanged.

**Cost, recomputed 2026-08-28.** Graphiti runs about five structured-output calls per episode: entity extraction, entity resolution, edge extraction, edge dedup, temporal invalidation. At ~100 emails/day, ~3k input tokens and ~300 output tokens per call, on `gemini-2.5-flash-lite` (about $0.10 in / $0.40 out per 1M tokens): ~45M in + ~4.5M out per month ≈ **$6-8/month** plus under $1 of embeddings. ADR-0058's $50-100 figure was priced **2026-07-31**, four weeks before this ADR — not on stale 2025 prices — and it already stated that it is "an estimate from list rates, not a measured trajectory, and therefore the first number to verify if this is ever revisited". The gap is not elapsed time. It is the model and the token assumption: ADR-0058 wrote "a cheap model" without pinning one, and this recompute pins `gemini-2.5-flash-lite` at a stated 3k in / 300 out per call. Both numbers are list-rate estimates. Measure before you cite either (`.lessons/model-cost-recompute-from-tokens.md`).

**What cheap models do not change.**

1. **The call is redundant.** Triage already runs a cheap model on every email. Graphiti would run a second pipeline over the same text for the same entity. One field in the existing call (D1) yields the same entity at $0.
2. **The store still leaves Postgres.** The Zep open-source server (Community Edition) is deprecated; the self-host path is Graphiti as a Python library over Neo4j or FalkorDB. Todos, Replicache, and the ADR-0056 confirm/reject surface read Postgres. A Graphiti store in prod needs a Graphiti→Postgres mirror, which is the "sync layer" ADR-0058 names. That cost is engineering time and a second failure domain, not dollars.
3. **Cheap models are weakest at the step we need.** Extraction and edge dedup are classification-shaped and a small model does them well. Resolution ("is this the node I already have?") is where small models over-merge or fail the output schema; Graphiti's own documentation warns about this. D4 puts the model in the narrowest possible band, behind a measured threshold, and records its output as a reversible proposal. Graphiti also confirms the D1 choice by example: its entity types are optional and its default node is a name plus a summary with no taxonomy.
4. **Runtime.** Graphiti is Python. Alfred is a TypeScript monorepo. A sidecar is fine for a dev oracle and a permanent operational cost in prod.

**Why the Langfuse analogy holds for D6 and not for a prod store.** Langfuse runs dev-only because it holds no product truth; prod behaves correctly without it. Graphiti as a store holds the truth for entities. A dev-only truth store gives prod nothing. A dev-only **oracle** gives prod calibrated thresholds and two prompts, which is what D6 ports.

## Alternatives

- (a) **Keep extending `loop-key.ts` per vendor.** Rejected: tier-5 enforcement, duplicated sender lists across packages, N PRs of the same shape, and the code's own header calls it interim.
- (b) **Graphiti/Zep as the prod entity store.** Rejected for the three unchanged reasons above. Cost is no longer one of them.
- (c) **Graphiti dev-only as a truth store, port "useful items" ad hoc.** Rejected: prod cannot read a dev store, and "useful items" without a named target is an open-ended spike. D6 names the three questions, the two artifacts, and the exit.
- (d) **Rewrite the knowledge substrate around Graphiti's schema.** Rejected: D7 shows the substrate already has every Graphiti concept.
- (e) **A closed `kind` enum on `about`.** Rejected during review: it is a declared list with the same blind spot as the vendor regex, it can split one referent across labels, and no consumer needs it once identity is the name and interpretation is node significance (D8).
- (f) **Model-only dedup: ask the classifier "is this a duplicate of a recent todo".** Rejected: it puts the resolution decision in the least reliable component with no reversible record, and it does not give briefing or the floors a shared key.

## Implementation order

The adjudications are numbered by topic, not by build order. A build in D-order starts at the only decision that needs a model, and it produces nothing until the projection can hold its output. Use the order below instead. Tracked as #917.

**S1 — deterministic referent nodes, no model.** Add `referent` to `ENTITY_NODE_KINDS` and `NON_PERSON_ENTITY_KINDS` (a contracts-only edit: both columns are unconstrained `text`, so no migration). Derive hard keys inside the existing gmail fold from the payload the reducer already writes, per D2. Mint on the highest-ranked anchor, link the rest, catch the identity conflict and record a proposal, per D3. This slice replays over today's log, needs no new observation kind, and is dry-runnable with the determinism validator in `project-user-model-gmail-shadow-committed.ts`. It is also where the multi-identity primitive gets built, which is the load-bearing unproven claim of the whole ADR — so it gets built with no model in the loop.

**S2 — consumers read the node.** D5. `gmailTodoSources` carries the node id; briefing continuity reads the same node; one `loop-key.ts` vendor branch is deleted behind a coverage probe.

**S3 — the classifier field.** D1, plus the `email_interpretation` observation kind D2 defines, for the tail with no hard key.

**S4 and later, deferred.** D8 significance (and the `attention.ts` reconciliation it owes), D9 `instructs`, D4 steps 2 and 3, and the node-supersession writer.

**D6 moves with D4.** The Graphiti oracle exists to calibrate D4's thresholds and to port its two prompts. D4 steps 2 and 3 are now the deferred part, so the spike buys nothing until they are on deck. Run it then, not first.

**Rollout is manual, once per user.** A change to the kind vocabulary changes classifier output, so the drift gate at `refold.ts:117-132` reports `logic-drift` and refuses to auto-activate. Every rollout of S1 needs a deliberate re-run of the shadow script with `--commit --activate`. This is the gate working as designed; plan for it rather than trip over it.

## Verification

- Prod probe before and after: `todos` created per distinct `referent` for `no-reply@sns.amazonaws.com` over 30 days; target is one live todo per alarm name.
- Eval both directions on the classifier field: MUST extract a stable `name` (SNS alarm, ClickUp task, GitHub PR, Stripe invoice; the same referent across three emails yields the same canonicalized name) and MUST return `null` (a human email whose subject starts with `ALARM:`, a newsletter, a calendar invite). The `descriptor` is not scored.
- D8 probe: for the top ten recurring referents on the work account, the todo count after the user's first dismissal.
- Convergence probe: for one CI failure on a PR that Linear also tracks, the count of `referent` nodes after the GitHub email, the Linear email, and the webhook have all been observed. Target is one.
- D9 probe: after "stop suggesting todos for <referent>" in chat, zero new `suggested` todos carry that node for 30 days, and the instruction appears in the changelog as a confirmed fact bound to the node.
- D4 step 3 stays off until the D6 findings doc reports the false-merge rate in the band on real mail.
- Merge-proposal probe (S1): the count of open referent merge proposals after a full replay. A number that grows without bound means the anchor choice is wrong, not that the supersession writer is missing.
- Determinism probe (S1): the shadow script's twin-run checksum must match on the referent projection version before any activation. A hard key derived from the payload is pure, so a mismatch is a real bug and never provider weather.
- Identity-contract probe (S1): every minted `referent` identity is parsed through `identityRefSchema` in the reducer, not only in a test, and not against `IDENTITY_VALUE_FORMATS` alone. The format is the weakest of the schema's rules — `integration_object_key` ends in `.+`, so a whitespace-padded or oversized value clears the format and fails later at `computeStableEntityId` or at the `entity_identities` write. Parsing the schema also states the canonical rule once instead of restating it here: `canonicalizeIdentityValue` does **not** case-fold `integration_object_key`, so the canonical refine is a trim, and the real case decision is per SEGMENT and owned by the minting module — `owner/repo` is folded through `canonicalizeIdentityValue` under its own `github_repository_full_name` kind, a commit SHA is lowercased, and an opaque id (`check_suite` node id) is preserved verbatim. Because the format admits almost anything, the module bounds the `externalId` itself and mints NO key over the bound, rather than building a value the schema will reject.
- Sender-gate probe (S1): a threading header is written by whoever sent the mail, so a `Message-ID` of `<owner/repo/pull/N@github.com>` from a sender that is not GitHub must mint nothing. The header class is the STRONGER class and is tried first, so it needs the same `trackerSenderKey` gate the subject class has — gating only the weaker class leaves the gate unreachable. One owner for that question, no second copy of the pattern table.
- The debt clock: each deletion of a `loop-key.ts` vendor branch cites the probe that shows projection coverage.

## Revisit trigger

Reopen the store question only on ADR-0058's trigger: multi-tenant Alfred with measured traversal latency. Reopen D4's model band if the oracle shows a cheap model resolves with a false-merge rate under 1% on the ClickUp tail; then the band may widen and the embedding step may shrink.

## Open / deferred

- Non-email sources (GitHub webhooks, ClickUp API, Linear API) carry a hard object id and mint `referent` identities directly from their reducers with no model. D3's hard-key rule is what lets them converge with email evidence; wiring each reducer is its own PR and follows ADR-0067's per-source pattern.
- **The node-supersession writer.** `entity_nodes.supersedes_entity_id` and `entity_identities.supersedes_id` still have no writers after this ADR, so two nodes that should be one stay two with an open proposal between them. This is the largest piece of ADR-0067 that D3 leans on and does not build.
- **The `attention.ts` recurrence vocabulary** (`normalizeSubjectForRecurrence`, `:175-190`) is not re-pointed here. Until D8 subsumes it, the repo carries one more subject normalizer than before, not one fewer.
- P4 beyond the single `instructs` binding in D9 stays deferred per ADR-0067.
- Auto-dismiss of a `referent` todo when the vendor sends a resolution event (`OK:` after `ALARM:`) is closure detection (#258), not dedup, and is not decided here.
