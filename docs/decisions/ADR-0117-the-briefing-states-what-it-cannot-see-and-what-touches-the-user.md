# ADR-0117 — The briefing states what it cannot see, and what in the world touches the user

**Status.** Proposed. Slices 1, 2, and 3 are built (2026-11-01), with the changes in **Built: slices 1 and 2** and **Built: slice 3**. Slice 4 is not built. Generalizes the connection block of the ADR-0100 amendment of 2026-10-28 to every briefing input. Extends ADR-0048 (content model) and ADR-0064 (quiet morning). Uses the ADR-0100 cause-and-recovery shape.

**Decision.** Every input that the briefing gather reads declares its **provenance**: `live`, `fallback`, `stale`, or `unavailable`, each with a cause and a recovery. One rule puts each non-live input that the user can repair into the fixed block of the ADR-0100 amendment. The composer receives the same list, so its prose cannot claim a source that it did not have. Separately, an official warning whose area contains the user's place, on the day of the briefing, is an at-risk item. A geometry match selects it, not a model.

---

## What happened

These facts are from production on 2026-10-28.

- **The weather was for another city, and nothing said so.** The user has no `location` preference. At that time, `resolveWeatherLocation` (`briefings/gather.ts`) fell back to `weatherFallbackFor(timezone)`, which maps `Asia/Calcutta` to Delhi. `readUserLocation` (`knowledge/location.ts`) replaced it in slice 1. The briefing showed Delhi's weather as if it were the user's own. The user lives in Bhubaneswar, near the coast where a cyclone made landfall that day. The briefing had no line about it.
- **Alfred already knew the city, in three places.** `user_facts` holds `home_city = "Bhubaneswar"` and `home_country = "India"`, both `confirmed`, and `bio_summary` says "based in Bhubaneswar". The app rail shows weather from browser geolocation (`apps/web/src/lib/weather`), and it keeps that location only in `localStorage`. The briefing reads none of them. Each consumer reads its own copy of one fact, and the server consumer reads the one copy that is empty.
- **The weather source has no warnings.** The gather calls the Open-Meteo forecast. A forecast code is not a warning. A government agency issues the warning.
- **A missing input has no cause.** The gather's one signal for a blind input is a NULL ("A NULL inside it means one source is missing", `schema/briefings.ts`). A NULL carries no cause and no repair. A fallback value carries no mark at all.
- **Old items read as news.** `integration_activity` carried Vercel "failed" deploys from 2025-04-08 and 2025-09-27 in a 24-hour window.
- **The owner cannot list the cases.** "I can't come up with these cases one by one." A design that depends on a hand list of cases fails on the next case.

## Decisions

1. **Each gather input declares its provenance, and the compiler holds the list.** Each contribution returns its value together with one of four states:

   | State | Meaning | Example |
   | --- | --- | --- |
   | `live` | Alfred read the real source for this user, in this window. | Calendar events read from the connected account |
   | `fallback` | Alfred used a default in place of a user fact. It names what it replaced. | Delhi weather in place of the user's city |
   | `stale` | The value is real but older than the window. It names its date. | A deploy failure from 2025-04-08 |
   | `unavailable` | Alfred could not read the source. It names the cause. | GitHub App credential missing |

   Each state except `live` carries a recovery from the ADR-0100 set: `connect <integration>`, `set <preference key>`, `retry`, or `none`. The gather type requires the field, so a new input cannot ship without a statement of its blind state. This is the answer to "I can't list the cases": each new source must answer the question when it is written, and `check-types` refuses it until it does.

2. **One rule chooses what the user sees.**
   - `unavailable` with recovery `connect`: a row in the block. It also stops a quiet morning, because the user lost a source (ADR-0100 amendment, item 2).
   - `fallback` with recovery `set`: a row in a briefing that sends for other reasons. It does not send a morning by itself, because the user did not lose anything. The row states the default and the one action, for example "Weather is for Delhi, the default for your time zone. Set your city."
   - `stale`: the item leaves the news list. It can appear only as an open loop under the ADR-0048 rules.
   - `retry` and `none`: the log only.

   The composer gets the full provenance list as a fact. It must not write "nothing needs your attention" about a source whose state is not `live`.

3. **Location is one fact with one reader, and a default never wins over a confirmed fact.** Location gets one owner reader, as the time zone has `settings({ userId }).timezone()`. Every server consumer (briefing weather, warnings, chat date grounding) reads through it. The time-zone city stays as the last default, but it is marked `fallback`. The order:
   1. The user's stated `location` preference.
   2. The confirmed `home_city` and `home_country` facts (ADR-0080), geocoded one time and kept with the fact.
   3. A city that Alfred proposes from evidence the user owns, and that the user confirms. Candidate evidence: the browser location that the rail already reads, the locations of calendar events, and the sign-in region from `session.ip_address`. Alfred never adopts a proposed city silently. A VPN or a trip makes a wrong silent location worse than a declared default. When the evidence disagrees with step 1 or 2 for several days, Alfred asks whether the user moved.
   4. For one day, an upcoming calendar event in another city is a second place for that day.

   The general rule: **before a consumer uses a default, it reads the confirmed fact that the default stands in for.** A default that wins over a confirmed fact is a defect, and its provenance is `fallback` with recovery `none`, so it reaches the operator log, not the user.

4. **An official warning at the user's place is an at-risk item.** The gather reads official warnings for each place from decision 3, for the briefing day. A warning is selected when its area contains the place, or when the place is inside a fixed distance from the area. That test is geometry, and no model makes it. A selected warning ranks first, under "something is wrong or at risk" in the briefing prompt. The source must be official and public. The candidates must be checked before the build: a global hazard feed for large events (for example GDACS for tropical cyclones, floods, and earthquakes), and a national CAP feed where one exists (for example NDMA Sachet in India, NWS in the United States, and MeteoAlarm in Europe). When the feed fails, the provenance is `unavailable` with `retry`. When the place is a `fallback`, the block row says that Alfred checked warnings for the default city.

5. **The same match covers other official events later.** The rule is "an official event whose place and time touch the user". Natural hazards are the first producer: GDACS reads cyclones, floods, earthquakes, volcanoes, and wildfires, and NDMA Sachet reads each CAP category. A later producer, for example a transit strike or a public holiday in the locale of a meeting, uses the same match and needs its own official source. This ADR does not add them.

## Built: slices 1 and 2 (2026-11-01)

The code follows decisions 1 to 3, with these changes. Each change is a fact about the build, not a new decision.

### Provenance

- **No `set` recovery yet.** No surface writes the `location` preference: there is no settings field and no chat tool. A recovery that the user cannot do is not a recovery. So the time-zone city is `fallback` with recovery `none`. It reaches the log only. The `fallback`/`set` row of decision 2 waits for a surface that can set the city (owner decision). Issue #1664 tracks it. `gatherProvenanceSchema` has no `set` arm until then.
- **The compiler holds the list.** The gather builds its provenance from a table that `satisfies Record<GatherInput, StatedProvenance>`. `StatedProvenance` is a non-empty tuple, so each input states at least one entry. A new member of `GATHER_INPUTS` does not compile until it states its read. The stored field stays optional, so a gather from before this build still parses. Each reader treats an absent list as no statements.
- **One owner decides who reads each entry.** `provenanceAudience` (`briefings/provenance.ts`) gives each entry its block row, its composer fact, and its log line. `blockingProvenance` gets the block rows from it. `@alfred/contracts` keeps only the `BlockingGatherProvenance` shape. Each entry that is not `live` goes to the log.
- **`unavailable` has eight causes.** `scope_missing`, `needs_reauth`, and `not_delivered` have recovery `connect`, and each is a block row that stops a quiet morning. `read_failed` has `retry`. `not_connected`, `no_place`, `silent`, and `record_incomplete` have `none`. The schema pins each cause to its recovery. Slices 1 and 2 built five causes. ADR-0118 slice 3 added `not_delivered`, `silent`, and `record_incomplete` (2026-11-02).
- **A Google row that is not active is a repair.** When no Google credential selects for an input, the gather reads the integration availability. When a credential row exists but no row passes the connected rule (ADR-0093), the cause is `needs_reauth`. It is a block row with recovery `connect`. Only "no credential row" gives `not_connected`. A fault of the availability read gives `read_failed`. The GitHub merged read does not make this check: its `no_connection` status gives `not_connected`.
- **`not_connected` is a composer fact, not a row.** No credential row is also what a deliberate disconnect leaves (ADR-0100 amendment 2026-10-28, item 3). So `not_connected` makes no block row and does not stop a quiet morning. The composer gets it as a fact (owner decision). The prompt tells the composer to say, in one short clause, that it could not read the source and what the briefing therefore cannot see. The prompt also tells it never to say that the day is clear on that basis.
- **The composer gets the inputs that it reads.** `COMPOSER_READS` (`briefings/agent/agent.ts`) lists email, calendar, the merged work in the day shape, the loop verdicts, the activity record, and `deploy_status`. The composer gets a fact for each entry of these inputs that is not `live`. Each fact names the tool, the reason, and what the briefing cannot see. When a connection key names the same source, the prompt tells the composer not to repeat the fact in the body. Slice 3 adds `official_warnings` to the list. ADR-0118 slice 3 adds the activity record (`list_activity`) and `deploy_status` (`get_day_shape`). Of these inputs, only `official_warnings` has a `fallback` state. Only `deploy_status` has a `stale` state, and that entry is a log line only.
- **Weather does not reach the composer as a fact.** Weather does not reach the composer, so its `fallback` and `read_failed` statements stay in the stored gather and the log. Before ADR-0118 slice 3, the activity list also reached the composer only as the count behind `get_day_shape.activityVolume`. Now the activity record reaches it through `list_activity`, and the verified pull through `get_day_shape`.
- **One calendar read.** The gather stores its calendar read in the workflow state. `list_calendar_events` returns that list, so the list and the calendar statement come from one read. A run from before this field reads the calendar again.
- **One row per integration.** An input row and a delivery alert for the same integration share a key. The delivery alert takes the row, because the repair link is the same. The delivery row also carries the input entry. So the model that writes the notice gets both facts, and `BROKEN_CONNECTION_GUIDANCE` does not deny the failed read.
- **The stale rule covers the verified pull only, and only a provider time.** The activity record reads only the acts whose delivery arrived in the window (ADR-0118 slice 3). The verified pull can report an old failure. Each pull item carries the clock of its time: `provider_event`, `delivered`, or `observed`. An item is stale only when its time is a `provider_event` time before the window start. A `delivered` or `observed` time is Alfred's clock, so the item stays in the list.
- **A failed verified pull is not `live`.** A pull that faults returns the `failed` outcome and writes a log line. The `deploy_status` statement is then `read_failed` with `retry`, and it names the provider. A failed read can make `activityVolume` too low. Since ADR-0118 slice 3, the composer gets a fact for it that names `get_day_shape`.
- **The stored list has a bound.** `GATHER_PROVENANCE_MAX` is 26: 22 before slice 3, and 24 before ADR-0118 slice 3 added `deploy_status`. A gather states at most two entries for each of the eight inputs. Weather can state a failed read and its fallback. `official_warnings` can state a place entry and a failed read. It also stores at most `GATHER_STALE_PROVENANCE_MAX` (10) stale entries. The verified pull reads at most five targets for each of its two providers, so ten is also its maximum. `boundProvenance` clips the list at the producer and logs each drop. So a stored list never fails its parse on length.
- **The web reads a bad list as absent.** The synced briefing schema (`packages/sync/src/schemas.ts`) reads `provenance` with `.catch(undefined)`. So an unknown or bad entry does not drop the briefing row on the web. The contract schema stays strict on the server write path. The web does not show provenance yet.
- **The email statement checks the credential only.** The email input reads `email_triage`, not Gmail. A failed `email_triage` read throws on purpose and fails the gather. The row is `failed`, the watermark does not move, and the next run reads the same window. A gather that continued would move the watermark past mail that it did not read. So a stored email statement always follows a completed read. It says only whether a Gmail account selects. A fault of the credential check is `read_failed`.
- **One loop's missing read is not an input fault.** The relevance pass already gives that loop an `unverifiable` verdict, and the composer reads it per loop. Only a fault of the whole pass makes `loop_relevance` `unavailable`.
- **One account in a calendar read.** When one Google account reads and another fails, the calendar is `live`, and the failure is a log line.
- **A missing grant is a row, also when the user chose it.** A Google account without the grant for an input gives `scope_missing` and a block row each morning. The owner grants all scopes, so this does not occur today. A user who declines a scope on purpose sees the row until the user grants it.

### Location

- **The reader and its order.** `readUserLocation` (`knowledge/location.ts`) reads the `location` preference first. Then it reads the confirmed `home_city` fact, checked against `home_country`. Then it reads the confirmed free-text `location` fact ("City / region they're based in"). The time-zone city is last. The `location` fact is after `home_city` because it is free text. The reader uses only the newest confirmed fact that the user stated (`isUserStatedSource`). Step 3 of decision 3 (proposals from evidence) is slice 4.
- **The basis.** The reader returns `preference`, `home_fact`, `location_fact`, `timezone_default`, `none`, or `fault`. It does not throw. `Place` (`@alfred/contracts`) is the one shape for a preference, a geocoded fact, and a time-zone city.
- **A confirmed fact that the geocode does not match.** The reader goes on to the next step. When the time-zone city then wins, the reader names the first such fact (`unplaced`). So the weather statement says that Alfred could not place that fact, not that Alfred knows no place.
- **A fault does not become a default.** A failed fact read or a failed geocode is the `fault` basis. The reader does not go on to the time-zone city, because the fault is temporary. Weather is then `read_failed` with `retry`, and the gather does not fail. One `WEATHER_DEADLINE_MS` covers the geocode and the forecast.
- **A long fact is not a place.** The reader does not use a place fact longer than `PLACE_TEXT_MAX` (100 characters). Such a value is not a place name, and its text goes into a bounded provenance reason.
- **The geocode is kept in the process, not with the fact.** Each geocode gives `placed`, `no_match`, or `fault`. The reader keeps a placed result and a miss in an in-process map. A fault is not kept, so the next read tries again. The owner kept the map in the process: Alfred has one user, a restart costs one request for each fact value, and `user_facts` has no column for a place. A preference row would show on the Preferences page as if the user set it.
- **The geocode matches the country by name or by code.** The reader asks Open-Meteo geocoding for ten candidates. Bhubaneswar also names a place in Bangladesh, so the first candidate alone is not safe. With a `home_country` fact, the first candidate in that country wins. The country matches by name, or by ISO two-letter code through `Intl.DisplayNames`. A three-letter value such as "USA" does not match. For a `location` fact, a part after a comma must name the country or the first-level region. Without a country and without such a part, the first candidate wins.
- **Chat reads the same place.** `read_user_context` reads `currentLocation` through `readUserLocation` and `statedLocationLabel`. So chat and the briefing give one answer, and decision 3 holds for chat. Chat gets the user's own words, and no name for a time-zone city. A read can wait for the geocode, up to `GEOCODE_TIMEOUT_MS`, when a fact value is new to the process.

## Built: slice 3 (2026-11-01)

The code follows decision 4, with these changes. Seven changes do not do what decision 4 says. They are under **Changes to decision 4**, and each bullet says that it changes decision 4. The other bullets are facts about the build. The probe notes are in `references/scratch/adr-0117-warnings/FINDINGS.md` (not tracked).

### Changes to decision 4

- **No distance band.** This changes decision 4, which also selects a warning when the place is inside a fixed distance from its area. Slice 3 selects a warning only when its area contains the place. A fixed distance from a point says nothing about the impact, because the impact depends on the severity (owner decision). GDACS already puts the severity in its cyclone wind areas: the Green, Orange, and Red classes are the 60, 90, and 120 km/h winds. On 2026-10-28 the nearest wind area of cyclone ARNAB-26 stopped about 318 km from Bhubaneswar. So GDACS itself said that the wind did not reach the place.
- **One place only.** This changes decision 4, which reads warnings for each place of decision 3. Decision 3 step 4 adds a calendar city for one day, and step 4 is slice 4. So the gather reads warnings for one place only.
- **The default city is a composer fact, not a block row.** This changes decision 4, which says that the block row names the default city. The slice 2 audience rule gives a `fallback` no block row (`provenanceAudience`, `briefings/provenance.ts`). So the warnings `fallback` is a composer fact and a log line. The fact names the default city and says that the briefing may be missing warnings for the user's area. The weather `fallback` stays in the log only, because weather does not reach the composer.
- **A forecast wind area for a later day selects the event today.** This changes decision 4, which reads warnings for the briefing day. A cyclone `WindRadii` area has the wind at one time (`polygondate`): the last advisory, then each forecast time. Such an area selects the event when its time is at or after the start of the briefing day, also when that time is on a later day. So a landfall tomorrow is in today's briefing (owner decision). The uncertainty cone is the forecast track, so it selects at any time. A wind area that only shows the past does not select: a `WindRadii` area of a time before the briefing day, and the buffer of the whole track. That buffer is a wind area with no `featuretype`, and it holds the past days of the track.
- **GDACS selects only the events that it marks current.** This changes decision 4, which selects a warning by its time on the briefing day. For an event in progress, GDACS gives the last update in `todate`, not an end time. So an event must have `iscurrent` "true". The event list asks for the briefing day and the seven days before it (`LIST_DAYS_BEFORE`), not three days. In the capture of 2026-11-01, a current flood had a `todate` three days old. An event that is not current is dropped before its area read.
- **Filters that decision 4 does not have.** This changes decision 4, which selects each official warning whose area contains the place. From GDACS, Alfred selects only Orange and Red events, and no drought. From Sachet, it selects only `Severe` and `Extreme` alerts of six hours or more, from onset to expires. The GDACS and Sachet bullets below give the reasons.
- **A default-city warning does not send a quiet morning.** This changes decision 4, which makes each selected warning an at-risk item. A warning for the time-zone default city appears in a briefing that sends for other reasons. It does not send a quiet morning (owner decision), because a `fallback` does not send a morning (decision 2). `sendableOfficialWarningCount` (`briefings/read.ts`) gives 0 when the gather has a warnings `fallback`, and both send gates read it. A warning for the user's place stops a quiet morning.

### What slice 3 does not catch

- **Slice 3 does not catch the 2026-10-28 case.** GDACS put Bhubaneswar in no wind area of ARNAB-26 and not in its cone, so the GDACS match does not select it. The state authority cyclone alerts in Sachet on 2026-11-01 (Andhra Pradesh SDMA) gave only a `Polygon URL` parameter, with no district code and no place name in `areaDesc`. That polygon route returns HTTP 403 to a script, so the district match cannot select such an alert. The Sachet RSS file holds about two days, so the probe could not read the alerts of 2026-10-28. A read of the Sachet polygon route is the path that would catch this case. It is a follow-up.

### Feeds and match

- **Two feeds.** GDACS is read for every place. NDMA Sachet is read when the place is in India and Alfred has its district. Each time-zone city states its country, and Delhi also states its state and district, so the gather reads Sachet for the Delhi default city. NWS and MeteoAlarm wait for a user outside India (owner decision). The code is in `briefings/official-warnings/`.
- **The name is "official warnings", not "warnings" and not "weather warnings".** The gather field and the provenance input are `official_warnings`, and the folder is `briefings/official-warnings/`. A bare "warnings" already has other meanings in the code: the AI SDK `CallWarning` list (`packages/ai/src/agent.ts`) and the log level `warn`. ADR-0118 named `sourceRoutes` for the same reason. "Weather" is not correct, because GDACS also reads earthquakes and volcanoes, and decision 5 adds events that are not hazards. "Official" is the property that selects a warning: an agency issues it, and a forecast code does not have an issuer.
- **GDACS: Orange and Red only, no drought.** The event list asks for `alertlevel=Red;Orange`. A Green event has a small expected impact. A drought lasts for months, so it would be an "at risk" item in every briefing. The area of each event type is a fixed set of geometry classes (`EVENT_AREA` in `gdacs.ts`): the cyclone `WindRadii` areas and its uncertainty cone, the flood's affected area (not the basin), the volcano circle, and the burned area. An earthquake area is a ShakeMap polygon of intensity 5 (MMI V) or more. A lower intensity reaches far from the epicentre. A GDACS warning expires at the latest time (`polygondate`) of a hazard area that contains the place, when that time is later than the event's last update. The reader builds each geometry URL itself, so a read goes only to GDACS. It reads at most 20 event areas, the nearest first. A failed area read is a partial failure, not a failed feed. An event, an area, or a date that Alfred cannot read counts as unread, and does not count as "not at the place".
- **Sachet: the RSS file and one CAP file for each alert.** The RSS file lists the last 100 alerts, about two days. A CAP file does not change after it is published, so the process keeps up to 500 parsed files by guid. A failed read is not kept. On 2026-11-01 a cold read took 3.5 s and a warm read 85 ms. The reader reads only links under the Sachet CAP path. It drops an alert that is not `Actual`, a `Cancel`, and an alert that an `Actual` update or cancel names in `references`. A `Test` or `Exercise` alert does not remove a real alert. A CAP time must have a zone offset, as CAP 1.2 requires. A time with no offset makes the alert unreadable, and it counts as unread. It prefers the English `info`.
- **Sachet: Severe or Extreme, six hours or more.** On 2026-11-01 about 85 of 100 Sachet alerts were IMD nowcasts of one to three hours, for example "Light Rain, Moderate". The user reads the briefing later, so such an alert has often expired. The reader selects only a `Severe` or `Extreme` alert that lasts six hours or more (owner decision). The hazard window is from `onset` (else `effective`, else `sent`) to `expires`. The six hours and the briefing both use this window. `effective` is only when the message takes effect, so a warning that takes effect today for a hazard tomorrow is tomorrow's warning. The alert is in force when its hazard starts before the day ends and it expires after the gather.
- **Sachet: the district match.** The geocode keeps `admin1` and `admin2` (`Place.area`). A generated table (`official-warnings/lgd-districts.ts`, from `scripts/generate-lgd-districts.mjs`) gives the LGD district code for the state and district names. Its header records the name, the byte size, and the SHA-256 of the release asset and of the CSV, so a person can download the same asset and run the script again to verify it. When the geocode gives a state that LGD knows, only a district in that state gives the code. A district with the same name in another state gives no code. When the user's district has an LGD code, an area with LGD codes matches by code only. Any other area (for example a CWC river gauge, which has no code) matches when its text has the district name and the state name. The district name alone is enough only when LGD has exactly one district with that name, and that district is the user's district. A place with no district does not read Sachet.

### Statements and the briefing

- **One place read.** The gather reads the place one time, and weather and warnings use the same read. `WEATHER_DEADLINE_MS` covers the place read and the forecast. The feeds have their own 30 s deadline, which starts after the place read. When another read of the gather fails, the gather also stops the feed reads. A feed that the deadline or this cancel stops keeps what it read and counts the rest as unread.
- **Two statements at most.** `officialWarningsProvenance` gives the place entry and a `read_failed` entry. The place entry is the time-zone city `fallback`, or `no_place` when Alfred read only GDACS for the user's place. Alfred reads only GDACS when it does not know the country of the place, or when the place is in India and has no Sachet district. A `fallback` wins over the `no_place` sentence, because the default city is not the user's place. A failed feed, or a part of a feed that Alfred could not read, is `read_failed` with `retry`, and the reason names the feed. A place `fault` or `none` reads no feed.
- **Each selected warning is a seed fact.** `officialWarningFacts` (`briefings/agent/agent.ts`) puts each warning in the composer's seed message: the issuer, the event, the severity word, the area, and the window in the user's time zone. The fact tells the composer to lead the body with the warnings, most severe first, to name the issuer, the event, and the severity word, and to add no advice that the warning does not give. So the rank does not depend on a tool call. When the warnings `fallback` names the default city, the fact names that city. `list_official_warnings` gives the details, for example the headline and the link. Its result has three states: `read` with the items, `not_read` (the gather read no feed), and `not_recorded` (a run from before the field). Only `read` has items, and the seed adds a warning fact only for `read` with items. The gather stores at most `OFFICIAL_WARNINGS_MAX` (8) warnings, by rank and then onset.
- **A warning for the user's place stops a quiet morning.** `isQuietMorning` takes `officialWarningCount` from `sendableOfficialWarningCount`. The legacy morning workflow runs the same gather, and its `decideSend` reads the same count. Its composer prompt gets the warnings with a rule that a warning leads. Its text without the model lists each warning first, and does not say that nothing stood out when a warning exists.
- **The web reads a bad list as absent.** The synced briefing schema reads `official_warnings` with `.catch(undefined)`, the same as `provenance`. The web does not show warnings.

## Note: the activity input reads the record (ADR-0118 slice 3, 2026-11-02)

The activity input now states the coverage of the ADR-0118 activity record. This adds three causes to the `unavailable` union. `not_delivered` has recovery `connect`, and it is a block row and a composer fact: the provider's events do not reach Alfred. `silent` and `record_incomplete` have recovery `none`, and each is a composer fact: Alfred cannot say that the window was quiet. The composer reads the activity input through `list_activity`, so the input is in `COMPOSER_READS`. The verified pull moves to a new input, `deploy_status`. Its composer fact names `get_day_shape`, because that tool counts the pull items. A `stale` entry is a log line only, because no composer tool returns the old item. ADR-0118 **Built: slice 3** has the details.

## Rejected alternatives

- **A list of cases in the prompt.** The owner cannot list them, and a prompt does not make the model apply a rule (ADR-0110 measured a cheap model that ignored a matched instruction for a month).
- **The composer decides what is missing.** On 2026-10-28 the composer dropped an open item because a rule told it to drop rows it could not check. A rendered row cannot be dropped.
- **A silent location from the sign-in IP.** See decision 3.
- **Forecast codes as warnings.** A heavy-rain code is not an agency warning. It has no area, no severity scale, and no issuer.

## Preserved behavior

The ADR-0048 content model, the composer's voice rules, and the weather row format do not change. The ADR-0064 quiet-morning rule changes by two inputs: the block rows of the ADR-0100 amendment, and a selected warning for the user's place (decision 4). A `fallback` does not send a morning, and a warning for the time-zone default city does not send one either. A user with a `location` preference sees no change in the weather row.

## Residual risk

- Feed coverage differs by country. A country with no CAP feed gets only the large global events.
- A cyclone's area is a forecast track, not a fixed shape. Slice 3 uses containment with no distance band, so a cyclone whose wind areas and cone stop short of the place is not selected, also when it is near.
- The GDACS `WindRadii` areas are snapshots 12 hours apart (in the capture of 2026-11-01). Between two snapshots the cyclone moves, and no area shows where it is. A place near the edge of the wind, between two snapshots and outside the cone, can be missed.
- A Sachet alert whose only area is a polygon cannot match. On 2026-11-01 the Andhra Pradesh SDMA cyclone alerts had a `Polygon URL` parameter and a non-place `areaDesc`. The polygon endpoint refuses a script (HTTP 403), and Alfred does not try to get around it. GDACS still selects an Orange or Red cyclone whose wind area or cone contains the place. A read of the polygon route is a follow-up (see **What slice 3 does not catch**).
- The geocode and LGD can spell a district in two ways (for example "Nellore" and "Sri Potti Sriramulu Nellore"). Then the code match fails, and the name match finds only an area text that uses the geocode's spelling. The reader logs a place that has no single LGD district. LGD has renamed several districts (for example Aurangabad to Chhatrapati Sambhajinagar, Osmanabad to Dharashiv, Allahabad to Prayagraj, Gurgaon to Gurugram, and Faizabad to Ayodhya), and a geocode can still give the old name. Then the user gets no code, and an alert matches only when its area text has the old name and the state name. Alfred has no alias table for these names.
- The Sachet RSS file holds about two days of alerts. A long warning issued before that window is not read.
- A user with no preference and no evidence still gets the time-zone city. The difference is that the briefing now says so.
- On a travel day the gather reads warnings for the user's usual place, not for the calendar city, until slice 4.
- A cold Sachet read is about 100 CAP files. When the deadline stops some of them, the briefing says that it may be missing warnings. If this occurs often, the clause becomes noise.
- Alfred now reads Sachet for the Delhi default city, because each time-zone city states its country, and Delhi states its district. A user in India with no place thus gets a Sachet read (about 100 CAP files when cold) for a city that is not the user's place. A Delhi warning appears, with the city name, in a briefing that sends for other reasons.
- A Sachet update or cancel matches the alerts that it replaces by the identifier in `references` only, not by the sender. Two senders with the same identifier can thus remove the wrong alert. A CAP `Error` message is not handled: Alfred drops it, and the alert that it names stays.
- A GDACS event list over its page bound (five pages of 100) counts as one unread item, because Alfred does not know the number of events after the bound. So the count in the reason can be too low.
- A warning section of the legacy composer has no source value for official warnings. It uses the `day_of_week` source, because no gather source names warnings.

## Implementation slices

1. The one location reader, with the confirmed `home_city` fact before the time-zone default. This alone fixes the 2026-10-28 weather row.
2. The provenance type on the current contributions: email, calendar, weather, integration activity, the GitHub merged read, and loop relevance. The only visible change is the block rows and the removal of stale activity items.
3. The warnings feed and the geometry match, after a probe of the candidate feeds.
4. The location evidence proposal (rail geolocation, calendar, sign-in region) and its confirmation.
