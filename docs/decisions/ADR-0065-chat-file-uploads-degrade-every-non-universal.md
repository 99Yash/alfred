# ADR-0065 — Chat file uploads: degrade every non-universal modality to text+images at ingest; the boss never sees a file type a model can't read


**Decision.** Chat gains file upload (today the composer's paperclip is a dead button — no input, no endpoint, no attachment column, no file parts). The load-bearing choice is **not** "route unsupported uploads to a capable model" — it is to **degrade every non-universally-supported modality into text (+ optional keyframe images) at ingest**, so that the only things ever handed to the boss model are **text and images**, the two modalities every boss model reads. Storage is **`files-sdk` over an S3 driver pointed at Railway buckets**; ingest runs as a **BullMQ `media.degrade` job** reusing the existing `transcribeAudio()` (OpenAI `gpt-4o-mini-transcribe`) for audio and **ffmpeg** for video (split audio track → transcribe; extract keyframes → image parts). The boss's model selection stays a **deterministic, pre-flight** concern; it is never an LLM/prompt decision, and after this work there is nothing left to route because nothing unreadable reaches the model.

**The load-bearing invariant — the boss receives only text and images; modality is normalized at the seam, never at the model.** A user upload produces **two artifacts**: the **raw media** (bucket, retained for replay/preview in the UI) and the **degraded artifact** (text transcript + optional keyframe images) that is the *only* thing entering the transcript and the model context. Images pass through untouched (universal). Everything else — video, audio, PDF, docx/xlsx/code — normalizes to text (+images) at ingest. This single invariant collapses three otherwise-hard problems at once:

- **No model-capability gate, no force-routing.** The originally-proposed `MODEL_CAPABILITIES` registry + "force video/audio turns to Gemini 2.5 Pro" is **rejected** (see Alternatives). Routing-per-turn is unsound: once a video file-part lives in a thread's transcript, every *subsequent* turn replays it, so a single video would pin the whole thread to Gemini and silently downgrade the user off their chosen tier (Auto=Sonnet 4.6 / Deep=Opus 4.8). Degrading at ingest means the historical transcript only ever holds text+images → no poisoning, no pinning, tier picker and attachments are orthogonal.
- **The PDF/Sonnet-4.6 capability question disappears.** models.dev lists Sonnet 4.6 as image-only (no PDF); rather than verify per-model PDF support and branch, **PDF degrades to text at ingest** (page-image rendering deferred), model-independently.
- **Gemini reverts to a pure reliability fallback** (ADR provider chain) — it is *not* on the ingest path and not a routing target.

**Why degrade-at-ingest over route-to-capable-model (the central grilled fork).** Routing makes "which model serves this turn" depend on attachment modality *and* on thread history (the replay problem above), reintroduces non-determinism, and couples the user's explicit tier choice to whatever they happened to attach. Degrading makes the model layer modality-agnostic forever, reuses infra already in the tree (`transcribeAudio`, BullMQ, the AI-SDK image-part path), and matches what the dimension reference app already does for documents (client-side doc→`txt_content`) — generalized to all non-universal modalities. The cost is an ingest pipeline (ffmpeg + transcription) and a native-binary dependency; accepted.

**Amendment (2026-06-24): storage moved to Cloudflare R2.** The provider-agnostic seam paid off — repointing the `CHAT_S3_*` vars at an R2 bucket (S3-compatible, `REGION=auto`, `ENDPOINT=https://<accountid>.r2.cloudflarestorage.com`) moved storage off Railway with **zero call-site changes**. Motivation was cost (R2's no-egress-fee free tier vs. Railway bucket usage) and that R2 supports a real CORS policy (the old Railway provider served no `Access-Control-Allow-Origin`, forcing the server-proxied upload relay; that relay stays the v1 path regardless). The paragraph below stands as originally decided; substitute "R2" for "Railway buckets" throughout.

**Storage — `files-sdk` over Railway buckets, lifecycle keyed to the thread, deletion by prefix.** `files-sdk` (S3 driver → Railway's S3-compatible buckets) gives a provider-agnostic `signedUploadUrl()`/`url()`/`delete()` surface; if Railway buckets disappoint, swap a driver, not app code. Bucket objects are **not** reachable by Postgres FK `CASCADE` (the orphaned-blob trap), so lifecycle is solved by a **key convention** rather than a tracking table: every object lives under **`chat/{userId}/{threadId}/{messageId}/{file}`**. Deletion is then a single **prefix delete** enqueued as a BullMQ cleanup job — **thread delete** → drop `chat/{userId}/{threadId}/`; **account delete** → drop `chat/{userId}/` (the existing user-FK cascade — ADR single-user-cascade — clears the rows). No reconcile sweeper for v1 (single-user, near-zero orphan risk; log-and-move-on). Raw media **dies with the chat** — it is conversation context, not a media library. Per-file caps **10–15 MB** (Alfred is single-user — dimension's 50 MB multi-tenant abuse caps are over-built here).

**Orchestration — one turn, graceful partial answer, live status; no proactive messages.** The boss harness today is strictly request→response: it **cannot await/poll a job mid-turn** and there are **no proactive follow-up messages** (only `spawn_sub_agent`'s fire-and-forget + scratchpad-read-on-next-turn, ADR-0036). Building proactive follow-up is a **separate epic, explicitly out of scope.** Because the user sends the prompt *with* the media in one message, v1 does this:

- **Enqueue `media.degrade` the instant the file is attached** (not at send) — degrade runs while the user is still typing, so by send-time it is usually already done (the cheap 80% of the async win).
- **Live degrade status** surfaced to the composer — **poll a status endpoint ~1s** for v1 (SSE push from the worker deferred).
- At turn time, a **bounded await** on the degrade job: ready → the boss runs with the full degraded artifact in context; not-ready-within-bound → the boss answers **the parts of the prompt that don't depend on the media** with an honest "still processing your upload" note, and the ready artifact lands naturally on the **next user turn** (no proactive push needed — the prompt and media share a thread).
- **Seam for the future:** attachment + degrade-status are passed into the boss context as a **structured field**, so a later epic can add true "answer-around-pending-media / proactive completion" once proactive messages exist — the A-now / B-ready-seam pattern (ADR-0060 standing-instructions precedent).

**Architectural shape.**

- **Ingest policy (`@alfred/contracts`, pure).** A deterministic `INGEST_POLICY` map: MIME (or MIME-class) → `{ kind: "pass-through" | "degrade-text" | "degrade-av" | "reject" }` + the `SUPPORTED_FILE_TYPES` whitelist and per-type size caps (borrowed from dimension's `upload-helpers.ts`, web-safe, zero Node deps so the composer and the worker share one truth). This *replaces* the rejected `MODEL_CAPABILITIES` idea — the question is no longer "which model reads this" but "how is this normalized to text+images."
- **Storage adapter (`@alfred/api`, server-only).** A thin `chat-storage` wrapper over `files-sdk` (S3 driver, Railway creds via `serverEnv()`): `signedUploadUrl(key)`, `url(key)`, `deletePrefix(prefix)`. Key builder enforces the `chat/{userId}/{threadId}/{messageId}/` convention.
- **Degrade worker (`@alfred/api`, `ingestion-runs` queue).** New job `media.degrade { attachmentId, userId }`: image → mark ready (pass-through); audio → `transcribeAudio(bytes)`; video → ffmpeg split audio → `transcribeAudio` + ffmpeg keyframes → image objects; pdf/docx/xlsx/code → text extraction. Writes the degraded artifact + flips status `pending→ready|failed`. **ffmpeg is added to the `apps/server` deploy image** (Nixpacks/Dockerfile) — workers run in-process in `server`.
- **Data model (`@alfred/db`).** A `chat_attachments` table (FK → `chat_messages`, **CASCADE**) rather than a jsonb column on the message: async status transitions (`pending|ready|failed`) and per-attachment degraded artifacts update cleanly without rewriting the message row. Columns: storage key, mime, name, size, `status`, `degraded_text`, `degraded_image_keys`, `lifecycle_dates`. `db:generate` → `db:migrate` (never `db:push`).
- **Transcript assembly (`chat-turn.ts`).** When building the model transcript, ready attachments map to AI-SDK parts: `degraded_text` appended as text + `degraded_image_keys`/images as image parts. **Raw media is never sent to the model.**
- **Composer (`apps/web`).** Borrow dimension's `attachment-input` UX (multi-file, drag/drop/paste, client-side validation against the shared whitelist + caps, doc→text client-side where trivial), wire the dead paperclip, upload via `signedUploadUrl`, render live degrade status.

**Sequencing (lowest-risk-first).** **Phase 0** — ADR + plan (this). **Phase 1** — storage adapter + `chat_attachments` table + signed-URL upload endpoint (no degrade yet; images pass-through end-to-end — proves the bytes path). **Phase 2** — degrade worker for the no-ffmpeg modalities (audio via `transcribeAudio`, pdf/docs→text) + transcript assembly + composer status UI. **Phase 3** — ffmpeg in the server image → video (audio-split transcript + keyframes). **Phase 4** — bounded-await + graceful partial-answer + the boss-context status seam.

**Why.** The feature is unbuilt end-to-end, so the design is free to pick the invariant that makes the model layer simplest forever: normalize at ingest so the boss only ever sees text+images. That kills routing, history-poisoning, the tier/attachment conflict, and the per-model PDF-capability branch in one move; reuses `transcribeAudio`, BullMQ, and the image-part path already in the tree; and keeps storage provider-agnostic and deletable by a single prefix. It also re-homes the user's "route to Gemini" instinct at the *right* layer — Gemini-class multimodality is an *ingest* concern (and we actually do it deterministically with ffmpeg+OpenAI), never a turn-routing one.

**Alternatives.** (a) **`MODEL_CAPABILITIES` registry + force-route video/audio to Gemini 2.5 Pro** (the design that entered the grill) — **rejected**: routing is a per-turn decision but file-parts persist in the transcript, so one video pins the whole thread to Gemini and silently downgrades the user's chosen tier; reintroduces non-determinism and couples tier to attachment. (b) **Inline base64 file parts, no bucket** — rejected: the user wants the raw media retained for replay, and base64 bloats the transcript/DB and still hits provider size limits; buckets + a key convention are cleaner and give a real deletion story. (c) **Pass PDF through to PDF-capable tiers, degrade only for image-only tiers** — rejected: reintroduces per-model branching and the tier/attachment coupling the invariant exists to kill; degrade-PDF-to-text is model-independent (page-image render deferred). (d) **Proactive follow-up messages so the boss answers later when media is ready** — rejected for v1: a separat…46 tokens truncated…with a structured-context seam left for the epic. (e) **Gemini as the ingest adapter** (one Gemini call emits transcript+description) — rejected: `transcribeAudio` already exists and ffmpeg gives real keyframes deterministically; keeps Gemini off the hot path entirely. (f) **Copy dimension's GCS upload code wholesale** — rejected: it's GCS-specific and tangled with their tRPC signed-URL endpoint + NATS; borrow the *validation/UX logic*, let `files-sdk` own the bytes.

**Parked.** Proactive "I've finished reading your video" completion messages (the centrality epic). SSE-pushed degrade status (poll-1s for v1). PDF page-image rendering (text-only v1). Scene-detection keyframes / frame-count tuning (fixed-interval v1). A bucket-vs-DB reconcile sweeper for orphans (single-user, log-only v1). Sharing/persisting media beyond thread lifetime (a media library). Embedding/RAG over uploaded files (these are turn-scoped context, not ingested corpus — unlike Gmail/Drive).

**Open.** Exact per-type caps within 10–15 MB and total-files-per-message. Bounded-await timeout value (and whether the composer's enqueue-on-attach head-start makes it rarely fire). Keyframe interval + max count. PDF text-extraction lib (and whether scanned PDFs need OCR — likely a v2 `reject` until then). Whether docx/xlsx→text runs client-side (dimension's `mammoth`) or in the worker. Status transport: confirm 1s-poll is acceptable vs a small SSE addition. Plan: [docs/plans/chat-file-uploads-v1.md](../plans/chat-file-uploads-v1.md).

**Implementation notes & honest costs (Phase 1 review, 2026-06-22).** Five things the build settled differently from, or more sharply than, the design above — recorded so the next phase reads them as choices, not accidents:

- **PDF (and any non-universal modality) degrades to *lossy* text — this is the known v2 gap, not a free win.** The body says "the PDF/Sonnet-4.6 capability question disappears." More precisely: it is *answered* with "degrade to extracted text and accept the fidelity loss." A scanned contract, an infographic, or a layout-heavy PDF gets a worse answer than a natively-multimodal ChatGPT/Gemini would. **PDF page-image rendering is therefore promoted from "deferred" to the known v2 gap** — the first thing to revisit when fidelity complaints appear.
- **Image transcript replay is bounded-per-turn but not compacted — a v2 gap.** Pass-through images are stored as object keys and re-read + re-base64'd into the model message on *every* turn (`hydrateTranscriptForModel`). Total inlined bytes per turn are capped (`MAX_MODEL_ATTACHMENT_BYTES_PER_TURN`, and `byteSize` on the stored part lets the budget gate skip over-budget images *without* downloading them), so it is not unbounded in the worst sense — but within budget there is **no cross-turn cache and no compaction**, so a thread with screenshots re-fetches and re-encodes the recent ones each turn (real input-token cost on Deep/Opus). Deferred fix: past a turn/byte threshold, replace older image parts with `[earlier image: name]` text at assembly time.
- **Ingest-abuse limiting (per-minute rate limit, per-message pending-bytes budget + reserve/release ledger, orphan reaper) is multi-user forward-compat, not a v1 need.** A single authed user cannot meaningfully commit upload abuse; this machinery is kept (working + tested) as the seam for a future multi-user surface, not because v1 requires it. Framed here so it reads as a deliberate over-build, not a contradiction of "dimension's multi-tenant caps are over-built."
- **Faithful retry copies bytes for key-purity, by design.** Re-sending a failed image turn `copyObject`s the prior message's bytes under the *new* message's key prefix rather than referencing the source key — so every message still owns its objects and the `chat/{userId}/{threadId}/` prefix-delete cleanup stays complete. The extra copy is the price of the key convention, not accidental complexity.
- **`/attachments/sign` is removed; `/attachments/upload` is the sole ingest.** Railway's bucket serves no CORS `Access-Control-Allow-Origin`, so the browser can never PUT direct-to-bucket — the signed-upload route was dead. With server-proxied upload as the only path (and it sniffs + libvips-decodes bytes before writing), **send-time validation collapses to a cheap `headObject`** existence+size+type check instead of a full re-download + re-decode on the user-blocking path. One deviation rides along: Phase 1 **uploads at send** (`Promise.all` on Enter), not on-attach as the plan intended — acceptable for images-only, but **restoring upload-on-attach is a prerequisite for Phase 2's bounded-await timing assumptions.**
