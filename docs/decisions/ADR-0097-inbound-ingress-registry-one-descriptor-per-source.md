# ADR-0097 — Inbound ingress registry: one descriptor per source behind one route

**Status.** Accepted (issue #562, Seam 1 of #554).

**Decision.** Inbound webhook sources are a typed registry, not an enum edit in three places.

1. **The contracts record is the source space.** `EVENT_SOURCE_ENTRIES` in `packages/contracts/src/event-triggers.ts` is one record keyed by source slug. Each entry names its `producer` (`in_process` or `inbound_webhook`) and its event-type tuple. `EVENT_SOURCES`, `EventSource`, `InboundEventSource`, `InProcessEventSource`, `EVENT_TYPES_BY_SOURCE`, and `EVENT_TYPES` are derived from it. This amends ADR-0047 item 3: the pair is still closed and const-narrowed, but it is one record, and per-source `*_EVENT_TYPES` constants are gone.
2. **One descriptor per inbound source, typed against its entry.** `InboundSourceDescriptor<S>` in `packages/assistant/src/connections/ingress/descriptor.ts` owns exactly the provider-specific knowledge: `verify(raw, headers)` over the raw bytes in constant time, a required `dedup` rule whose synthetic key receives the projected event type and switches on it exhaustively, `project(payload, headers)` to an event type the entry declares, `resolveOwner`, and an optional `subscription.health`. The registry `INBOUND_SOURCES` is typed `{ [S in InboundEventSource]: InboundSourceDescriptor<S> }`. An `inbound_webhook` entry with no descriptor, a descriptor whose slug the record does not declare, and a descriptor filed under the wrong key (`InboundSourceDescriptor<S>` pins `slug: S`) are all compile errors. No boot-time assertion repeats what the compiler proves, and header casing needs none: `Headers.get` is case-insensitive.
3. **One route.** `POST /webhooks/inbound/:source` in `packages/http/src/connections/inbound-webhook.ts` hands the raw body and headers to `receiveInboundDelivery`, which runs the shared path: look up, verify raw, parse, project, key, attribute, insert one `event_receipts` row with `onConflictDoNothing`, enqueue `ingress.deliver`. The route maps the outcome to a status and knows no provider. `POST /webhooks/github` stays as an alias because the GitHub App's hook URL points there. The receive path and the job body live in `packages/assistant/src/connections/ingestion/` (`inbound-receive.ts`, `inbound-deliver.ts`), beside the queue they produce for and run in; `connections/ingress/` holds only the descriptors, the registry, and the health reader, so the door that trigger readiness imports never reaches BullMQ.
4. **The receipt is the delivery.** `event_receipts` gains a nullable `payload` column (migration 0114). An inbound row stores the verified body under `provider = <slug>`, `provider_delivery_id = <dedup key>`, `event_type = <slug>.<type>` (written by `eventTypeName` and read back by `parseEventTypeName` in `@alfred/contracts`, the one home for that encoding; the Gmail receipt writer uses the same function). The `ingress.deliver` job publishes `{ receiptId, deliveryKey }` on the trigger bus and marks the row `completed` or `failed`. The domain event is a pointer, the same rule ADR-0047 set for Gmail.
5. **A degraded subscription is a readiness problem, not silence.** `readInboundTriggerHealth(userId)` reads each descriptor's `subscription.health`. A descriptor with no `subscription` adapter reads as degraded. An unhealthy entry names its own recovery, `{ kind: "connect", integration }`, `{ kind: "retry" }`, or `{ kind: "none" }`, so readiness maps the first two straight onto `WorkflowRecoveryAction` and never guesses an integration from the source slug (the two slug spaces only happen to collide on `github`).
   *Amended 2026-09-06 (#976).* Readiness reads **one map keyed by `EventSource`**, `readEventSourceHealth(userId, availability, now)` in `packages/assistant/src/automation/event-source-health.ts`, not one map per producer. The map is a `Readonly<Record<EventSource, EventSourceHealth>>`, so the resolver's lookup cannot miss and there is no fallback verdict for an absent source; the only place a fallback exists is inside the inbound fold, for a descriptor with no `subscription` adapter. The verdict shape is `EventDeliveryHealth` in `connections/ingress/descriptor.ts`; the inbound adapters return it directly, and nothing outside `@alfred/assistant` reads it, so it does not live in `@alfred/contracts`. **The grain is declared on the entry.** `EVENT_SOURCE_ENTRIES[source].delivery` is `{ grain: "source" }` or `{ grain: "account", integration }`; `eventDeliveryAccounts(source)` derives the credential provider and the connected rule from the integration registry, and canonicalization, the approval display, the Gmail reader, and the resolver all read that one field. An `inbound_webhook` entry is `source` grain by type, because `InboundSubscriptionAdapter.health(userId)` answers for the user as a whole; a per-account inbound source (a Slack workspace, say) needs a new adapter shape before the entry type admits it. **The grain also sits on the value.** `EventSourceHealth` is `{ grain: "source", health }` or `{ grain: "account", accounts, healthOf(row) }`; `healthOf` is a function of the availability row, not a map keyed by account id, so a selected row always has a verdict. A `(source, accountRef)` tuple key was rejected because inbound triggers carry no `accountRef`, so every source-grain entry would need a sentinel ref. **Selection is not a delivery verdict.** For an account-grain source the resolver first settles the account with the rules the capabilities use: no row that proves the integration connected is a `connect` problem (`trigger_not_ready`); a ref that names no row or more than one, or no ref at all, is `choose_account` on the `trigger` field; only a selected row is asked for its delivery health. Before this amendment an ambiguous ref was resolved by position, and every unresolved ref read as a missing watch. **In-process sources name a reader or claim `healthy_by_construction`.** The reader table is `satisfies { [S in InProcessEventSource]: … }`, so a new in-process source does not compile until it says which; the claim is admissible only at source grain, and it means this process publishes the events, so there is no subscription to lose (`google.oauth.callback`, `learn-skill`, `email-triage`). **Two problem codes, chosen by the recovery kind.** `connect` means the user must act, so the trigger gets `trigger_not_ready` and the workflow blocks; `retry` and `none` describe delivery that time or an operator restores, so the trigger gets `trigger_degraded` and the run defers. `provider_unhealthy` leaves the readiness vocabulary (`RunDeferReason` keeps its own `provider_unhealthy`; that is the run scheduler's word, not a readiness code). The resolver takes `{ availability, eventSourceHealth }` as one `WorkflowReadinessContext`, read by `readWorkflowReadinessContext`, so the rows a trigger resolves against are the rows its health was read for. The change probe: a new inbound source adds a descriptor and appears in the map with no edit to readiness.
6. **The registry is the ceiling, not the definition.** `AUTHORABLE_EVENT_SOURCES` in `@alfred/sync` stays `["gmail"]`. The registry removes the enum ceiling; which sources a user may subscribe a workflow to remains a curated subset.
7. **Gmail stays on its own route.** Its Pub/Sub push is OIDC-authenticated and carries a pointer, not the event; the ingestion worker publishes Gmail's domain events, so its entry is `in_process`.
8. **`event_receipts` owns the GitHub body, and it is the only copy.** The verified body sits in `event_receipts.payload` and nowhere else. The `github-activity-fold` consumer reads it back by receipt id and runs the ADR-0062 reducer over it directly; `briefings/gather.ts` and the committed object-state backfill read the same rows, filtered on `provider = 'github'` and decoded with `parseEventTypeName`. The consumer runs in `propagate` mode: a failed fold fails the `ingress.deliver` job, the receipt reads `failed`, and the queue retries. The reducer is idempotent, so a retry re-applies the same event with the receipt's own `delivered_at` and cannot regress state. *Amended 2026-09-06 (#975).* As first accepted, this item kept `webhook_events` as a transitional legacy read shape that the consumer wrote from the receipt, with #975 named as its closer. #975 moved both readers, dropped `webhook_events` (migration 0117 copies its attributable rows into `event_receipts` first, so the audit trail keeps the pre-cutover deliveries), and removed the `WebhookEvent` row type. Nothing reads or writes `webhook_events` now.

**Why.**

- **Three edits per source is no capability.** Before this change a new push source was an enum edit in contracts, a hand-written route in `@alfred/http`, and a switch case in the trigger module. `github-webhook.ts` was already the descriptor pattern by hand: raw-body HMAC, then `onConflictDoNothing` keyed on `X-GitHub-Delivery`. The work generalizes it.
- **Verification before parse is the trust boundary.** The `parse` hook hands the handler the exact bytes. Re-serializing a parsed body changes whitespace and breaks the HMAC. No agent-authored verifier exists: each `verify` is a few lines of provider code that must be right.
- **Dedup is declared, never guessed.** `dedup` is a required discriminated union. A source with no stable delivery id must declare a synthetic key over the payload. A source that declares neither does not compile, which is stronger than the issue's "fails at boot". The key is `(payload, type, payloadHash) → string | null`, where `type` is what `project` returned: a switch on it with a `never` default proves every subscribed type has a key rule, so `null` can only mean the payload lacks the identity the rule reads. Where a provider repeats one identity for distinct events and offers no other fact (Sentry's issue transitions), the key folds in a slice of the body digest and accepts the rare retry that re-serializes a changed body as a duplicate receipt, because the alternative drops a real event for good.
- **Acknowledge fast, then work.** The request returns as soon as the receipt row exists. The bus, the object-state fold, and any workflow run happen in the `ingress.deliver` job and its consumers. A slow handler ends delivery for some providers (Sentry auto-unsubscribes after 1000 timeouts in 24h), so nothing runs inline.
- **Fan-out stays on the bus.** ADR-0047 removed hardcoded fan-out. The old route called the ADR-0062 object-state reducer inline; that fold is now the `github-activity-fold` trigger consumer in `packages/assistant/src/runtime/adapters/github-activity-consumer.ts`, which reads the receipt payload by id and runs the reducer over it. (Until #975 it also inserted a `webhook_events` row and ran the reducer only for a newly inserted one; the receipt's own dedup index and the deliver job's `completed` skip make that gate redundant.)
- **Seam 2 depends on this.** Rung B and rung C completion notices arrive as inbound webhooks. A delegated run cannot report home without a descriptor to report into.

**Alternatives rejected.**

- (a) **Keep `EVENT_SOURCES` and add a `github` route by hand.** Preserves the three-edit cost the issue names.
- (b) **Descriptor in `@alfred/contracts`.** `verify` needs the webhook secret and `resolveOwner` needs the database; neither is browser-safe. Contracts keeps the entry, the server keeps the descriptor, and the mapped type joins them.
- (c) **`deliveryId(): string | null` with an implicit "probably unique" fallback.** The spec forbids it. The required `dedup` union makes the fallback unrepresentable.
- (d) **Publish the body on the bus.** Puts third-party text in `agent_runs.trigger.payload`, which ADR-0047 rejected for Gmail, and copies it into every run the event starts. (The body sat in two tables during the cutover item 8 describes; #975 closed that.)
- (e) **Store unattributable deliveries with `user_id NULL`.** `event_receipts.credential_id` is `NOT NULL` with a cascade, and a row nobody owns has no consumer. Such deliveries are acknowledged and logged, not stored. `webhook_events` used to keep them; that behavior changes.
- (f) **Run the fold inline in the route.** Reintroduces hardcoded fan-out and puts reducer latency on the provider's timeout budget.
- (g) **Keep the fold `best-effort`.** The inline handler isolated the reducer so its error could not 500 the provider. Inside a queued job with five retries that reason is gone, and `best-effort` would count a failed fold as accepted, mark the receipt `completed`, and leave no path to ever write the row: a redelivery finds `completed` and does not re-enqueue, and no reconciler reads `event_receipts.payload`. The fold is idempotent (`applyEvent` is monotonic on `stateDeliveredAt` with an absorbing `resolved` guard), so a retry is safe and `propagate` is correct.

**Implementation notes.**

- The `ingress/` door imports no queue and no bus, because `automation/readiness-context.ts` imports it. The queue's producer (`inbound-receive.ts`) and the job body (`inbound-deliver.ts`) live in `connections/ingestion/`, where importing `queue.ts` is normal; the receive path calls `enqueueInboundDelivery` directly and the route imports one name from the ingestion door.
- The `ingress.deliver` job uses `jobId = ingress.deliver.<receiptId>` with `removeOnFail: true`. BullMQ refuses a second `add` for a `jobId` whose record still exists in any state (`addStandardJob` → `handleDuplicatedJob` only emits `duplicated`), which is the wanted no-op while the job is live and closes the crash window between the insert and the first enqueue. With the queue's default `removeOnFail` (seven days) it would also swallow every redelivery after the last attempt failed, and the receipt would stay `failed` with no way to revive it; `removeOnFail: true` drops the record with the final failure so the next redelivery adds a fresh job. The receipt row records the failure, so the queue's failed set added nothing.
- `deliverInboundReceipt` skips a `completed` receipt and retries a `failed` one, so the queue's retry attempts are not defeated by the status the previous attempt wrote. A receipt whose stored event type its source does not declare is a permanent data error: it is marked `failed` and the job returns rather than throwing, so the queue does not spend five attempts on it.
- Residual risk of the `propagate` fold: on a retry `acceptEvent` runs again for the same event. ADR-0047's idempotency is bounded, an active-run unique index over the event identity on non-terminal rows (#531), so a retry that lands after the first workflow run has already finished can start a second run for the same delivery. Accepted: the fold's failures are connection faults with a five-second first backoff, and a workflow run rarely finishes inside that window.
- `githubInstallationId` lives in `@alfred/integrations/github` beside `findCredentialByInstallationId`, which already owns installation ids; the descriptor and the fold consumer both import it from there.
- `findCredentialByInstallationId` in `packages/integrations/src/github/credentials.ts` replaces `findUserByInstallationId`: the receipt needs the credential id and the account id, not only the user.
- No feature tests (CLAUDE.md). The compiler proves the registry is exhaustive, `parseJsonWith` and `inboundDeliveryPayloadSchema` parse at the boundaries, and `check:exports` and `check:architecture` hold the module lines. Residual risk: the receive path's insert-then-enqueue ordering and the duplicate re-enqueue are proved by reading, not by a test.
