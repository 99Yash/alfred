# ADR-0088 — The `mcp.call` approval floor is a floor, not a constant: a reviewed per-descriptor downgrade lowers it at the dispatch gate, delegated entirely to a single fail-closed resolver (BUILT — #541 Part 3; amends ADR-0069)


**Decision.** `mcp.call` keeps its static `high` `riskTier` as a **floor**, not a fixed tier. A `resolveRiskTier` hook on the tool definition (`packages/api/src/modules/tools/registry.ts`) computes the EFFECTIVE tier from the validated input at the dispatch gate; for `mcp.call` it delegates to `resolveMcpCallRiskTier` (`packages/api/src/modules/mcp/risk.ts`), which honors a reviewed lower tier from `mcp_tool_policy` **only when** the caller owns the connection, the echoed `catalogRevision` is the connection's current one, and a reviewed policy binds to the exact `(connection, remoteName, descriptorHash)` of the tool being called. Every point of uncertainty — unowned/absent connection, missing or stale revision, descriptor drift, no policy, or an out-of-enum persisted tier — returns the `high` floor. This lets a user-reviewed safe tool (e.g. a read downgraded to `low`) stop staging for approval on every routine call, while an unreviewed or drifted tool always re-gates.

**Why.** ADR-0069 made `high` a hard approval floor the autonomy toggle cannot override. That is correct for an *unreviewed* outbound MCP action but wrong forever: once the user has explicitly reviewed the exact descriptor and recorded a lower tier, re-prompting every time is nagging, not safety. Binding the downgrade to the descriptor **hash** is what keeps it honest — a server that changes a tool's schema produces a fresh hash, a policy miss, and an automatic re-gate, so a downgrade granted for one shape can never silently carry to another.

**Trust boundary (the load-bearing part).** The dispatcher does **not** clamp the resolver's return (`dispatch/index.ts` — `const riskTier = tool.resolveRiskTier ? await tool.resolveRiskTier(...) : tool.riskTier`); it cannot, because the feature is precisely to go *below* the static floor. `toolRequiresApproval` then gates on `riskTier === "high"`, so any value the resolver returns other than `high` waives approval. The `resolveRiskTier` hook is therefore the **sole** gate on lowering an approval floor — there is no central guard, type, or test that makes an over-permissive return impossible. The safety invariant rests on (a) `resolveMcpCallRiskTier` being fail-closed and (b) the hook's contract doc requiring every implementer to be. Today this is a **tier-3 control**: one caller, decision centralized in one resolver. It is accepted as-is *for one caller*; the named debt is that a second implementer returning an over-permissive tier on a bug would silently un-gate a high-floor action. If the hook grows past one caller, the guard must be promoted from convention into a central clamp + downgrade audit rather than another hand-written careful function.

**Residual (named, not covered).** (1) **No downgrade audit yet.** The staging row persists the *effective* `riskTier` but not the authorizing `policyRevision`, and there is no observation/ledger breadcrumb naming which review waived the floor — a gap for a batch that spent Parts 1–2 on correlation evidence. Acceptable while the write path (`upsertToolPolicy`) has only test callers, so no real downgrade can occur; add the breadcrumb when Part 4 wires the write path. (2) **Narrow TOCTOU on the downgraded path.** For a tool downgraded below `high`, approval is waived at the gate against the *current-at-gate* revision; if the catalog refreshes between gate and execute, the broker's effect axis re-checks (descriptor miss → `unknown` → barrier) but approval was already waived against the pre-drift descriptor. The window is near-zero (downgraded calls are autonomous and execute immediately) and unreachable today (write path unwired), but it becomes real the moment Part 4 ships the write path. (3) **Gate/execute are not "coherent," only independently conservative.** The gate reads `revision.descriptorHashes[remoteName]`; the broker recomputes `descriptorHash(liveTool)` live. They agree only absent drift; under drift both default conservatively (floor here, `unknown`/effectful there) — a safety property, not an equality guarantee.

**Alternatives.** (a) **Clamp in the dispatcher** — impossible without defeating the feature (the clamp would be the floor). (b) **Return a richer object** (tier + authorizing policy) so dispatch can audit centrally — deferred as over-engineering for one caller; revisit with residual (1) when the write path lands. (c) **Keep `high` a hard constant** — rejected: it is the ADR-0069 nagging problem this ADR exists to fix.

**Cross-ref.** Amends ADR-0069 (the hard-confirm floor — now a floor a *reviewed* downgrade can lower, never the autonomy toggle). Builds on the #540 MCP broker/persistence substrate (ADR-0018 lineage) and Parts 1–2 of #541 (result provenance, correlation evidence). The hook contract lives in `LiveToolArgs.resolveRiskTier`; the resolver and its fail-closed branches in `mcp/risk.ts`.
