# ADR-0088 — The `mcp.call` approval floor is a floor, not a constant: a reviewed per-descriptor downgrade lowers it at the dispatch gate, delegated entirely to a single fail-closed resolver (BUILT — #541 Part 3; amends ADR-0069)

**Decision.** `mcp.call` keeps its static `high` `riskTier` as a **floor**, not a fixed tier. A `resolveRiskTier` hook on the tool definition (`packages/assistant/src/tool-runtime/internal/registry.ts`) computes the EFFECTIVE tier from the validated input at the dispatch gate; for `mcp.call` it delegates to `resolveMcpCallRiskTier` (`packages/api/src/modules/mcp/risk.ts`), which honors a reviewed lower tier from `mcp_tool_policy` **only when** the caller owns the connection, the echoed `catalogRevision` is the connection's current one, and a reviewed policy binds to the exact `(connection, remoteName, descriptorHash)` of the tool being called. Every point of uncertainty — unowned/absent connection, missing or stale revision, descriptor drift, no policy, or an out-of-enum persisted tier — returns the `high` floor. This lets a user-reviewed safe tool (e.g. a read downgraded to `low`) stop staging for approval on every routine call, while an unreviewed or drifted tool always re-gates.

**Why.** ADR-0069 made `high` a hard approval floor the autonomy toggle cannot override. That is correct for an _unreviewed_ outbound MCP action but wrong forever: once the user has explicitly reviewed the exact descriptor and recorded a lower tier, re-prompting every time is nagging, not safety. Binding the downgrade to the descriptor **hash** is what keeps it honest — a server that changes a tool's schema produces a fresh hash, a policy miss, and an automatic re-gate, so a downgrade granted for one shape can never silently carry to another.

**Trust boundary (the load-bearing part, superseded by the 2026-08-11 amendment below).** The original dispatcher did **not** clamp the resolver's return (`dispatch/index.ts` — `const riskTier = tool.resolveRiskTier ? await tool.resolveRiskTier(...) : tool.riskTier`); it could not apply a simple static floor because the feature was precisely to go _below_ that floor. `toolRequiresApproval` then gated on `riskTier === "high"`, so any value the resolver returned other than `high` waived approval. The `resolveRiskTier` hook was therefore the **sole** gate on lowering an approval floor. The safety invariant rested on (a) `resolveMcpCallRiskTier` being fail-closed and (b) the hook's contract doc requiring every implementer to be. This tier-3 control was accepted for one caller only. The named debt required a central clamp + downgrade audit before a second implementer landed.

**Residual (named, not covered).** (1) **No durable authorizing-policy audit yet.** The 2026-08-11 amendment adds a structured log for every allowed or clamped downgrade, but the staging row persists only the _effective_ `riskTier`, not the authorizing `policyRevision`; there is still no durable observation/ledger breadcrumb that names the exact review which waived the floor. Add that breadcrumb when Part 4 wires the write path. (2) **Narrow TOCTOU on the downgraded path.** For a tool downgraded below `high`, approval is waived at the gate against the _current-at-gate_ identity; if the catalog refreshes between gate and execute, the broker resolves the durable identity again and requires its descriptor hash to equal the live client's hash before honoring the policy (mismatch → `unknown` → barrier), but approval was already waived against the pre-drift descriptor. The window is near-zero (downgraded calls are autonomous and execute immediately) and unreachable today (write path unwired), but it becomes real the moment Part 4 ships the write path. The two phases deliberately take separate snapshots because an approved call may resume in another process; what is now shared is the single `resolveMcpToolIdentity` derivation, not mutable in-memory state across the approval boundary.

**Amendment (2026-07-27, architecture review candidate 5).** `resolveMcpToolIdentity` in `mcp/persistence.ts` now owns the durable `(owned connection pointer, current revision hash, descriptor hash, reviewed policy)` identity and resolves it with one joined read that projects only those scalars and the policy row — never the catalog-sized descriptor JSON. Both `resolveMcpCallRiskTier` and the broker consume it. The broker additionally compares that persisted hash to `descriptorHash(liveTool)` before reusing the policy, so live drift remains fail-closed without a second policy-key derivation. First-use client hydration deliberately re-reads the mutable connection row: ownership/policy resolution and endpoint/credential freshness are different claims, and passing the earlier row into the manager could connect to a stale endpoint after a concurrent connection update.

**Alternatives.** (a) **Clamp in the dispatcher** — impossible without defeating the feature (the clamp would be the floor). (b) **Return a richer object** (tier + authorizing policy) so dispatch can audit centrally — deferred as over-engineering for one caller; revisit with residual (1) when the write path lands. (c) **Keep `high` a hard constant** — rejected: it is the ADR-0069 nagging problem this ADR exists to fix.

**Cross-ref.** Amends ADR-0069 (the hard-confirm floor — now a floor a _reviewed_ downgrade can lower, never the autonomy toggle). Builds on the #540 MCP broker/persistence substrate (ADR-0018 lineage) and Parts 1–2 of #541 (result provenance, correlation evidence). The hook contract lives in `LiveToolArgs.resolveRiskTier`; the resolver and its fail-closed branches in `mcp/risk.ts`.

## Amendment — 2026-08-11: central downgrade clamp and Calendar escalation (#232)

`calendar.create_event` is the second `resolveRiskTier` user. Validated input with one or more attendees raises the effective tier from `medium` to `high` because the provider sends invitations with `sendUpdates=all`; input without attendees stays `medium`.

Before this second use, the dispatcher promoted the named trust-boundary debt into code. It now validates the resolver output and compares its explicit severity rank with the static tier. An invalid result fails closed to the static tier. A resolver can raise risk without another declaration. A lower result is clamped to the static tier unless the tool declares a non-empty `riskTierDowngradeReason`. The dispatcher logs invalid output, a clamped downgrade attempt, and an allowed reviewed downgrade without logging tool input. `mcp.call` carries the one reviewed downgrade reason; Calendar carries none, so a faulty Calendar resolver cannot lower its `medium` tier.

The approval requirement on a pending staging row is monotonic. A resume can retain an existing gate after policy becomes less strict, and it can promote an old autonomous row when current validated input resolves to a stricter floor. It can never use a stored `requiresApproval: false` value to override a newly-required approval. Promotion binds the current validated proposal and hash, updates the effective risk snapshot and notification/expiry fields, and only then lets the status machine see the row. This closes the rolling-deploy/crash-resume case where an invite row was inserted as `medium` before #232 and resumed as `high` after it.

The live-chat scheduling hint has no validated input or execution context. It therefore keeps every dynamic-risk tool in the serial approval lane. The real dispatch still resolves the input and can execute a lower-tier call under autonomy. This conservative hint prevents a dynamic `high` result from producing concurrent sibling approval cards.
