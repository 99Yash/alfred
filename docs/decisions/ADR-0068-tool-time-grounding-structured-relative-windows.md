# ADR-0068 — Tool time-grounding: structured relative windows resolved server-side in the user's timezone + reject invented/colliding search qualifiers, never trust the LLM to free-hand an external query DSL (resolves #213)

**Decision.** The boss must never be relied on to (a) recall an external query language's exact syntax from its weights, or (b) do timezone-correct "today" math by hand. Two structural rails enforce this. **(1) The user's IANA timezone is a first-class field on `ToolExecuteContext`** — the dispatcher resolves it once (from the canonical `"timezone"` pref, falling back to the existing visible `"briefing.timezone"` setting and then UTC; reusing chat's per-run snapshot when present) and hands it to _every_ tool, so any tool that turns a relative window into concrete bounds anchors "today"/"past week" on the user's **calendar day**, not the server's UTC day. **(2) Time-relative filters are structured fields resolved server-side, and the free-form escape hatch is validated, not trusted.** For `github.search_pull_requests`: `closedWithinDays`/`createdWithinDays`/new `mergedWithinDays` (`N=1` = today in the user's zone, `N=7` = the last 7 calendar days) compile to `merged:>=<tz-local date>` in the handler; the free-form `query` is whitelist-checked at schema time — an **invented qualifier** (`merged-by:`, `closed-by:`), one that **collides with a structured field** (`is:`/`author:`, or a date qualifier whose `*WithinDays` field is also set), or a contradiction such as `is:unmerged` with merged filters is rejected as `invalid_input`, so the boss gets an actionable signal and retries instead of shipping a confident wrong answer.

**Why.** Prod evidence, two failure modes, same root cause. **(i)** "How many PRs did I merge today" → the boss free-typed `merged-by:@me` (chat `b32f67f8`, 2026-06-23/24). GitHub has no `merged-by:` qualifier; it does **not** error on an unknown qualifier — it silently demotes it to a free-text term, matches nothing, and returns `total_count: 0`. The tool call therefore "succeeds" with count 0, so the boss answered "0 PRs" **twice** (verified false via `gh`: PR #255 merged that day, plus #252/#253 the day before) until the user pushed back and it stumbled onto valid `author:@me`. **(ii)** #213: the same question asked twice gave 19 vs 23 because the boss free-typed `closed:>` one turn and `closed:>=` the next, plus duplicated `is:pr`/`author:` clauses that `buildPullRequestSearchQuery` blindly concatenated. The boss already _had_ correct date grounding in its system prompt (`formatDateGrounding` injects "Wednesday, 24 June 2026 (2026-06-24), timezone Asia/Kolkata") — so the bug was never "it doesn't know today"; it was that **the tool surface forced improvisation** (no structured `merged` window existed) and **silently accepted the improvisation** (no qualifier validation, UTC-sliced date math). Calendar already proved the right pattern: a relative `window` enum resolved against `resolveUserTimezone`. This ADR generalizes that pattern (timezone on ctx) and closes the two holes GitHub left open.

**The shape.** `ToolExecuteContext.timezone: string` (required), filled in `dispatchToolCall` from `DispatchArgs.timezone ?? resolveUserTimezone(userId)`; calendar drops its two ad-hoc `resolveUserTimezone` reads and consumes `ctx.timezone`. `buildPullRequestSearchQuery(input, timezone, nowMs)` resolves every `*WithinDays` window via `addLocalDays(localDateInTimezone(tz, now), -(N-1))`, converts that local date's midnight to an RFC3339 UTC-offset lower bound (`merged:>=2026-06-06T18:30:00+00:00` for 2026-06-07 in Asia/Kolkata), and dedupes its emitted tokens defensively. The qualifier validator lives in web-safe `@alfred/contracts/github-search.ts` (`GITHUB_PR_SEARCH_QUALIFIERS` whitelist + `pullRequestQueryIssues()`), wired as a `superRefine` on `searchPullRequestsInput`; tool/field descriptions steer the boss to the structured fields and explicitly warn that GitHub ignores invented qualifiers. Gmail's `q` stays free-form (its operator set is a legitimate rich DSL) but its description now steers to Gmail's own server-resolved relative operators (`newer_than:`/`older_than:`), which are timezone-proof. Guarded by deterministic unit tests (`buildPullRequestSearchQuery` tz-boundary + dedupe cases, `pullRequestQueryIssues` accept/reject cases) and a behavioral eval (`github-grounding.eval.ts`: asserts the boss uses a structured window and emits no invented/colliding qualifier).

**Alternatives.** (a) **Teach the boss GitHub's qualifier set in the prompt** — rejected: a longer list to misremember, fragile prompt-patching (violates the principles-over-exemplars posture); the correctness belongs in the tool, not the prompt. (b) **Strip/sanitize unknown qualifiers silently** (#213's lighter suggestion) — rejected: silent rewriting hides the model's mistake and still ships a possibly-wrong query; a hard `invalid_input` gives the boss a signal it can act on. (c) **Resolve timezone inside each tool** (status quo, calendar's pattern) — kept as the fallback but lifted to `ctx` so it's resolved once and uniformly available, which is the reusable "know where the user is" primitive other time-relative tools inherit for free. (d) **Add explicit `mergedFrom`/`mergedTo` RFC3339 bounds like calendar** — deferred: `mergedWithinDays` + grounding covers the common "today/past week" questions, and a specific past range (e.g. "merged in October") is a legitimate free-form `merged:A..B` the validator allows. (e) **Block all date qualifiers in `query`** — rejected: it would break legitimate explicit ranges the structured windows can't express; only collisions with a set structured field are rejected.
