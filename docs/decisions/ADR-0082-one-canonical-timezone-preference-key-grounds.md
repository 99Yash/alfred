# ADR-0082 — One canonical `timezone` preference key grounds both chat and briefing; captured at onboarding (BUILT — #229)

**Decision.** Timezone lived under **two** preference keys: `timezone` (read by `resolveUserTimezone` for chat/boss date grounding + calendar windows) and `briefing.timezone` (read by `resolveBriefingPreferences` + written by the settings picker). The settings picker wrote only `briefing.timezone`, so `timezone` stayed unset and chat silently grounded in **UTC**; symmetrically a `timezone`-only user got UTC **briefing delivery** (morning brief at 13:25 IST, 2026-06-21). Make **`timezone` the one canonical key**: the settings picker now writes it (reading `briefing.timezone` as a display fallback), and **both** resolvers read canonical-first (`timezone` → `briefing.timezone` → UTC) — identical precedence, so delivery time and date reasoning can never diverge. `briefing.delivery_hour`/`evening_hour` stay briefing-scoped. The browser's `Intl.DateTimeFormat().resolvedOptions().timeZone` is captured at onboarding-complete and persisted to `timezone` **only if unset**, so a user who never opens settings no longer defaults to UTC.

**Why.** There is one human ("my timezone") behind both surfaces; two keys was an accident of the briefing feature shipping first. Unifying on `timezone` (the broader-scoped key) rather than `briefing.timezone` matches its role as the grounding zone for all date reasoning. **Canonical-first in both resolvers** with `briefing.timezone` retained as a read fallback makes the change **back-compatible with zero migration** — existing `briefing.timezone`-only rows keep working; new writes converge on the canonical key. Capturing at onboarding (server-persisted from a browser-sent value, guarded to not clobber an explicit choice) closes the "never set it → UTC" hole at the root, beating a silent UTC default.

**Alternatives.** (a) **Co-write both keys from settings forever** — rejected: leaves two sources of truth permanently; canonical-first reads + a one-key writer is cleaner and equally safe. (b) **Make `briefing.timezone` canonical** — rejected: narrower scope; `timezone` already grounds chat/calendar. (c) **Infer tz server-side from the primary Google Calendar** — viable as a future enrichment, but the browser zone is simpler, available at onboarding without an API call, and already the value the settings picker offers; calendar-derived tz can layer in later. (d) **Block briefing scheduling until a real tz is known** — rejected: harsher than necessary now that onboarding captures it; the UTC default remains only for the vanishing case of a user with neither key.

**Cross-ref.** Shares the canonical-first precedence with `firstValidTimezone` (`user-timezone.ts`, regression-tested). The captured zone grounds ADR-0053 (run grounding / date reasoning) and every tz-derived briefing window (ADR-0048). Part of the #218 user-model hygiene line.
