# ADR-0062 — Integration object-state memory: a deterministic, registry-driven external-object projection on the Postgres substrate (extends ADR-0058/0057/0053/0052; resolves #212)

**Decision.** Introduce a first-class, cross-integration **object-state memory**: a deterministic projection of the lifecycle state of external _work objects_ — GitHub PRs / issues / check-suites today; ClickUp tasks and remote Claude Code runs later — built on the Postgres substrate (ADR-0058), fed in **real time by a webhook-triggered reducer**, and read by briefing loop-reconciliation (now) and by the boss as a dispatch-gated tool (now/next). It is the **deterministic sibling of the semantic user-memory** (ADR-0057): the same _temporal + graph_ machinery, with the _fuzzy/vector/LLM_ half deliberately omitted from its closure path. This is the "awareness layer" #212's prod recon proved the data forces, and the shared state layer ADR-0052 implicitly assumed but never built.

**The load-bearing invariant — propose / dispose.** Extraction (the LLM/boss front-door, ADR-0063) may _propose_ a candidate key (a `head_sha`, its abbreviated prefix, a pull-request URL, or the canonical URL derived from repository + PR number — each carrying its `exact`/`prefix` match mode) and work-signals. It may **never assert object state.** "Is PR #172 merged" is answered only by the deterministic reducer over `webhook_events`. A hallucinated key resolves to nothing — it cannot _fake_ a merge. So an LLM-extracted key is safe, because resolution and state are deterministic. This is what keeps ADR-0048-D's contract test (`closure ⇐ positive terminal signal`, absence never closes) intact while still letting the boss own the rich extraction.

**Framing — why a new primitive, not one of the obvious reuses.**

- **Not more node-types in `entities`/`user_facts`.** Those are LLM-_proposed_, confidence-gated, low-churn, vector-recalled, and _about the user_ (ADR-0056/0057 — `proposeFact`/`supersedeFact`, HIL-reversible). Object-state is reducer-_computed_, exact-keyed, high-churn (one PR fires opened→synchronize×N→closed), deterministic, and _about external work_. Routing that churn through `proposeFact` is a category error: wrong trust model, wrong cadence, and it would pollute the significance signals ADR-0057 derives.
- **Not ADR-0052's todos.** ADR-0052 _produces and reconciles persisted `todos`_ from the GitHub API. It claimed the ephemeral briefing-loop reconciliation "inherits these signals **for free**" — prod proves it does **not** ("merged PR shows failing for days"), because there is no shared state layer to inherit _from_. ADR-0062 **is** that layer. ADR-0052's eventual native producer and #212's briefing reconciliation both become _consumers_ of it.
- **Not a gather-time recompute over `webhook_events`.** The loop spans the PR's whole event history — the opener email and the merge webhook are both days old — and `gather` reads only a **24h window, cap 25** (`gather.ts:gatherIntegrationActivity`). A recompute structurally cannot see the merge. A **materialized, indexed projection** is required, not optional, at dozen-user scale with months of webhook history.
- **For _this_ primitive, "all the Zep/Neo4j goodies" is wrong — one of them is a bug.** Bitemporal + invalidation (state changed at T), graph traversal (object↔person↔project), and exact key-resolution: **yes, core.** Semantic/vector recall: **no — actively harmful**, because closure must be deterministic; if "is #172 merged" ever resolved through a nearest-neighbor we'd have built a flaky briefing. Community detection: irrelevant. Object-state takes the _structural/temporal/graph_ subset, deliberately not the _fuzzy-semantic_ half.

**Architectural shape.**

- **Registry — the typed SSOT (`@alfred/contracts`, pure).** A per-provider `IntegrationObjectDef`: `kinds`, `keyKinds`, `keyResolvesTo` (`head_sha` and `pull_request_url` → `pull_request`, never → `issue`), `normalize(kind, nativeState) → StateCategory`, and `readableBy` surfaces. Declared `as const satisfies IntegrationObjectDef<Shape>` → literal types **and** a uniform iterable map; adding a provider is a compile-forced complete definition. This is precisely the constraint set Postgres cannot enforce (an enum-per-provider, a key-kind-per-provider), enforced at the type + API layer instead — the generalization of ADR-0053 from "which tools exist" to "which object kinds/keys/states each provider has."
- **Normalized `state_category` = `active | resolved | failed | abandoned`.** Provider-agnostic consumers (briefing reconciliation) read this; the **native** state (`open`/`merged`/`closed`/`success`/`failure`/…) is retained on the row for display + audit. The mapping is per-`(provider, kind)` data in the registry — deliberately lossy-but-honest: consumers that must stay generic read the bucket, consumers that need fidelity read native.
- **Storage (Postgres; ADR-0058 "graph as a _model_, not an _engine_").**
  - **`integration_objects`** — identity `(user_id, provider, kind, external_id)`; `state_category`, `native_state`, `title`, `url`, `attributes` jsonb; **own** bitemporal `valid_from` / `valid_until` / `supersedes_id` columns (the same machinery as `user_facts`, giving point-in-time + supersession for free — but **not** routed through `proposeFact`, which is LLM/confidence-gated and wrong for deterministic state). Indexed on `(user_id, provider, kind)` and `(user_id, state_category)`.
  - **`integration_object_keys`** — sidecar `(user_id, provider, key_kind, key_value) → object_id`. `head_sha`→PR, `pull_request_url`→PR, `run_id`→PR, and `task_id`→task all resolve uniformly. Actions mail uses `head_sha`; review, comment, and merge mail uses the canonical PR URL derived from `owner/repo#number`. Raw branch names are deliberately not a key because they are repo-scoped.
  - **`integration_object_relations`** — object↔entity edges (`authored_by`, `in_project`, `closes`), mirroring `entity_relations`' shape (denormalized `user_id`, from/to, `relation`, `metadata`). **Schema note:** `entity_relations` is entity↔entity (both FKs → `entities.id`), so objects are **not** represented as `entities` rows — that would pollute the canonical-name-indexed people/org table with high-churn objects. A dedicated edge table keeps graph traversal uniform (same recursive-CTE style) _without_ the overload. This is how the goodies — traversal, cross-source dedup — arrive without contaminating semantic memory.
- **Reducer — per-provider, real-time (`@alfred/api`).** `applyEvent(provider, event)`: pure, idempotent, replayable from `webhook_events` (+ `documents`). Runs **on webhook delivery** off the existing `github-webhook.ts` handler (real-time projection, no poll, no gather-recompute) **and** as a one-off **backfill** over existing `webhook_events`. The reducer is the **irreducibly per-provider** part — there is no generic reducer; "cross-integration" means generic _schema + interface_, per-provider _reducers_. GitHub first: `opened`/`synchronize` → upsert `head_sha`→PR key + `active`; `closed && merged` → `resolved`; `closed && !merged` → `abandoned`; `check_suite` failure → `failed`. Idempotency from the existing `(provider, provider_event_id)` dedup plus monotonic transitions guarded by `delivered_at`.
- **Interface — the ADR-0058 swappable abstraction.** `ObjectStateStore`: `applyEvent`, `resolveByKey(provider, keyKind, value)`, `getState(ref, at?)` (point-in-time via the bitemporal columns), `related(refOrEntity, relation?)`, `list(provider, filter)`. If the store is ever swapped, callers don't change.
- **Consumers (v1).**
  - **Briefing reconciliation (#212, #1081).** For each GitHub email loop: `extractKeys(document)` deterministically proposes a literal `head_sha`, its abbreviated prefix, a pull-request URL, or the canonical URL derived from the notification's repository + PR number; then `resolveByKey` (exact candidates) or `resolveByKeyPrefix` (prefix candidates, per the key's match mode) → `getState`. `resolved`/`abandoned` ⇒ drop from the demanding lane **and** surface in the evening "closed today" recap (ADR-0048 #5). State **unknown** ⇒ the loop **stays live** (the contract). Because object-state is webhook-real-time while email is poll-ingested, the merge may already be projected at tag time (⇒ demote at the _source_, the email never enters the demanding lane) or arrive after (⇒ briefing reconciles as the catch-up backstop). Both paths are made safe by "absence never closes."
  - **Boss tool.** `resolveByKey`/`getState`/`list` exposed as **dispatch-gated** boss tools (ADR-0053 — available iff the provider is connected), so "what's the status of my PR" is answerable in chat, not only in background flows.
- **Access control (extends ADR-0053).** The DB does not enforce who-reads-what; therefore the registry's `readableBy` + connection-gated dispatch **is** the access model. No parallel mechanism and no field-level redaction at single/dozen-user scale.

**Scale posture.** Decided for **~a dozen users**, not single-user shortcuts and not hyperscale: a materialized indexed projection + an idempotent replayable reducer (not a gather-time recompute), but no sharding/multi-region/graph-engine. Revisit at multi-tenant scale, consistent with ADR-0058.

**Honors ADR-0048.** `gather` computes `loopStatus` deterministically from object-state; the composer renders only; closure requires a positive `resolved` signal; absence (no webhook, unknown key, API gap) never closes. A contract test pins this and is required before #212 ships.

**Why.** The loop is unsolvable while state lives only in a 24h webhook window or is parsed from email text. A materialized deterministic projection with a key index gives native cross-object identity; determinism is preserved by confining the LLM to _proposing keys_; the design generalizes to ClickUp / remote Claude Code via the registry + a per-provider reducer; and it delivers the temporal/traversal/cross-source goodies of a graph DB on owned Postgres, per ADR-0058 — building the memory _intelligence_ rather than buying the _store_.

**Alternatives.** (a) **More node-types in `entities`** — rejected: pollutes confidence-gated semantic memory with high-churn deterministic state; wrong write-path and trust model. (b) **Gather-time recompute over `webhook_events`** — rejected: the loop spans beyond the 24h read window; doesn't survive dozen-user history. (c) **Treat email text as closure evidence.** Rejected: email may only propose an exact identity key. The webhook reducer remains the sole source of object state, so a spoofed or wrong key resolves to nothing and cannot fake a merge. (d) **Buy a graph DB (Zep/Neo4j)** — rejected per ADR-0058. (e) **Fold object-state into `memory_chunks`** — rejected: breaks determinism and the contract test.

**Parked.** Recurrence-decay (#212 "B" — demote-never-bury on repeat) is a separate ticket. ClickUp / Claude-Code reducers land with those integrations. Boss-tool exposure tuning. The rich extraction front-door is **ADR-0063**.

**Amended 2026-09-20 (#1094).** A gather-time verified pull folds Railway pull
receipts into the same store through the same `applyEvent` guards (unknown
kind/token no-write, per-kind absorbing, `(providerEventTime, deliveredAt)`
recency). This is the second closure source beside the webhook reducer,
admitted because Railway is failure-mail-only with no push source: email can
observe the failure and can never observe the recovery, so no real-time
reducer input exists. It is not the rejected gather-time recompute: it reads
CURRENT provider state over an authenticated grant and folds it through the
reducer, rather than re-scanning a 24h event window. The pull receipt is
synthetic with one minter (`mintRailwayPullReceipt`); email text never asserts
state. Scope limit: the pull appends verified verdict lines and maintains
trigger rows — it does not drop email loops through `reconcileEvidence` (the
Railway adapter proposes no keys until the deployment-URL grammar lands), so
`deployment_target` declares `closesAskOn: []` until then.

**Amended 2026-09-23 (#1192).** The verified pull is now a provider-agnostic
driver in the connections layer (`connections/verified-pull/driver.ts`). The
driver owns the trigger order, the target cap, the dedup by attempt key, the
fold through `applyEvent`, and the re-read of the target row. A
`VerifiedPullProvider` owns target discovery, the authenticated read, the
receipt mint, and the verdict line. Its session is opaque to the driver, so an
MCP read and a REST read plug in the same way. Railway is the first provider,
with no behavior change. Gather runs every provider in the `VERIFIED_PULLS`
registry, which is keyed by `ObjectStateProvider`. A new provider adds one row
there and one implementation file, and does not change gather.

**Open.** Backfill horizon over `webhook_events` (how far back to replay). Whether `check_suite` is its own object kind or an attribute of the PR. Cross-source dedup convergence policy (when a ClickUp task and a PR are "the same loop" — the binding constraint ADR-0052(B) named). v1 loop-opener scope = GitHub Actions CI-failure emails; Railway build-failure added if it recurs.

**Amended 2026-09-06 (#975).** The reducer's input log is `event_receipts` (`provider = 'github'`, `event_type = 'github.<type>'`), not `webhook_events`, which ADR-0097 item 8 retired. The real-time fold is the `github-activity-fold` trigger consumer, and the committed backfill replays `event_receipts`. Idempotency now comes from the receipt's `(provider, provider_delivery_id)` dedup index plus the same monotonic `delivered_at` guard.

**Amended 2026-09-15 (#1081).** GitHub PR objects mint a canonical `pull_request_url` key beside `head_sha`. Trusted GitHub notification mail can propose the same key from a PR URL, `owner/repo#number`, or GitHub's `[owner/repo] ... (PR #number)` subject. This changes matching coverage, not the trust model: only reducer-owned object state can close the loop, and an unmatched or wrong key keeps it live. Existing object URLs are backfilled into the key table during migration.

**Amended 2026-09-15 (#1092).** An Actions failure mail names its commit in the abbreviated form — `... (efd2e98)` — so a key candidate may now be a PREFIX of the stored value, not only the whole value. An extracted key carries its match mode (`exact` or `prefix`), and the store answers a prefix candidate with `resolveByKeyPrefix`. Three floors keep the weaker evidence safe: the abbreviation must be at least 7 hex, it must stand in trailing parentheses at the end of the subject and mix digits with a–f letters (so parenthesized words, build numbers, and dates do not count), and a prefix that matches more than one object resolves to nothing. This again changes matching coverage, not the trust model: the reducer still owns state, so a wrong or ambiguous prefix keeps the loop live.

**Amended 2026-09-15 (#1088).** Reconciliation is **one shared operation**, and closure policy moves from a global rule to a **per-kind declaration**.

- **The seam.** `proposeObjectKeys(subject, reading)` (pure, synchronous) and `reconcileEvidence({ userId, subjects })` (async) in `@alfred/assistant/connections` own everything that is provider-agnostic: resolving a candidate key, the exact-beats-prefix precedence, deduplicating keys across subjects, and reading closure. The two consumers that exist today — the briefing's `dropClosedLoops` and the pre-send open-ask guard — each held a private copy of it and now share one; Context Search enrichment (#1087) becomes the third.
- **The adapter.** `ObjectStateAdapter.proposeKeys` is a provider's irreducible half: which written forms name one of its objects, and what the canonical value of each one is. A second provider is therefore one adapter file plus its registry entry and reducer — not a second copy of the reconciliation. `githubObjectStateAdapter` is the first.
- **Two readings, because a caller's authority differs** (superseded by the 2026-09-17 amendment below, which adds a third reading and moves the annotating role off `mentions`). `about` means the text is a notification about ONE object; the adapter may demand provenance (the `github.com` sender-domain gate) and refuses an ambiguous reference, because the caller **drops** an item on the result. `mentions` means the text merely NAMES objects; no provenance is claimed and every named object is proposed, because the caller only **annotates**. Neither reading asserts state, so both stay inside propose / dispose.
- **Per-kind closure (`ObjectKindDef.closesAskOn`).** `isLoopClosingCategory` is replaced by `closesOpenAsk(provider, kind, category)`. `LOOP_CLOSING_STATE_CATEGORIES` remains the **vocabulary** a kind declares within, not the rule. An undeclared kind closes nothing, so absence still never closes.
- **Per-kind absorption (`ObjectKindDef.absorbing`).** The store's monotonicity guard reads `isAbsorbingState(provider, kind, category)` instead of hard-coding "`resolved` absorbs". `pull_request` declares `absorbing: ["resolved"]`, which reproduces the old guard exactly. This is the hook #1093 needs: work that closes by **succession** rather than by transition — a CI run, a deployment — declares `absorbing: []`, and a later failure after a success then lands as ordinary traffic with no second branch in the store.
- **Relation to ADR-0103 (Proposed).** This slice delivers ADR-0103's resolve half and its "move the absorbing rule into provider-and-kind policy" requirement. It differs on one signature, deliberately: ADR-0103 proposed `reconcileDocuments(userId, documentIds)`, which reads documents back out of the database. The pre-send open-ask guard has no document at all — it reconciles composed prose — and the briefing gather already holds each row's text in the loop that partitions it. So the operation takes a caller-supplied `ReconcileSubject` instead, and the caller proposes keys where it already has the text. ADR-0103's receipt half (`projectReceipt`, state-receipt provenance, one-to-many deltas) is untouched and still open.

**Amended 2026-09-17 (#1087).** A **third** reading, `annotates`, supersedes the "Two readings" bullet above. Context Search enrichment is the third caller of the #1088 seam, and it has less authority than either reading that existed.

- **The three readings, ordered by what the caller DOES with a resolution.** `about` — the caller **drops** an item, so the adapter demands provenance and refuses an ambiguous reference. `mentions` — the caller **suppresses** a composed sentence, so the adapter claims no provenance but proposes only a written form that names a work object directly. `annotates` — the caller **decorates** evidence it already holds, drops nothing, suppresses nothing, and closes no loop, so the adapter may also propose an identifier for a CONSTITUENT of a work object: a commit sha names the pull request that carries it. A wrong proposal under `annotates` costs one absent annotation.
- **`mentions` keeps the suppression role, not the annotation role.** The #1088 bullet gave `mentions` the words "the caller only **annotates**". That description now belongs to `annotates`. `mentions` is unchanged in behavior and still has one caller, the pre-send open-ask guard.
- **Propose / dispose is unchanged.** No reading asserts state. A wrong or hallucinated key resolves to nothing and closes nothing, so the third reading widens matching coverage only.
- **Open.** All three readings return the same type, so an `annotates` result compiles where a closure reader expects an `about` result. The second annotating source (#1090) must narrow that.
