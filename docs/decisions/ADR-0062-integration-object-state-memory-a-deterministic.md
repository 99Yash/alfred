# ADR-0062 — Integration object-state memory: a deterministic, registry-driven external-object projection on the Postgres substrate (extends ADR-0058/0057/0053/0052; resolves #212)


**Decision.** Introduce a first-class, cross-integration **object-state memory**: a deterministic projection of the lifecycle state of external *work objects* — GitHub PRs / issues / check-suites today; ClickUp tasks and remote Claude Code runs later — built on the Postgres substrate (ADR-0058), fed in **real time by a webhook-triggered reducer**, and read by briefing loop-reconciliation (now) and by the boss as a dispatch-gated tool (now/next). It is the **deterministic sibling of the semantic user-memory** (ADR-0057): the same *temporal + graph* machinery, with the *fuzzy/vector/LLM* half deliberately omitted from its closure path. This is the "awareness layer" #212's prod recon proved the data forces, and the shared state layer ADR-0052 implicitly assumed but never built.

**The load-bearing invariant — propose / dispose.** Extraction (the LLM/boss front-door, ADR-0063) may *propose* a candidate key (a 40-hex `head_sha`, a PR number) and work-signals. It may **never assert object state.** "Is PR #172 merged" is answered only by the deterministic reducer over `webhook_events`. A hallucinated key resolves to nothing — it cannot *fake* a merge. So an LLM-extracted key is safe, because resolution and state are deterministic. This is what keeps ADR-0048-D's contract test (`closure ⇐ positive terminal signal`, absence never closes) intact while still letting the boss own the rich extraction.

**Framing — why a new primitive, not one of the obvious reuses.**

- **Not more node-types in `entities`/`user_facts`.** Those are LLM-*proposed*, confidence-gated, low-churn, vector-recalled, and *about the user* (ADR-0056/0057 — `proposeFact`/`supersedeFact`, HIL-reversible). Object-state is reducer-*computed*, exact-keyed, high-churn (one PR fires opened→synchronize×N→closed), deterministic, and *about external work*. Routing that churn through `proposeFact` is a category error: wrong trust model, wrong cadence, and it would pollute the significance signals ADR-0057 derives.
- **Not ADR-0052's todos.** ADR-0052 *produces and reconciles persisted `todos`* from the GitHub API. It claimed the ephemeral briefing-loop reconciliation "inherits these signals **for free**" — prod proves it does **not** ("merged PR shows failing for days"), because there is no shared state layer to inherit *from*. ADR-0062 **is** that layer. ADR-0052's eventual native producer and #212's briefing reconciliation both become *consumers* of it.
- **Not a gather-time recompute over `webhook_events`.** The loop spans the PR's whole event history — the opener email and the merge webhook are both days old — and `gather` reads only a **24h window, cap 25** (`gather.ts:gatherIntegrationActivity`). A recompute structurally cannot see the merge. A **materialized, indexed projection** is required, not optional, at dozen-user scale with months of webhook history.
- **For *this* primitive, "all the Zep/Neo4j goodies" is wrong — one of them is a bug.** Bitemporal + invalidation (state changed at T), graph traversal (object↔person↔project), and exact key-resolution: **yes, core.** Semantic/vector recall: **no — actively harmful**, because closure must be deterministic; if "is #172 merged" ever resolved through a nearest-neighbor we'd have built a flaky briefing. Community detection: irrelevant. Object-state takes the *structural/temporal/graph* subset, deliberately not the *fuzzy-semantic* half.

**Architectural shape.**

- **Registry — the typed SSOT (`@alfred/contracts`, pure).** A per-provider `IntegrationObjectDef`: `kinds`, `keyKinds`, `keyResolvesTo` (`head_sha`→`pull_request`, never →`issue`), `normalize(kind, nativeState) → StateCategory`, and `readableBy` surfaces. Declared `as const satisfies IntegrationObjectDef<Shape>` → literal types **and** a uniform iterable map; adding a provider is a compile-forced complete definition. This is precisely the constraint set Postgres cannot enforce (an enum-per-provider, a key-kind-per-provider), enforced at the type + API layer instead — the generalization of ADR-0053 from "which tools exist" to "which object kinds/keys/states each provider has."
- **Normalized `state_category` = `active | resolved | failed | abandoned`.** Provider-agnostic consumers (briefing reconciliation) read this; the **native** state (`open`/`merged`/`closed`/`success`/`failure`/…) is retained on the row for display + audit. The mapping is per-`(provider, kind)` data in the registry — deliberately lossy-but-honest: consumers that must stay generic read the bucket, consumers that need fidelity read native.
- **Storage (Postgres; ADR-0058 "graph as a *model*, not an *engine*").**
  - **`integration_objects`** — identity `(user_id, provider, kind, external_id)`; `state_category`, `native_state`, `title`, `url`, `attributes` jsonb; **own** bitemporal `valid_from` / `valid_until` / `supersedes_id` columns (the same machinery as `user_facts`, giving point-in-time + supersession for free — but **not** routed through `proposeFact`, which is LLM/confidence-gated and wrong for deterministic state). Indexed on `(user_id, provider, kind)` and `(user_id, state_category)`.
  - **`integration_object_keys`** — sidecar `(user_id, provider, key_kind, key_value) → object_id`. `head_sha`→PR, `run_id`→PR, `task_id`→task all resolve uniformly. The `head_sha`→PR index is the exact thing the prod recon proved necessary (the CI email carries a head-sha and *no* PR number). Raw branch names are deliberately not a v1 key because they are repo-scoped.
  - **`integration_object_relations`** — object↔entity edges (`authored_by`, `in_project`, `closes`), mirroring `entity_relations`' shape (denormalized `user_id`, from/to, `relation`, `metadata`). **Schema note:** `entity_relations` is entity↔entity (both FKs → `entities.id`), so objects are **not** represented as `entities` rows — that would pollute the canonical-name-indexed people/org table with high-churn objects. A dedicated edge table keeps graph traversal uniform (same recursive-CTE style) *without* the overload. This is how the goodies — traversal, cross-source dedup — arrive without contaminating semantic memory.
- **Reducer — per-provider, real-time (`@alfred/api`).** `applyEvent(provider, event)`: pure, idempotent, replayable from `webhook_events` (+ `documents`). Runs **on webhook delivery** off the existing `github-webhook.ts` handler (real-time projection, no poll, no gather-recompute) **and** as a one-off **backfill** over existing `webhook_events`. The reducer is the **irreducibly per-provider** part — there is no generic reducer; "cross-integration" means generic *schema + interface*, per-provider *reducers*. GitHub first: `opened`/`synchronize` → upsert `head_sha`→PR key + `active`; `closed && merged` → `resolved`; `closed && !merged` → `abandoned`; `check_suite` failure → `failed`. Idempotency from the existing `(provider, provider_event_id)` dedup plus monotonic transitions guarded by `delivered_at`.
- **Interface — the ADR-0058 swappable abstraction.** `ObjectStateStore`: `applyEvent`, `resolveByKey(provider, keyKind, value)`, `getState(ref, at?)` (point-in-time via the bitemporal columns), `related(refOrEntity, relation?)`, `list(provider, filter)`. If the store is ever swapped, callers don't change.
- **Consumers (v1).**
  - **Briefing reconciliation (#212).** For each CI/build-failure email loop: `extractKeys(document)` (v1 = a deterministic GitHub-CI regex pulling the literal `head_sha`; see ADR-0063 for the rich replacement) → `resolveByKey` → `getState`. `resolved`/`abandoned` ⇒ drop from the demanding lane **and** surface in the evening "closed today" recap (ADR-0048 #5). State **unknown** ⇒ the loop **stays live** (the contract). Because object-state is webhook-real-time while email is poll-ingested, the merge may already be projected at tag time (⇒ demote at the *source*, the email never enters the demanding lane) or arrive after (⇒ briefing reconciles as the catch-up backstop). Both paths are made safe by "absence never closes."
  - **Boss tool.** `resolveByKey`/`getState`/`list` exposed as **dispatch-gated** boss tools (ADR-0053 — available iff the provider is connected), so "what's the status of my PR" is answerable in chat, not only in background flows.
- **Access control (extends ADR-0053).** The DB does not enforce who-reads-what; therefore the registry's `readableBy` + connection-gated dispatch **is** the access model. No parallel mechanism and no field-level redaction at single/dozen-user scale.

**Scale posture.** Decided for **~a dozen users**, not single-user shortcuts and not hyperscale: a materialized indexed projection + an idempotent replayable reducer (not a gather-time recompute), but no sharding/multi-region/graph-engine. Revisit at multi-tenant scale, consistent with ADR-0058.

**Honors ADR-0048.** `gather` computes `loopStatus` deterministically from object-state; the composer renders only; closure requires a positive `resolved` signal; absence (no webhook, unknown key, API gap) never closes. A contract test pins this and is required before #212 ships.

**Why.** The loop is unsolvable while state lives only in a 24h webhook window or is parsed from email text. A materialized deterministic projection with a key index gives native cross-object identity; determinism is preserved by confining the LLM to *proposing keys*; the design generalizes to ClickUp / remote Claude Code via the registry + a per-provider reducer; and it delivers the temporal/traversal/cross-source goodies of a graph DB on owned Postgres, per ADR-0058 — building the memory *intelligence* rather than buying the *store*.

**Alternatives.** (a) **More node-types in `entities`** — rejected: pollutes confidence-gated semantic memory with high-churn deterministic state; wrong write-path and trust model. (b) **Gather-time recompute over `webhook_events`** — rejected: the loop spans beyond the 24h read window; doesn't survive dozen-user history. (c) **Email-text PR-URL/number parse** (ADR-0052 alt-a) — rejected for closure: brittle + spoofable; the `head_sha`→webhook→PR chain + DKIM verification is the robust replacement, which is why this ADR can revisit 0052's rejection of email-derived signals *for matching* without reviving it *for closure*. (d) **Buy a graph DB (Zep/Neo4j)** — rejected per ADR-0058. (e) **Fold object-state into `memory_chunks`** — rejected: breaks determinism and the contract test.

**Parked.** Recurrence-decay (#212 "B" — demote-never-bury on repeat) is a separate ticket. ClickUp / Claude-Code reducers land with those integrations. Boss-tool exposure tuning. The rich extraction front-door is **ADR-0063**.

**Open.** Backfill horizon over `webhook_events` (how far back to replay). Whether `check_suite` is its own object kind or an attribute of the PR. Cross-source dedup convergence policy (when a ClickUp task and a PR are "the same loop" — the binding constraint ADR-0052(B) named). v1 loop-opener scope = GitHub Actions CI-failure emails; Railway build-failure added if it recurs.
