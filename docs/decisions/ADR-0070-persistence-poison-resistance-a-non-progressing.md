# ADR-0070 — Persistence poison-resistance + a non-progressing-step backstop: no tool result can wedge a run, and a step that can't commit dies instead of looping (resolves #267)


**Decision.** Two structural rails make the agent executor poison-proof. **(1) Tool results are sanitized at the dispatch boundary** before they touch any persisted store: the moment `tool.execute()` returns in `executeAndCommit` *and* `executeFastPath` (`dispatch/index.ts`), every string in the result is recursively stripped of `U+0000` and lone UTF-16 surrogates, the result is flagged `sanitized:true`, and a server-side `warn` is emitted naming the tool and the count removed. This is a **platform invariant**: no tool, present or future, can return a value that the database refuses to persist. **(2) A non-progressing step fails the run terminally.** When `leaseRun` reclaims a stale-`running` row, it counts the prior **consecutive `"lease reclaimed"` failures for the same `(run_id, current_step)`** since the last *successful* step (derived from `agent_steps`, no schema change); at **3** it transitions the run to terminal `failed` with `error.message = "step <id> not progressing: reclaimed N times"` instead of re-leasing. Failover survives a single genuine worker death (one free reclaim+retry); a step that is itself broken dies fast.

**Why.** Proven root cause, not hypothesis — re-verified against dev run `run_m78xa3ei2w4n` (2026-06-25). The boss called `drive.export_file` with `mimeType:"application/pdf"`; Google returned a valid 43KB PDF in 1.7s (replayed against the dev creds — *not* slow, *not* a hang, *not* event-loop blocked), but `exportFile` decodes via `res.text()`, so the result was a string carrying **129 `U+0000` bytes**. The `status='executed'` UPDATE that writes `execute_result` (jsonb) is *outside* the `try/catch` that wraps `tool.execute` (`dispatch/index.ts:694`), so it threw — verified against the dev DB: jsonb → `22P05 unsupported Unicode escape sequence`, text → `22021 invalid byte sequence for encoding "UTF8": 0x00` — leaving the staging row stuck `pending` (confirmed: `pending`, no `execute_error`). **The root is the poisoned *result*, and rail (1) fixes it there:** a result cleaned the instant `tool.execute` returns persists fine, the turn *succeeds*, and the throw-chain below never begins — #267's loop is structurally impossible. The incident *also* exposed a second, distinct defect on the failure-recording path (visible only because the sanitizer wasn't present, so the result-write threw): the throw propagated to `finalizeFailedMessage` (which *succeeded* — the `failed/attachment` chat-message row exists) and then to `runOnce`'s catch → `commitStepFailure`, whose own `agent_runs.error = { message: <the poison pg error> }` jsonb write **re-threw on the same null byte**, escaped `runOnce`, and left the run `running`. Either fix alone breaks the loop — the boundary sanitizer by keeping the result clean (success, the best outcome), the error-sink strip by making the failure *fast-terminal in ~2s* — but they cover **different poison classes** (the boundary sanitizer: poison arriving as a tool *result*, this incident; the error-sink strip: poison arriving as a *thrown error/text* string), so both ship and neither is singularly "the wedge." The step then sat **86.8s in `running`** until the stale-lease sweep reclaimed it (`error->>'message' = "lease reclaimed…"`), re-ran the same poison, and would have looped forever (manually cancelled at the 2nd reclaim). *Note:* the run's `attempt` had reached `18`, but `attempt` is the monotonic per-step counter (≈ 9 chat-turn + 9 dispatch executions, including ~16 steps of legitimate prior work — a PR search **and** a built Google Sheet); only **one** genuine reclaim had occurred. The infinite-loop mechanism is real, but it was nascent, not "18 reclaims deep." The lease/heartbeat machinery (60s `STALE_RUN_LEASE_MS`, 10s heartbeat) is *correct* failover; the defect was that nothing distinguished "the worker died" from "this step can never commit," so failover kept rescuing an un-rescuable step. A timeout fix or a lease-cap-alone fix would have only converted an infinite loop into a slow opaque failure — they miss that the poison is at the *persist*, not the call.

**The shape.** A `sanitizeToolResult(value)` helper in `@alfred/contracts` (web-safe, the one definition) walks the result and returns `{ value, removed }`; both dispatch execute paths apply it immediately after `tool.execute` returns, so the jsonb write *and* the returned `toolResult`/in-memory transcript (`agent_runs.transcript`/`state` are the same poison sinks) are all clean. Two correctness requirements for the helper to actually hold the platform invariant: it must strip `U+0000` from **object keys, not only values** (a NUL-byte key poisons the same jsonb write), and the `sanitized` flag must ride on the **dispatch envelope / tool-call log, not as a property assigned to the result value** — a bare string/array/primitive result can't carry a flag, and assigning to a string throws under ES-module strict mode. **The same strip is applied at the error-recording sinks** — `commitStepFailure`/`markRunFailed` (`error.message`), `finalizeFailedMessage` (`content` + `toolCalls` previews), and the dispatcher's own `executeError` write (`dispatch/index.ts:673-685`). These close the **throw-poison class** — poison arriving as a *thrown error/text* string (a tool that throws a NUL-byte message) — which the boundary sanitizer structurally cannot reach (it sanitizes *results*, and a throw carries no result). They are not redundant with it: for #267's result-poison, the boundary sanitizer makes the result persist cleanly (the turn succeeds), while the error-sink strip is a redundant second guarantee (even if the boundary were bypassed, the failure is **fast-terminal in ~2s** rather than an endless reclaim). With both, the backstop guards only a genuinely non-progressing step. The backstop is a single query in `leaseRun` (`COUNT` the contiguous tail of same-`(run_id, current_step)` `agent_steps` rows that `leaseRun` marked reclaimed, since the last *successful* step) gated at `>= 3`; **it must match on a structured reclaim marker `leaseRun` sets — e.g. `error->>'reason' = 'lease_reclaimed'` or a dedicated flag column — not `LIKE 'lease reclaimed%'` on the human-readable message, so rewording the prose can never silently disable the safety net.** On trip it calls the existing terminal-fail path so the failed run flows through normal reconciliation (feeds ADR-0072's message↔run consistency). The backstop's own terminal write **must** use the synthetic clean message `"step <id> not progressing: reclaimed N times"` and must **not** echo the original error — otherwise the terminal write re-throws on the same poison and the run survives its own backstop. `attempt` stays the monotonic per-run idempotency counter it became in the chat-latency fix (`docs/plans/chat-latency-and-github-tools.md`) — the backstop keys on *same-step consecutive reclaims*, never on `attempt`, because `attempt` legitimately climbs on every `chat-turn↔dispatch-tools` loop and is not a retry count. Covered by deterministic tests (sanitizer null-byte/surrogate cases; the backstop trip at 3 vs. one-free-reclaim survival). **The backstop tests presuppose a DB/tx lease-test harness that does not exist yet (#137, "stand up a DB/tx test harness") — building it is a Phase-1 prerequisite, not a given.** Implementation note: the "consecutive reclaims since the last *successful* step" anchor must key on `commitStepSuccess`'s actual terminal-success status value — because monotonic `attempt` means a given `step_id` recurs across loop iterations, the count must reset on real forward progress, not on the same `step_id` reappearing.

**Alternatives.** (a) **A wall-clock timeout at the dispatch layer** — rejected: the call isn't slow (1.7s, proven); a `setTimeout` is also defeated by the same event-loop-block class the heartbeat is, so it's both unnecessary here and unreliable in general. (b) **Cap on `attempt`** — rejected: `attempt` is monotonic per the chat-latency ADR; a cap would kill legitimate long multi-turn runs. (c) **A blanket sanitizer at every DB write site** — rejected as the *primary*: scattered, easy to miss the next sink, and it strips blindly without the "this came from tool X" provenance; the dispatch boundary is the single semantically-correct origin (binary-as-text is already garbage — stripping control chars loses nothing real). **But the error-recording sinks are still required, not optional belt-and-suspenders** — they close the *throw-poison* class (a tool that throws, rather than returns, a NUL-byte string), which the result-boundary sanitizer structurally cannot reach; and in #267 the error re-throw is what turned a would-be fast-terminal failure into a loop. So `commitStepFailure`/`markRunFailed`/`finalizeFailedMessage`/`executeError` get the strip as a required companion to the dispatch-boundary sanitizer, not a nice-to-have. (d) **Reject any tool result containing null bytes** (fail the turn) — rejected: a stray control char shouldn't nuke a whole turn; strip + flag + warn is observable without being destructive, and genuine binary misuse is caught upstream by ADR-0071's honest read-tool.

**Cross-ref.** Composes with ADR-0016/0026/0035 (the step executor / lease / sub-agent model) and the chat-latency monotonic-`attempt` fix. The sanitizer is the platform-level companion to ADR-0071's tool-level "don't ingest binary as text." The terminal-fail path is the precondition that makes ADR-0072's message↔run reconciliation and ADR-0073's child-completion signal reliable (a wedged child now actually terminates). **Sits in the Reliability lease cluster (#135/#136/#137/#151):** **#135** (no alert path on terminal job failure; metering/heartbeat errors swallowed) is the sharpest coupling — the backstop *and* ADR-0072's terminal finalization **manufacture** terminal failures, and outside chat (sub-agents, briefings) a backstop-killed run dies **silently** until #135's alert path exists (ADR-0072 covers only the chat-visible case). The backstop is the "give up on a non-progressing step" half of step-retry policy, and **#136's transient-retry (re-enqueue 429/5xx with backoff) is the complementary "retry the recoverable" half** — they must be designed to coexist (the backstop keys on consecutive *worker-death reclaims* of a step; #136 on *error classification*; note BullMQ already retries the job at `attempts:3`, a third, distinct layer). #137 (zero lease/idempotency tests) is the missing harness this ADR's tests depend on; #151 (write idempotency) is eased because terminal-fail curbs the retry-storm that duplicates resources.
