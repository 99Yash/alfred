# ADR-0048 — Briefing v3: open-loop unit, discretionary morning + always-on evening, compose-time read-only reconciliation

**Decision.** The briefing is reframed at the product level. It is no longer "a cross-source digest composed and emailed every morning" (ADR-0041's empty-state-never-skips, single-surface model — itself the source of the "redundant, ugly, long" complaint that triggered this rethink). It becomes a set of **renders of an open-loop model**, split into two surfaces with **deliberately different firing models**. This **amends ADR-0041**: the gather/compose/reference/`briefings`-entity machinery is retained; the firing model, surface semantics, and framing are replaced. The current `morning-briefing` workflow (m10 deterministic inbox digest) is **replaced, not patched**.

Seven coordinated micro-decisions:

1. **The unit is the open loop.** Alfred tracks _open loops_ — anything across integrations that needs the user or shapes their day. Briefings are **renders** of that model, not summarizers of inputs. The inbox is the "now" render; morning and evening briefings are two more. This is the framing that makes the rest cohere — "what to surface" is "which loops are live for this moment", not "summarize today's email".

2. **Triage labels are immutable; reconciliation is read-only and compose-time.** A thread tagged `action_needed` stays tagged — it was correct when written. The briefing cross-checks candidate loops against current integration state at compose time (a PR that merged silently → loop closed → don't surface) but **never rewrites the triage record**. Rewriting triage on integration state changes is a cross-source state-machine — a separate, deliberately-avoided "can of worms" (see Parked). Thread-cache invalidation on _new Gmail activity_ is the existing, separate mechanism.

3. **Form: a <6-sentence paragraph.** Not a list, not a digest. Still-live/urgent items collapse to **one summary sentence**, omitted entirely when nothing is live (no "you have no urgent items" padding). Email stays short, ends in a `View full briefing` link. (This is tighter and more prescriptive than ADR-0041's 4–6-line `breakingSummary`, and the same content drives both surfaces.)

4. **Morning = orientation, discretionary.** Forward-facing ("what does my day look like"), **today + tomorrow** window, calendar-anchored. Folds in **recall** that is _anchored to a concrete calendar item_ (no event → no recall — open-ended "surface relevant old context" is rejected as a noise source). Firing is **discretionary**: a routine day → **silent, no email**. But the gate **errs toward sending** on ambiguity because the costs are asymmetric — an unnecessary short email costs ten seconds; a wrongly-suppressed briefing costs the dropped ball. Mechanically this is **compose-then-gate**: draft, then decide if it clears the bar; a suppressed morning still leaves a quiet in-app record so suppression never reads as a bug.

5. **Evening = close, always fires.** Distinct job: close the day. Content = synthesis of what came in (**loops closed / still open — closure, not a transcript** of what the user already watched happen) + any meeting still left this evening + optional **tomorrow-prep** (surfaced at night while there's time to act) + a **human leaving note**. It **always fires** because closure is intrinsically valid, and content **degrades gracefully** to **weather + a personal sign-off** ("34°C in Delhi, clear sky. See you tomorrow, Yash") on an otherwise-empty day — the daily-varying weather is what keeps the note from becoming wallpaper. A **week-level** note ("brutal week — log off") rides along occasionally, keyed to real intensity, never nightly.

6. **Day-aware framing, localized.** Both surfaces read the _kind of day_ (weekday / weekend / the user's holidays) before choosing words; holidays are localized via the onboarding profile (Thanksgiving ≠ India). ADR-0041 had day-of-week/holidays as a _gather source_; here it is also a **voice/framing** concern — a Sunday surfaces a live item rephrased for downtime, not narrated like a workday.

7. **Channel: email push + in-app durable record.** Email carries the paragraph + `View full briefing` link; the in-app surface is the canonical, scrollable record and the silent-day escape hatch. (Reaffirms ADR-0041's split surface and ADR-0020's email-only-at-v1; overrides ADR-0041's "empty state never skips, single daily send" with the morning/evening firing models above.)

**Schema consequence.** Two sends per day (morning + evening, distinct jobs) means the per-day identity from ADR-0041 (`UNIQUE(user_id, briefing_date)`) must gain a **slot** dimension — `(user_id, briefing_date, slot)` with `slot ∈ {morning, evening}`. The existing slot-based `briefing_runs` table (from the in-flight `daily-briefing` workflow) and ADR-0041's `briefings` table consolidate into one slotted entity — **resolved in the 2026-06-02 amendment below** (keep `briefings` canonical, add `slot`, retire `briefing_runs`).

**Why.** The original briefing was rejected as "redundant (I've already seen my priority email), ugly, and long" — a daily memo that re-narrated the inbox regardless of whether anything warranted it. The fix is not a nicer template; it is a different posture: **think like a personal assistant**, who speaks when it matters in the morning and closes the day with you in the evening. The open-loop framing is what lets "speak when it matters" be principled rather than ad hoc, and the read-only reconciliation is what makes "it matters" honest (a merged PR is not a live loop) without opening the much larger live-state-machine build.

**Alternatives.**

- (a) **Keep ADR-0041's unconditional daily single briefing.** Rejected — it _is_ the complaint. A memo every morning regardless of content is the noise the rethink exists to remove.
- (b) **Rewrite triage tags when integration state changes** (true reconciliation). Rejected for this iteration — a cross-source state machine fed by webhooks is a real build and a "can of worms"; the label was correct at write time, and compose-time read-only filtering captures the user-visible value now.
- (c) **Recap-as-transcript / open-ended recall.** Rejected — telling the user what they already watched happen, or surfacing unanchored old context, reproduces the exact "I already know this" redundancy. Recap is closure-only; recall must anchor to a concrete calendar item.
- (d) **Warm sign-off every night as a standalone reason to send.** Rejected — a heartfelt note nightly becomes wallpaper within a week. Solved by making the _evening close_ the job and degrading content to daily-varying weather rather than firing a content-free greeting.
- (e) **Always-send evening + always-send morning (symmetric).** Rejected — symmetric firing reintroduces over-pinging; morning's orientation job has nothing to say on a quiet day, evening's close job always does. The asymmetry is intentional.
- (f) **Build the advance-reminder / anomaly workflow now.** Deferred — see Parked.

**Parked (explicit non-goals this iteration).**

- **Advance reminders** — commitments with a future date-of-impact, surfaced N days out, off the morning/evening cadence. A separate workflow and discussion.
- **Anomaly detection** — "a meeting you agreed to that isn't on the calendar yet." Highest magic, highest annoyance risk (a wrong nag burns trust fast); deliberately deferred. Shares the noise failure mode that anchored-recall (decision #4) was designed to avoid.
- **Continuous open-loops state machine** — webhook-driven reconciliation so the inbox is correct _between_ briefings, not just at compose time. The right end-state; today is compose-time, read-only only. **(GitHub slice un-parked for persisted `todos` — see ADR-0052. Polling, not yet webhooks; the briefing's ephemeral-loop reconciliation here is unchanged but inherits ADR-0052's signals.)**

**Open.**

- The **"worth sending" gate** for the discretionary morning — threshold definition and whether it's an LLM judgment or a heuristic over loop signals. Trust-critical: a wrong suppression is the expensive error. (Where the gate _lives_ and what it _records_ is resolved in the amendment below; the threshold _logic_ stays open.)
- **Recall anchoring precision** — quality here is where the feature lives or dies in practice.
- **Week-intensity signal** source for the evening week-level note (activity volume, run cost, hours-in-app, …).

**Amendment (2026-06-02) — entity, scheduling, suppression, and source-availability locked.**

The four implementation questions left open above are decided. The product model is unchanged; these are the structural commitments that let the rebuild start.

**A. Entity: `briefings` stays canonical, gains `slot`, `briefing_runs` is retired.** The `briefings` table (ADR-0041, Replicache-synced, typed `gather`/`full_briefing`) is the single canonical entity — matches the cutover note already in `packages/db/src/schema/briefings.ts`. It gains a `slot text NOT NULL` (`'morning' | 'evening'`); the unique index changes `UNIQUE(user_id, briefing_date)` → `UNIQUE(user_id, briefing_date, slot)`; the Replicache key changes `briefing/{briefingDate}` → `briefing/{briefingDate}/{slot}` and the read schema adds `slot`. `briefing_runs`'s two live roles migrate: the **watermark** (`watermark_at`, the `documents.ingested_at` cut-off per `(user, slot)`) moves onto `briefings` as a column, queried over **terminal _consumed_ states only — `status ∈ {sent, suppressed}`** — and the partial watermark index moves from the legacy `WHERE status = 'composed'` to `WHERE status IN ('sent', 'suppressed')`. `composed` is deliberately **excluded**: in this model it is an _intermediate_ state (`composing → composed →` gate `→ sent | suppressed`, decision C), so a run that crashes after compose but before terminalizing must **not** advance the cutoff — that window's loops were never delivered, and consuming them would silently drop a briefing the user never received (the asymmetric "silence is the expensive error" rule applies to the watermark too). `failed` (a composed briefing whose send failed, ADR-0041) is excluded for the same reason — the next run re-reads that window so nothing is lost; a stuck-`composed` or `failed` row is reprocessed, never consumed. The **prior-body-as-prompt-context** role is already served by `briefings.breaking_summary` / `full_briefing` (the agent reads prior `briefings` rows), with a `body_markdown` column added only if the mailer render needs the markdown source. Run-level audit (tokens, `agent_run_id`, error) belongs to `agent_runs` — ADR-0041 alternative (f) already rejected render-history — so `briefings` keeps only a soft `agent_run_id` for traceability. `briefing_runs` is marked **legacy-only immediately** and dropped in a follow-up migration once the daily-briefing workflow stops writing it.

**B. Scheduling: `briefing.tick` fans out both slots with slot-scoped idempotency.** Preferences already carry both hours (`briefing.delivery_hour` = morning, `briefing.evening_hour` = evening; `resolveBriefingPreferences` returns both). The tick's per-user check (`packages/api/src/modules/briefing/queue.ts`) widens from `localHour === deliveryHour` to evaluating **both** hours and enqueuing a run **per matching slot**. `enqueueBriefingRun` takes `slot: 'morning' | 'evening'`; the workflow `input` carries `{ slot, briefingDate, reason }`. The idempotency key becomes **slot-scoped** — `briefing:{userId}:{briefingDate}:{slot}` — replacing the morning-`briefing:` / evening-`recap:` split; the `email_sends (user_id, idempotency_key)` unique index still backs no-double-send, now per slot. If a user misconfigures `delivery_hour === evening_hour`, both fire the same hour — harmless (distinct slot keys), worth a log warning.

**C. Suppressed morning is a persisted terminal state, not a synthesized UI empty-state.** `BriefingStatus` gains `suppressed`: `pending | gathering | composing | composed | sent | suppressed | failed`. Two columns are added: `send_decision text` (`'sent' | 'suppressed'`) and `gate_reason text` (why the gate decided as it did). Flow for morning: `composing → composed →` gate `→ sent` (`email_send_id` set) **or** `→ suppressed` (`email_send_id = NULL`, `gate_reason` set). The composed `breaking_summary` / `full_briefing` persist **either way**, so the in-app "quiet day" record renders from a real row rather than being faked client-side. `suppressed` applies to **morning only** — evening always fires (its job is closure; on an empty day it degrades to weather + sign-off, which is a `sent`, not a `suppressed`). The Replicache read schema adds `slot`, `status`, `send_decision` so the client can render a quiet morning distinctly from an absent one.

**D. Source-availability contract: closure requires positive evidence; absence never closes.** Compose-time reconciliation (decision #2) is **fail-safe toward surfacing**. A loop is suppressed-as-closed **only** on a _positive authoritative signal_ (GitHub reports the PR merged; a Gmail thread shows a reply was sent). When the provider is unavailable — scope missing, integration not connected, API error, or the contribution is `null` — the loop **stays live and is surfaced**, optionally flagged "couldn't verify current state." The composer is **forbidden from inferring closure**: the gather computes loop status deterministically and the composer only renders it — it may never downgrade a live loop to closed on its own. Email-derived signals (`source='email_triage'`) may _open or sustain_ a loop and may carry positive progress evidence, but their **absence never closes** one. This **corrects the stale line in `docs/reference/briefing.md`** that says scopes are unchanged from m10 and briefing reads local DB only: calendar anchoring adds the **existing `CALENDAR_READONLY_SCOPE` (`calendar.readonly`)** to `GOOGLE_FEATURE_SCOPES.briefing` (which today carries only `gmail.readonly`). This **deliberately reuses** the scope the `calendar` feature already grants — public/sensitive tier, free to verify, often already consented — rather than introducing the narrower `calendar.events.readonly` ADR-0041 named; that constant does not exist in `oauth.ts`, and a second, divergent calendar scope would add a consent line and break the app's single-calendar-read-scope convention for marginal least-privilege gain. If least-privilege ever justifies the narrower scope, that's a deliberate `oauth.ts` change, not a doc-vs-code drift. Reconciliation reads ingested integration state from local DB where Alfred ingests it, degrading to surface-as-live where it doesn't. Current implementation has best-effort calendar + weather gatherers and keeps `integration_activity: { items: [] }` until direct activity producers are wired.
