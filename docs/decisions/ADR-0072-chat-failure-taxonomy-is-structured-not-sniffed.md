# ADR-0072 — Chat failure taxonomy is structured, not sniffed: an attachment-presence gate, a narrowed signal set, and terminal-aware finalization (resolves #269)


**Decision.** A failed chat turn's `error_kind` is gated by **structure first, then narrowed by an intentional signal** — never by an over-broad substring net — and a message is only finalized `failed` when the fault is genuinely **terminal**. Three changes, in priority order: **(1) A presence gate is the load-bearing fix.** An `error_kind` in the `attachment` family is returned only when an **image attachment is actually present in the model's replayed input**; with no image anywhere a `drive.export_file`/tool/persistence failure classifies as `generic` ("Something interrupted this reply"). Because the whole-thread transcript is replayed every turn (`.lessons/chat-vision-transcript-replay-poison.md`), the gate is **thread-wide but split by recoverability**: an image on the *current* user turn yields `attachment` (the UI's "Send without it" retry can drop it), whereas a reject attributable only to an *earlier* turn's replayed image yields a distinct **`attachment_history`** kind whose recovery is "start a new chat" — because the "Send without it" retry only drops the current turn's attachments and would otherwise dead-end, failing again on the same poison. This (with the current/historical split) resolves the reported #269. **(2) Narrow the classifier to the genuine attachment-failure signal.** The legitimate attachment case is the **model provider rejecting a hydrated image** at the generation call (`"unable to process input image"` and the `invalid`/`unsupported image` family), recurring on transcript replay. `classifyChatFailure` keeps only that narrow signal set — **gated on the presence/locus of an image** (`currentTurnHasImage` / `historicalHasImage`, derived from a `chat_messages`⋈`chat_attachments` join) — and the over-broad `mentionsAttachment` net (`attachment|file|image|media|mime`) is **deleted**, because that net is exactly what mis-bucketed the export failure. Attachment *hydration* keeps its existing graceful behavior — a bad image is swallowed per-image into a placeholder text part and the turn continues; it is **not** promoted to a turn-failing throw (that would regress graceful degradation, and hydration is not where the user-visible attachment failure surfaces today). **(3) Terminal-aware finalization**: `finalizeFailedMessage` marks the `chat_messages` row `failed` only on a genuinely terminal fault, not on an error that the executor will retry/reclaim — so the message status and `agent_runs.status` agree.

**Why.** Dev-DB proven: `msg_oo41nkmv4e61` was `status='failed', error_kind='attachment', content=''` on a turn with **no attachment**, while its run kept looping (the #267 poison). `classifyChatFailure` (chat-turn.ts:1319-1340) sniffs an over-broad substring net (`attachment|file|image|media|mime`, plus a `could not process` clause) to *guess* the kind — exactly the "infer intent from a string" anti-pattern that caused the GitHub/export misuses — so a non-attachment failure whose message merely contained `"file"` got bucketed as `attachment` and the UI showed "I couldn't read one of the attached files / Send without it" for a request with nothing attached. The desync (message `failed` while run `running`) came from finalize-then-rethrow on an error that was then reclaimed. The codebase already states the right philosophy — the `ChatErrorKind` doc comment says it *"borrows Effect's tagged-error → handle-per-tag shape"* — the defect is that the classifier conflated the *one* genuine attachment signal (the provider's image-reject) with a net broad enough to swallow unrelated tool errors, and nothing checked whether the turn even had an attachment.

**The shape.** A `threadImageAttachments(userId, threadId, currentUserMessageId)` helper joins `chat_attachments`⋈`chat_messages` for the thread's `ready` image attachments (a direct `image/*` upload or a degraded modality that contributed keyframe images) and returns `{ currentTurn, historical }` by matching each attachment's `message_id` against the triggering `userMessageId` (carried on the chat run state). `classifyChatFailure(err, { currentTurnHasImage, historicalHasImage })` matches the narrow provider-image-reject signal set and then returns `attachment` if the current turn has an image, else `attachment_history` if only an earlier turn does, else `generic`; the broad `mentionsAttachment` net is removed. Hydration's per-image swallow-to-placeholder (today raising `UnsupportedStoredImageError` caught locally) is left intact — it is *not* the failure surface. `finalizeFailedMessage` is called only from the terminal-fault path (the #267 backstop guarantees poison/commit failures *reach* terminal rather than looping, which is what makes "finalize only when terminal" coherent). Client `FAILURE_PRESENTATION` gains an `attachment_history` row (copy: an earlier image keeps affecting replies → start a new chat, `retry:"none"`); the `attachment` row keeps its "Send without it" retry; a non-attachment tool failure renders the honest `generic` copy instead of a nonsensical attachment chip.

**Alternatives.** (a) **Presence gate but keep the broad substring net** — rejected: within an attachment-bearing turn the net still mis-tags an unrelated tool failure as `attachment`; the gate must be paired with narrowing the net to the one genuine signal. (b) **Throw a tagged `AttachmentError` at the hydration site and delete all signal matching** (an earlier draft of this ADR) — rejected: hydration already swallows a bad image to a placeholder and continues, so it is *not* where the user-visible attachment failure surfaces (that is the provider image-reject at the generation call); promoting hydration to a turn-failing throw would regress graceful degradation, and a hydration-thrown tag would never see the provider reject — leaving genuine image-rejects misclassified `generic`. (c) **A new `tool_failed` kind** — rejected as scope creep; `generic` is honest and the copy is adequate. (d) **Reconcile message↔run status with a sweep/join after the fact** — rejected in favour of not creating the desync in the first place (terminal-aware finalization); the backstop already guarantees terminality.
