# ADR-0081 — Non-prod must not mutate the shared Gmail mailbox: one explicit `GMAIL_MAILBOX_WRITES_ENABLED` gate at the write boundaries (BUILT — #278)


**Decision.** Dev and prod connect to the **same real Gmail account**, and both ran the triage relabel writer and the watch lifecycle against it — each environment's classify strips the other's Alfred labels and applies its own, so the live mailbox lands on the wrong label or none (Tania thread, 2026-06-25). Gate every outbound Gmail **mutation** behind a single resolver, `gmailMailboxWritesEnabled()` (`@alfred/env/server`): an explicit `GMAIL_MAILBOX_WRITES_ENABLED` (`"true"`/`"false"`) wins, otherwise it **defaults to production-only** (`NODE_ENV === "production"`). Checked at the two real chokepoints — `reconcileThreadLabel` (the ONE label-writer per rfc-triage-tags Invariant 6; it now short-circuits to `applied:false reason:"writes-disabled"` before touching Gmail, so the canonical `email_triage` row still commits — DB-only classify) and the watch lifecycle (`installGmailWatch`/`uninstallGmailWatch`/`stopGmailWatchWithAccessToken`, plus an early skip in the `gmail.watch_install`/`watch_renew` jobs). Prod behavior is unchanged.

**Why.** The gate is **an explicit flag, not implicit `NODE_ENV` coupling** — a developer can deliberately opt a box into real writes (`=true`) without faking `NODE_ENV=production` (which would change a dozen unrelated behaviors), and a future staging target that runs `NODE_ENV=production` can be told `=false`. The decision is **resolved in one helper**, never by branching on the env field at call sites, so the policy is discoverable and can't drift. Gating at `reconcileThreadLabel` (not the lower `applyTriageLabel`) keeps DB correctness: the skip returns before any label id is computed, so nothing bogus is persisted to `applied_label_id`, and it covers **both** the classifier workflow and the async relabel job (the existing `emailTagging` feature flag only gated the workflow). Stopping the watch from non-prod is the *more* dangerous direction — it would kill prod ingestion — so `stop`/`uninstall` are gated too. The `writes-disabled` relabel outcome logs at **info**, not the error level the #277 `target-unresolvable` path uses, because in non-prod it is expected, not a fault.

**Alternatives.** (a) **Gate on `NODE_ENV` directly** — rejected: implicit, conflates "is this prod" with "may I write Gmail," and offers no deliberate dev opt-in. (b) **Gate inside the low-level `gmail.ts` wrappers** (`modifyMessageLabels`/`createLabel`/`startWatch`) — rejected: they return `GmailMessage`/`GmailLabel`/watch state, so a no-op would have to fabricate a return the caller persists; the semantic chokepoints are the honest seam. (c) **Reuse the per-user `emailTagging` feature flag** — rejected: it's a user preference (off = "don't tag my mail"), orthogonal to the environmental "don't fight prod over the shared account," and it doesn't cover the watch or the relabel job. (d) **Separate dev Gmail account** — the real long-term fix, but out of scope and gated on test-account provisioning; the flag is correct regardless.
