# ADR-0050 — Todos: persisted open loops, hybrid-authored, one-table status model, passive v1

**Decision.** Add a **`todos`** entity: a user-managed list of commitments, surfaced in the right-hand quick rail, where items are either captured by the user or **proposed by Alfred** from across connected integrations. The framing claim that makes the rest cohere: a todo is the **first _persisted_ materialization of the open-loop model** ADR-0048 deliberately kept ephemeral. ADR-0048 computes "open loops" on the fly at briefing compose-time, reconciles them read-only, and throws them away — explicitly _not_ building a persistent cross-source store (its Parked "continuous open-loops state machine"). A todo is the user's opt-in to _persist_ one such loop and track it to completion. This entity is therefore the natural future home of that parked machine, which is why its deferrals (below) are deliberate, not gaps. **v1 is passive**: Alfred authors and assists, but never executes.

**Entity & status model — one table, status-driven.** A single `todos` table, not a todo table plus a separate suggestions table. Status is `suggested | open | done | dismissed`:

- `suggested` — Alfred-proposed, not yet accepted; renders in the rail's _Suggestions_ section. Authored only by Alfred (`created_by='agent'`).
- `open` — a live todo: a user's manual add, or a promoted suggestion. The `+` affordance flips `suggested → open` (a one-field update, no cross-table copy).
- `done` — completed; `completed_at` set. Done todos **linger 7 days** then fall out of the sync window, not the database (instant vanish loses the "I did this" beat and the list's honesty).
- `dismissed` — declined/dropped. On a `suggested` row it is a "no thanks" signal; on an `open` row it is "dropped it." Both terminal.

Deliberately **absent at v1**: `running` / `interrupted` / `needs_attention` / `error` — those are dimension's _agent-run_ states, reserved for the deferred agent-executable path. Todos are a **flat open list**, not day-bucketed: the rail's date header is ambient context only. Columns: `id`, `user_id` (FK CASCADE), `name`, `description?`, `status`, `created_by` (`'user'|'agent'`, survives promotion so acceptance is measurable later), `executor` (`'user'` in passive v1; `'agent'` deferred), `kind` (`'task'` in v1; future executor-specific variants), `assist?`, `sources` (jsonb), `agent_run_id?` (FK, traceability), `completed_at?`, `position?` (forward-compat for manual reorder), `due_date?` (forward-compat, no scheduling built), `+ lifecycle_dates`, `row_version`.

**Authoring — `system.suggest_todo`, source-agnostic, no HIL.** Alfred's proposals enter through a single write tool, `system.suggest_todo`, callable by any agent run. It inserts a `suggested` row. It is **off the `action_stagings` / approvals HIL path** (ADR-0043): a suggestion has no real-world side effect, so gating it would be a category error. This is the explicit exception to the generic "state-changing system tools are staged for audit" runtime posture: audit lives on the todo row (`agent_run_id`, `created_by`, lifecycle dates), not in an approval record. The **primary caller is the briefing workflow** — it already runs a cross-source `gather` (email + calendar + `integration_activity`), so suggestions ride the existing cross-source open-loop computation rather than a second pipeline; triage and chat may also call it. The tool is **source-agnostic by construction**: cross-integration coverage falls out of the gather and widens automatically as `integration_activity` producers land (GitHub, then Slack once connected). User-authored todos and user-initiated lifecycle transitions (`create`/`complete`/`reopen`/`promote`/`dismiss`/`edit`) are **client Replicache mutators**; agent writes are server-side via the tool, then poke. The `assist` field carries an optional Alfred-authored tip on how to approach the item, degrading to an honest "I can't act on this — no permission / integration not connected" when Alfred is clueless. `assist` is _not_ execution.

**Multi-source provenance — `sources` from day one.** Provenance is a `jsonb` array of typed refs `[{ provider, kind, id, url? }]`, not a single email-only `source_thread_id`. The canonical source identity is `(provider, kind, id)`; `url` is display/navigation metadata and does not participate in dedup. A todo represents a real-world commitment that can span channels (a Gmail thread _and_ a Slack thread on one row), so it must carry N sources from the first write. This is also the data the deferred cross-source state machine would watch. The briefing's `[[<kind>:<id>]]` reference _resolver_ is deliberately **not** reused: it resolves against a frozen `gather` snapshot, whereas a todo resolves against _live_ data; same kind vocabulary, different resolution context, so fusing them now would be premature coupling.

**Dedup — owned by gather-normalization + a merge guard, structural only.** One real-world event must yield one suggestion even when it arrives through two channels (tagged in Slack _and_ an email notification of that tag). Dedup lives in two places, neither of them the todo schema:

1. **Gather normalization** — a service-notification email (e.g. `notifications@slack.com`) normalizes into its origin-provider activity item via triage's existing `SenderContext` body-actor parsing + `integration_activity` email-triage backfill (`source='email_triage'`), so it never becomes a standalone email loop. When a direct producer exists, the direct event and the notification-email dedup by provider/thread id here.
2. **`suggest_todo` idempotency** — before inserting, the tool checks for an existing `open`/`suggested` todo referencing any incoming `source`; on overlap it **merges** (appends only missing source refs to that row's `sources`) instead of creating a duplicate.

This handles the **structural** case (the notification is recognizable and shares an id). **Semantic** dedup — two genuinely independent signals about the same ask with no shared id — is LLM-judgment over loop identity and is **deferred** with the rest of cross-source resolution; worst case the user gets two suggestions and dismisses one.

**Surface.** Right-hand quick rail (`quick-access-rail.tsx`), two sections mirroring Dimension's web app: **Todo** (checkbox list of `open`/`done`) above **Suggestions** (`suggested` rows, each with a `+` to promote). Replicache-synced: `IDB_KEY.TODO`, per-row key `todo/{id}` (flat — no day prefix); `syncedTodoSchema = { id, status, createdBy, executor, kind, name, description?, assist?, sources, agentRunId?, completedAt?, position?, dueDate?, rowVersion }`; `ENTITY_FETCHERS.todo` filters `user_id = current AND status != 'dismissed' AND (status != 'done' OR completed_at >= now() - 7d)`. The screenshot's checkmark/camera toggle is the deferred agent-executable switch and is at most laid-out, not wired.

**Why.** "Action item extraction → managed todo list" was listed in the workflow catalog (this file, workflow-defaults table) as **OFF** at v1 — "partly redundant with the email-triage `action_needed` tag." That redundancy dissolves once you see a todo as a _persisted open loop_ rather than an email-tag mirror: the `action_needed` label is an immutable triage fact about one thread; a todo is a cross-source, user-owned commitment the user manages to completion. Building it on one status-driven table (rather than dimension's two-entity suggestion/promote shape) matches Alfred's single-user scale and keeps provenance attached to one surviving row. Routing Alfred's proposals through a no-HIL `suggest_todo` tool — not the approvals path — keeps the heavyweight gate where it belongs (side-effecting writes) and lets the cheap, side-effect-free act of _suggesting_ stay cheap. Keeping v1 passive avoids prematurely opening a second front door onto the boss runtime (manual-trigger workflows already are one) and avoids the parked cross-source state machine, while the forward-compat columns (`executor`, `kind`, `sources`, `due_date`, `position`) mean each deferred capability lands without a database migration.

**Alternatives.**

- **(a) Two entities (dimension's `suggestedMessages` + `todos` + `createFromSuggestion`).** Rejected — dimension needs the second table because suggestions there also back suggested _chat prompts_; Alfred has no such second consumer, so it buys only a join, a copy-on-promote, and a second synced entity. A `suggested` status is the same UX with one table.
- **(b) Agent-executable todos in v1** (mark `executor='agent'`, spawn an `agent_runs` run, reflect run-state on the checkbox, gate tool calls via `/approvals`). Deferred — strictly more powerful and clearly on the roadmap, but it inherits run-state, interrupt linkage, and a tool-scope model onto a checklist, and overlaps the existing manual-trigger workflow front door. Schema is shaped so it lands later without a database migration.
- **(c) Single email-only `source_thread_id`.** Rejected — a todo is a cross-channel commitment; an email-only link can't represent "opened from a Slack tag _and_ an email" and would need a migration the moment Slack connects.
- **(d) Cross-source auto-close now** (watch every surface; close a todo when the user replies anywhere). Deferred — this _is_ ADR-0048's parked "continuous open-loops state machine": live webhooks from every integration + identity resolution + completion signals. Also blocked on reality (Slack isn't connected). v1 completion is manual.
- **(e) Route suggestions through the `action_stagings` HIL.** Rejected — approvals exist for side-effecting writes; a suggestion has no side effect, so gating it is a category error and a heavyweight detour for a dismissable row.
- **(f) Reuse the briefing `[[<kind>:<id>]]` resolver for provenance.** Rejected for now — it resolves against a frozen gather snapshot; todos need live resolution. Shared kind vocabulary, not a shared resolver.
- **(g) Day-bucketed todos with rollover** (dimension's `assigned_date`). Rejected at v1 — brings a rollover job, overdue semantics, and the "unfinished todos vanish/pile up" annoyance for no v1 value; `due_date` lands forward-compat without scheduling.

**Parked (explicit non-goals this iteration).**

- **Agent-executable todos (the B-path)** — `executor='agent'`, runtime-backed, HIL-gated. The headline future capability; schema is forward-compatible for it.
- **Cross-source auto-close + cross-source identity resolution** — the ADR-0048 parked state machine; todos are its future home (the `sources` array is the watch-list).
- **Semantic dedup** of independent same-topic signals with no shared id.
- **Due-dates / scheduling / rollover** and the parked **advance-reminders** workflow (commitments surfaced N days out) — `due_date` column exists; the cadence logic does not.
- **Manual drag-reorder** — `position` column exists; the interaction does not.
- **Suggestion-acceptance learning** (tuning what Alfred proposes from accept/dismiss rates) — `created_by` + dismissed-state make it measurable later.

**Open.**

- **Suggestion production cadence** — primary caller is the briefing workflow (≈2×/day), but whether triage events should also fire `suggest_todo` live (event-driven freshness vs. proposal noise) is settled during build against observed rates, not now.
- **Exact rail visual grammar** — section treatment, suggested-row affordance, done-fade — settled at build time against Dimension's web app and the existing `quick-access-rail.tsx`; design detail, not architectural.

**Amendment (2026-06-05) — producer model inverted: suggestions are real-time off triage, not a briefing ride-along; resolves the cadence Open.**

The original ADR named the **briefing workflow** the primary `suggest_todo` caller (reuse its cross-source `gather`, avoid a second pipeline) and left **production cadence** Open. Production exposed the failure mode: a new user (`yash.k@oliv.ai`) signed up, accrued **6 `action_needed` + 5 `urgent`** triaged threads within six hours, and got **zero** todos — the `morning-briefing`/`daily-briefing` cron never fired in that window, and nothing else calls the tool. The cron-batch producer makes the rail _hostage to a ~2×/day job_; for the surface whose entire value is a live, in-the-UI commitment list, that is the wrong cadence. **Decision: todos are produced by a real-time pipeline; the briefing is removed from the todo path entirely.**

- **Briefing is fully decoupled — not even a "mentioner."** It neither reads `todos` nor calls `suggest_todo`. Its action-ish mentions are **ephemeral open loops** (ADR-0048), computed from the gather/embeddings at compose-time and thrown away — a parallel feature that happens to look similar, not "todos that got mentioned." This reaffirms the CONTEXT.md boundary (ephemeral _open loop_ vs. persisted _Todo_); the two never touch. Strike "primary caller is the briefing workflow" from the original Authoring section.
- **Producer = a tail step on the `email-triage` run.** "Real-time like email tags" means the tag _is_ the trigger: triage already fires per freshly-ingested Gmail doc (`emitEvent`, ADR-0047), so the suggestion is minted in the same run that classifies the mail. The todo's `agent_run_id` points at that triage run — clean provenance, **no second pipeline, no extra run, no boss**. `suggest_todo` stays the **source-agnostic seam** (its original design), so each future real-time source calls it from _its own_ ingestion path: email via triage now; `integration_activity` producers (GitHub first) from their ingestion as they land. There is **no standalone cross-source gather** for todos — the briefing owns the only daily gather, and todos ride per-source events instead.
- **Selectivity — the tag is necessary, not sufficient.** Two-stage gate: (1) deterministic category pre-filter drops `marketing`/`newsletter`/`fyi`/`done` outright; (2) a **context-sufficiency judgment** mints a suggestion only when the mail is worth acting on _and_ carries enough concrete context to write a specific, actionable item. A vague ask ("something broke, please fix" with no what/where) yields **no todo even when tagged `action_needed`/`urgent`** — a bad, un-actionable rail item is worse than a missing one.
- **Where the judgment runs — folded into the single cheap classify call, zero added cost.** Consistent with ADR-0051 ("cheap-model-always, made smart by deterministic context; no routine boss"): the context-rich `classify` call already has the full email open, so its output schema gains one optional `todoSuggestion: { name, assist? } | null`. No new LLM call, no boss escalation (ADR-0051 removed it). The quality lever for the context-sufficiency call, if flash-lite under-judges, is ADR-0051's **conditional second cheap pass** / prompt iteration — **not** a boss step.
- **Unchanged.** One-table status model; no-HIL (a suggestion has no side effect); source-overlap **merge** as the v1 dedup guard (now more load-bearing — the same thread can surface in both a real-time triage event and, later, a cross-source activity event); 7-day done window; `executor`/`kind` inert. Noise is governed by the selectivity gate and tuned against observed accept/dismiss (`created_by` + `dismissed`), per the original noise rationale.

This **resolves the cadence Open** (real-time/event-driven, not cron-batch) and reverses the producer choice; it is a producer/trigger change only — **no schema migration** to `todos` (the `todoSuggestion` field lives on the triage classifier's output, not the DB).

**Amendment (2026-06-06) — todo-worthiness is an orthogonal rubric, not a category gate; floor shrunk to `{marketing, newsletter}`.**

The 2026-06-05 amendment's selectivity was a **two-stage category gate**: (1) a deterministic pre-filter dropping `marketing`/`newsletter`/`fyi`/`done`, and (2) a context-sufficiency check folded into the cheap classify call. Production showed this conflates two orthogonal axes. _Category_ answers "what kind of mail is this / which Gmail label"; _todo-worthiness_ answers "does this leave an obligation on the user worth remembering." Folding the second into the first produced **both** error directions: a self-initiated "Sign in to Anthropic" email (correctly `action_needed`) **minted a todo** because `action_needed` is eligible and the ask is concrete; and an `fyi` that carries a real obligation ("auto-renews unless you cancel") **could never** mint one because `fyi` was floored. The fix is not a sixth exemplar — it is to make the todo decision its own judgment.

**Decision: todo-worthiness is an orthogonal rubric the cheap model applies over the whole email, with category demoted to evidence + a thin consistency floor.**

- **The rubric — five ordered tests, stop at the first failure (prompt rule 16).** (a) **Obligation on me** (gate): is there an action the _user_ must take? (b) **Significance**: does it matter on its face — a deadline, money, a deliverable, a commitment — vs. real-but-trivial (rate-your-driver, optional surveys)? (c) **Memorability**: would the user forget/drop it, or is it self-resolving / mid-flow (self-initiated auth, expiring codes, "thanks!")? (d) **Actionability**: can a specific item be written from the email alone? (e) **Already handled**: thread state shows the user replied / loop closed. Only all-five-pass yields a `todoSuggestion`. This is a **memory-aid** test, not an "is there an action" test — **memorability is the load-bearing discriminator**, and it dissolves the old rule-15 auth patch into a _consequence of principle_ (auth fails the memorability test) rather than a hand-written exception.
- **Category and todo may legitimately disagree.** The decision evaluates the whole email including secondary/trailing asks; a `done` closure that ends with a significant request stays `done` AND can yield a todo. The category is never distorted to chase the ask.
- **The deterministic floor shrinks to `{marketing, newsletter}`** (`TODO_INELIGIBLE_CATEGORIES`, `resolveTodoSuggestion`) and is reframed as a **consistency guard against classifier leakage**, not a relevance judgment: a genuine personal obligation on a broadcast bucket is, by definition, a misclassification. `fyi` and `done` leave the floor — the rubric owns them.
- **Significance is split; personal relevance is deferred.** v1 judges **intrinsic** significance from the email alone — which already kills both live bug classes (auth via memorability, trivial-survey via significance). **Personal relevance** — "does this touch a project/person _this user_ cares about" — needs the agent's persistent memory and is parked (D1 below).
- **Principles + log-sourced exemplars.** The rubric is the pillar; a small set of **exemplars** anchor it only at boundaries where two dimensions tug (each exemplar names its deciding dimension), harvested from `triage.sender_extraction` logs, never pre-guessed. This is the disciplined form of the example-patching that opened this work.
- **Observability — a rubric trace.** `todoDecision: { outcome, note? }` is emitted on **every** classification (`outcome ∈ {proposed, no_obligation, not_significant, would_not_forget, too_vague, already_handled}`), logged to `triage.sender_extraction`. A wrong suggestion _and_ a wrong omission are now debuggable by dimension — so the rubric is **tuned**, not patched.
- **Unchanged.** Folded into the single cheap classify call, zero added LLM cost, no second pass, no boss (ADR-0051); one-table status model; no-HIL; source-overlap merge; manual completion. **No schema migration** — the rubric output rides the classifier; `todoDecision` is an additive field on its output, not a DB column.

**Auto-removal of suggestions — explicitly out of scope; v1 is manual dismissal.** The lifecycle counterpart ("when does a suggested todo stop being worth showing") is deferred to the existing `dismissed` status (user dismisses in the UI). Two parked forms: **same-thread retraction** (auto-dismiss an unpromoted suggestion when sent-mail thread state shows the user already replied — feasible on the foundation built, withheld until dismissal rates justify the tool-call spend) and **cross-source auto-close** (already parked, alt-d). Every retraction is a tool-call/DB mutation; spend them on evidence, not speculation.

**Parked threads surfaced during this grill (deliberate non-goals, recorded so they aren't gaps):**

- **D1 — Personal-relevance significance.** A cached, compact `User context` projection (role / company / active projects / key people) fed to the rubric's significance test. Gated on `entities` actually populating (0 on prod today) and a cold-start fact-quality check. The orphaned `readTriageUserContext` reader is the seed; "cache the projection" is real work (6 live queries, uncached).
- **D2 — User-fact expiration/decay.** Facts need a validity horizon so a stale role/project doesn't silently poison significance. Fact-layer concern (ADR-0012), but a prerequisite for D1 being trustworthy.
- **D3 — Self-evolving memory.** The broader system that learns the user from every chat/email/integration signal. Its own track; this ADR only _consumes_ memory.
- **D4 — Agent-authored deterministic execution facets.** The escape from the N-tool-calls cost of bulk mutation: the agent authors a schema + handler once (approved), then steady-state runs without an LLM in the loop ("a machine that builds machines"). Cross-cutting agent-runtime direction, not todo-specific. See `oss/self-syncing-agent`.

**Amendment (2026-06-09) — stringency reframe: real-stake significance, manufactured-urgency exclusion, ownership-attribution gate, terse-imperative voice.** Production review of the live rail (37 agent-todos across two prod accounts; ~70% noise) exposed three failure classes the 2026-06-06 rubric did not catch, all rooted in a **too-loose significance test**, not bad bot-detection. The fix sharpens the rubric's text; it does **not** un-defer personal relevance (D1 stays parked).

- **16b significance is reframed from "matters on its face" to "real, external stake."** The old wording — "a deadline, money, a real deliverable, a commitment to a person, _or a clear cost of not doing it_" — let **manufactured urgency** clear the bar: a chess.com streak "lost at midnight," "7 unread on Linear," "5 people viewed your profile," marketing scarcity. The reframed stake is one of: _a real, identifiable person waiting on an action by the user_ (identifiable from the email at v1; the org-graph enriches this under D1/B); _money owed or at risk, a hard deadline, lost access, a commitment made to a human_; **or** _a real-world consequence to the user judged from content_ — which is exactly where a **bot** earns a todo (leaked key, prod down). Stakes a product **manufactures to drive engagement**, and **ceremonial obligations** (AGM/"save-the-date"), carry no stake → `not_significant`, fall back to `fyi`. This stays **intrinsic** (email-only judgment) and is written as a **B-ready seam**: when D1's user-context projection lands, it feeds 16b as one more observation, not a rewrite. Personalized relevance (B) is the agreed _destination_, not a rejected path.
- **16a gains an ownership-attribution gate** (the "Sakshi standup" bug: a `done` todo "Run the Engineering standup meeting" minted for the user when the body said _Sakshi_ runs it — the model had the right owner in `assist` and still assigned it to the user). 16a now requires the action be owned by **the user, not a third party named in the body** → else `no_obligation`. This needs the one piece of identity the email-only classifier lacks: a **minimal identity signal** (user display name + account email), added as a deterministic observation (ADR-0051 amendment). This is the first surgical brick of D1/B, forward-compatible with the full user-context slice.
- **The bot carve-out is model-judged, not slug-floored.** Rejected: growing `BOT_SLUGS` or a deterministic `resolveTodoSuggestion` backstop keyed on `effectiveAuthor='bot'`. Per ADR-0051 §5's anti-brittleness stance, the cheap model judges bot-ness + consequence from subject/content; advisory automated output (Greptile/CodeRabbit nitpicks, Dependabot) → `fyi`/no-todo unless the body carries a hard consequence. `effectiveAuthor` stays a fed _hint_, never a floor. **Liveness layer (the refinement the first dry-run forced):** for code/PR/review findings — bot OR human — the consequence test turns on _is something ALREADY LIVE at stake_: a secret already committed/exposed, a vulnerability in `main`, a prod outage, a blocked deploy → real stake → todo; a finding that exists only in the UNMERGED PR (nitpick, perf, even a vuln in proposed code not yet in `main`) is pre-merge advisory → `fyi`. The discriminator is liveness, not "is a reviewer waiting" — this is what the dry-run showed prompt-only was missing (Greptile leaked 3/4 as "reviewer waiting" before the layer). No hard guarantee — validated by the dry-run backfill, tuned from `todoDecision` traces.
- **Title voice: terse imperative, active, name the object.** `name` is a short imperative (target ≤~8 words) with the real verb (`Reply`, `Pay`, `Fix`, `Rotate`), never a hedge ("Review and address…", "Look into…"). `assist` only when it carries a decision or concrete next step, active voice, else omitted. Schema cap (`name` ≤120) unchanged; the lever is the prompt.
- **Trace decision:** reuse the existing `not_significant` outcome with a light `note` convention (`manufactured:`/`advisory:`) rather than adding a `todoDecision.outcome` value — manufactured-stake _is_ a significance failure; smaller blast radius, still log-aggregable.
- **Validation before any write: a dry-run backfill.** Re-classify historical email with the new prompt, **read-only**, and diff against current state in three buckets — _kills_ (suggested todos the new bar drops), _category flips_ (→fyi), and _false negatives_ (real obligations wrongly dropped, the risk bucket). Ship the live prompt + a real re-tag/re-suggest backfill only after the diff clears.
