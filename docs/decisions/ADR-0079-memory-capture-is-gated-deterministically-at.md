# ADR-0079 — Memory capture is gated deterministically at two layers (write-invariant vs document-attribution), with one canonical fact ontology, read-side convergence, and hold-`proposed` conflict detection (DESIGNED — in progress, see docs/plans/memory-capture-hardening.md)


**Decision.** The per-document fact-extraction path stops harvesting transactional/third-party metadata as durable `user_facts`, enforced by **deterministic code gates at two layers**, with the prompt demoted to defense-in-depth. **(1) `@alfred/contracts` owns *what keys exist*:** one canonical fact-key registry, not a divergent `FACT_ONTOLOGY` vs `CANONICAL_FACT_KEYS` split. Canonical storage keys are durable fact concepts: `full_name`, `first_name`, `last_name`, `user_nickname`, `bio_summary`, `work_summary`, `employer`, `job_title`, `team`, `manager`, `location`, `home_city`, `home_country`, `timezone`, `birthday`, `marital_status`, `spouse_name`, `personal_site`, `github_username`, `twitter_handle`, `linkedin_url`, `family_summary`, `notable_relations`, plus prefixes `relationship:` and `pref:`. `FACT_KEY_ALIASES` is an **explicit** legacy/producer map — `current_company`/`company`/`company_name`→`employer`, `current_role`/`role`→`job_title`, `current_work`→`work_summary`, `current_location`→`location`, `name`→`full_name`, `personal_website`→`personal_site`; **no** fuzzy/semantic guessing, so `website`/`url`/`homepage` stay rejected — consumed by `canonicalizeFactKey(key)` before dedup/conflict. **(2) `packages/api/.../memory/fact-policy.ts` owns *which sources write which keys*:** `classifyDocumentFactKey → "tierA" | "tierB" | "not_writable"` (Tier A authorship-free = `relationship:<email>` only; Tier B authorship-required = the canonical identity/profile set; `not_writable` = `pref:*`, `standing_instruction`, `phone_number`, unknown, junk), `validateFactValueForKey`, `SINGLE_VALUED_KEYS` over the canonical profile keys, and an evidence-returning `authoredByUser(doc, selfIdentity) → Authorship` that is **conservative-default-`false`** and **provider-discriminated rather than stringly-typed**: positive decisions carry structured proof such as Gmail `{source, method:"sent_flag"|"from_connected_account", accountId, accountEmail, fromEmail}` or Slack/GitHub `{source, method, observed, matchedSelf}`; negative decisions carry a closed reason (`unsupported_source`, `missing_self_identity`, `missing_author_identity`, `identity_mismatch`, `ambiguous_author`, `metadata_unparseable`). Gmail prefers `documents.accountId`→`integration_credentials.accountLabel` over global `user.email`; Slack/GitHub require stable ids or verified emails/logins; `gcal`/notion/imessage/uploads/unknown ⇒ `unsupported_source`. **`proposeFact` is the unbypassable persistence backstop:** canonicalize aliases for **all** sources before dedup/conflict (non-document `ok:false` persists as-is + a `fact_key_unknown_non_document` trace), and for `source.kind==="document"` only it rejects unknown / `not_writable` / bad-value-shape; it does **not** do authorship. **The workflow** (`memory-extraction.ts`) adds the contextual authorship check, selects `documents.accountId`, loads connected-account labels, increments `blocked`, and traces structured proof/reject data. **Read-side convergence is in scope:** `read_user_context` keeps DTO fields such as `currentCompany/currentRole/currentLocation`, but maps them from canonical storage keys `employer/job_title/location`; existing live alias rows are canonicalized in the same slice. **Conflict detection is source-agnostic:** for `SINGLE_VALUED_KEYS`, an incoming value differing from an active authoritative value supersedes immediately when the source is user-driven, but is held as `proposed` with no `memory.fact_learned` event for autonomous sources. Cleanup runs on the same classifier: alias-key live-row convergence, then canonicalization failures, `not_writable`, and Tier-B attribution failures; done = dev verifiably ≤1 active value per single-valued key.

**Why.** This is the capture-side root of the identity-hallucination bug (read-side #329 shipped in #332) and a **recurrence** of `.lessons/user-facts-document-metadata-noise.md`: the prior fix leaned on the extraction prompt + a tiny `isDocumentMetadataKey` deny-list, and the prompt did not hold — dev shows `home_city`×12, `home_country`×7, `github_username`×8 (incl. the `Alfred` bot), a contact's `phone_number`, `personal_site = sandromaglione.com`, all `confirmed, 0.95`. Two distinct failures the data exposed: **transactional junk** (`evoting_*`/`*_insurance_*`/`programming_language`) which key-shape alone can reject, and **third-party attribution** (a sender's signature-block city landing as the user's) which `proposeFact` *structurally cannot* judge — it only sees `(key, value, source.kind)`, never the sender. The workflow already has the document context, so authorship belongs there. Canonicalization and rejection are deliberately *different policies*: aliasing prevents `current_company`/`company`/`company_name`/`employer` coexisting as separate truths and must run for every source; unknown-key rejection is scoped to the polluted `document` path. Storage keys should be durable concepts, not read DTO labels: currentness is represented by status and validity windows, while the read API can still expose `currentCompany`. Identity has authoritative sources — cold-start research, user edits, `system.remember` — so a conservative-default-`false` authorship gate makes under-learning from email nearly free while killing the over-learning that is the bug. Hold-`proposed` over auto-supersede because deterministic code cannot tell "the user moved" from "a contact's city leaked" — both arrive at 0.95 — so the safe direction is to surface, not silently overwrite the truth.

**Alternatives.** (a) **Tighten the prompt again** — rejected: the prompt already states every needed rule and failed on exactly those cases; it stays as recall guidance, never the safety floor. (b) **One allow-list in `proposeFact`, context passed all the way in** — rejected: makes the persistence layer infer sender identity and reach into `documents`; the two-layer split keeps the unbypassable invariant context-free and the attribution check where the context already is. (c) **Keep `current_*` canonical to avoid touching #332** — rejected: it preserves a UI/read DTO naming accident as storage ontology. #330 touches the read side and live rows instead. (d) **Gate-only, no alias normalization** — rejected: too lossy during cleanup and leaves producer drift invisible; explicit aliases canonicalize and trace drift. (e) **Global unknown-key rejection across all sources** — rejected for #330: trusted/curated paths may keep unknown keys with drift traces, but known aliases still canonicalize globally. (f) **A new `conflict` status with review UI** — deferred to P2 governance (SI-4 in `long-term-memory-v1.md`): hold-`proposed` reuses existing statuses and caps the damage now. (g) **`pref:*` / `phone_number` document-writable under authorship** — rejected: durable preferences from email is a separate product problem, and phone numbers need a typed `{label,number}` value first. (h) **Auto-supersede single-valued conflicts by confidence/recency** — rejected: a stray 0.95 third-party value would silently overwrite the truth.
