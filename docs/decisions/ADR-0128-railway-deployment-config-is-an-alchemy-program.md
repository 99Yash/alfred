# ADR-0128 — The Railway deployment config is an Alchemy program (ACCEPTED — 2026-11-18; the program owns the production topology — 2026-11-18)

**Status.** Accepted, adopted. Amends [ADR-0007](./ADR-0007-hosting-railway.md) (hosting stays Railway), relates to [ADR-0114](./ADR-0114-effect-runs-the-mcp-connection-lifecycle-and-nothing-else.md) and [ADR-0129](./ADR-0129-effect-is-an-allowed-dependency-and-the-migration-is-gradual.md) (Effect adoption), and leaves [ADR-0108](./ADR-0108-infrastructure-cost-is-a-memory-shape-problem-not-a-platform-problem.md) untouched.

**Problem.** The deployment topology — server, web, Railway-managed Postgres with pgvector, Redis, private networking — exists only in the Railway dashboard plus an implicit Nixpacks build. The repo states none of it, nothing checks it, and ADR-0007's one-dashboard ergonomics have a cost the record never priced: the topology is memory, and memory is exactly what a platform switch burns. The owner's stated hedge — "if Railway is down, we might switch" — is not served by anything that exists today; leaving Railway would be a manual rebuild from recollection.

**Decision.** Alfred declares its Railway infrastructure as one typed TypeScript program using [Alchemy](https://alchemy.run) (`alchemy` + `@alchemy.run/railway`, Effect 4 runtime), versioned in the repo and applied with `alchemy deploy`. Hosting stays Railway; ADR-0108's cost verdict is untouched — this changes where the config lives, not what runs. Adoption is staged: the probe round-trip is done and the production cutover waits on the acceptance criteria below.

**Evidence.** Full probe round-trip on 2026-11-18 against a scratch project (measured numbers and every friction in [`docs/research/alchemy-railway-probe.md`](../research/alchemy-railway-probe.md); working probe in `references/scratch/alchemy-railway-probe/`): plan of 6 resources + 3 bindings in ~0.9 s; deploy in 2m02s with the service shipped as an uploaded build context (no Docker daemon, no git); live `/health`, Redis write+read, volume persistence, and a private Postgres URI that Alchemy itself secret-redacts; a second deploy proving **`Plan: no changes` in 7 ms**; and a destroy that removed 6/6 resources in 22.7 s with nothing left in the workspace. The type checker caught three real API mismatches in the docs' own example before anything deployed — the compiler carries the proof, which is the house style for gates.

## D1 — The infra program is its own program, outside app code

- One program (`alchemy.run.ts` + resource modules, e.g. under `infra/`) declares the topology. It imports `effect` — Alchemy v2 is Effect-native and its resources are typed through it.
- This is the first Effect use outside the ADR-0114 island. ADR-0129 (2026-11-18) opens Effect adoption generally at a gradual pace, so no adoption ADR was needed; the program follows the same per-module discipline — its public interface is a CLI, not app types.
- The program carries no business logic. Infrastructure binds to the app through environment variables only. If a resource seems to need app wiring inside the infra program, that is a smell to raise, not a capability to extend.

## D2 — The deploy trigger changes, and the memory ingest must follow (gating criterion)

- Today Railway builds on GitHub push, and the memory pipeline reads `RAILWAY_GIT_COMMIT_SHA` as the deployed commit (`docs/theory/memory.md`). Under Alchemy, the deploy is a context upload; the probe could not verify that Railway sets `RAILWAY_GIT_COMMIT_SHA` on such deploys, and the docs are silent.
- **No production cutover until the deployed-commit ingest reads a source that is proven on both the old and the new trigger** — verify Railway still sets the variable on context-upload deploys, or write the CI commit (`GITHUB_SHA`) into the service environment at deploy time and re-source the ingest.
- The first cutover experiment is `alchemy plan --adopt` against the real `alfred` project in a read-only plan: the probe proved adopt of owned orphans and preview machinery, but not takeover of a foreign, dashboard-created project.

## D3 — State is local, and recovery is the documented default

- `Alchemy.localState()` keeps state under `.alchemy/` (gitignored). A wiped state store re-adopts owned resources silently on the next deploy; foreign-looking resources fail with a typed `OwnedBySomeoneElse` instead of being adopted by accident. No new cloud dependency for state — the Postgres state backend exists if a second machine ever needs it, and needs no new provider either (ADR-0008's Postgres).

## D4 — Version pin and known frictions, accepted

- Pin `effect@^4.1.4` stable together with `alchemy` and `@alchemy.run/railway` at the same beta. The docs' `effect@rc` is stale and breaks the CLI boot (`effect/SemVer` is gone at rc.118) — probe finding.
- Accepted frictions: pre-1.0 beta churn on both packages; `alchemy logs` unsupported for Railway (logs stay in the dashboard); one harmless `mongodb` unresolved-import warning per Service bundle; OAuth setup is interactive-only, so the automatable path is a stored token (`--method stored --set token=env:RAILWAY_API_TOKEN`).

## Amendment 2026-11-18 — both D2 gates answered; cutover slice built

Evidence in [`docs/research/alchemy-railway-probe.md`](../research/alchemy-railway-probe.md), section "Cutover gate experiments". Both gates ran against the real project (read-only) and a scratch foreign project (apply):

- **Foreign takeover works.** `alchemy plan --adopt` previews the adoption of the dashboard-created project per-resource, and the apply-time ownership probe takes over a foreign-named service **in place** (output id equals the pre-existing service id; no duplicate). Service adoption is deferred to apply because the project reference is unresolved at plan time — the plan shows a tentative create. Adoption side effect to handle: with default props it mints a second public domain, so the cutover program sets `publicDomain: false` (which never deletes a domain the program does not own).
- **The `.lookup` path exists and is the better default for what the program should not manage yet.** `Project.lookup` / `Postgres.lookup` / `Redis.lookup` / `Volume.lookup` resolve real prod values read-only; a lookup never creates, adopts, writes state, or can be destroyed. It also dodges the lowercase-name hazard: the provider lowercases declared names, so the capitalized dashboard service `Postgres` cannot be matched by name.
- **`RAILWAY_GIT_COMMIT_SHA` is not set on context-upload deploys** (measured: an Effect-native Service's container env held no commit SHA, no branch, and `RAILWAY_GIT_REPO_OWNER`/`RAILWAY_GIT_REPO_NAME` empty). The D2 fallback therefore applies: the trigger-switch slice must write the commit (and repo identity) into the service environment at `alchemy deploy` time and re-source the two consumers — Sentry release attribution (`apps/server/src/instrument.ts`) and the memory producer's deployed-commit field (`docs/theory/memory.md`).
- **The cutover slice is in the repo** under `infra/` as a workspace member: the program lookup-declares the project and the two databases (destroy-proof), manages the two app services with their current GitHub source (deploy trigger unchanged), and every plan proves the databases exist through a pure `VerifyDatabases` action. The first adoption is `pnpm --filter @alfred/infra adopt`.

## Amendment 2026-11-18 — the program owns the production topology

The owner ran `pnpm --filter @alfred/infra adopt`. The apply-time probe took `server` and `web` over **in place** (output ids equal the pre-existing service ids; nothing duplicated), no domain was minted (`publicDomain: false` held), and the adopt triggered one redeploy per service, both SUCCESS with live `/health` (200) and web root (200) after. The next `alchemy plan` reads `Plan: no changes` in ~3 s, and the stack output resolved all four database lookups to real values. ADR-0108's cost verdict and ADR-0007's hosting stay untouched; the deploy trigger is still the GitHub push, so D2's re-source work remains the one open gate before a trigger switch. The version triple is catalog-pinned (owner approved the `effect` 4.0.6 → 4.1.4 bump; see the ADR-0129 amendment).

## Amendment 2026-11-18 — the deployed-commit ingest is re-sourced (the D2 gate is built)

Evidence in [`docs/research/alchemy-trigger-switch.md`](../research/alchemy-trigger-switch.md). The switch specifics are source-confirmed against the pinned provider (`alchemy`/`@alchemy.run/railway` 2.0.0-beta.87): `context:` is a local directory uploaded to Railway's `up` pipeline (mutually exclusive with `repo:`/`image:`), service variables reach the Railpack build and the runtime, no `registry:` prop exists, and the `main` contract is Effect-native only — the Elysia server moves by `context:`, not `main`.

The re-source slice is built:

- **Nothing in the API maps an uploaded deploy to a commit.** `serviceInstanceDeployV2(commitSha)` validates against the connected repo (gone after the switch), and the provider's deploy message is fixed. Railway's git variables are "provided if the deploy originated from a GitHub trigger" (docs.railway.com/variables/reference), matching the measured absence. The ADR's fallback applies.
- **Neutral variable names, not user-set `RAILWAY_*` names.** The current Railway docs state no rule against the prefix (they instruct users to set some, e.g. `RAILWAY_DOCKERFILE_PATH`), but API acceptance is unverified; the neutral name is this ADR's named fallback and costs one theory-page rename.
- **The infra program writes `ALFRED_DEPLOYED_COMMIT_SHA` + `ALFRED_DEPLOYED_REPO_OWNER`/`ALFRED_DEPLOYED_REPO_NAME` into the server environment** via the Service `env` prop (upsert-only — `syncEnv` never deletes an undeclared variable — applied before the deploy it marks needed). The value is CI's `GITHUB_SHA`, else `git rev-parse HEAD` at deploy time; a dirty-tree gate joins with the switch slice, when the uploaded working tree is what ships.
- **The consumers chain `SENTRY_RELEASE || RAILWAY_GIT_COMMIT_SHA || ALFRED_DEPLOYED_COMMIT_SHA`** (`instrument.ts`, the post-build `sentry-release.mjs`, the `@alfred/env` schema). Railway's var is fresh on every git deploy and wins while the GitHub trigger runs; the written var is the only source after the switch. `SENTRY_RELEASE` is not set on the prod server (verified, names only) — the pre-slice source was the SDK's own `RAILWAY_GIT_COMMIT_SHA` read, which the chain preserves. `docs/theory/memory.md` now cites the new variables for the producer and the name-link evidence.
- **Still open before the switch:** who runs `alchemy deploy` per release (the trigger stops being GitHub push), and then the switch itself: `repo:` → `context:` with the monorepo root as the upload (node_modules/`.git` excluded via ignore file — the tar caps are 32 MiB and 10k entries).

## Amendment 2026-11-18 — the trigger switch: context upload + a deploy GitHub Action

Evidence continues in [`docs/research/alchemy-trigger-switch.md`](../research/alchemy-trigger-switch.md). The owner chose the deploy runner: a GitHub Action on merge. The switch is built:

- **The deploy trigger is the workflow.** `.github/workflows/deploy.yml` runs `pnpm --filter @alfred/infra adopt` on every push to `main` (and manual dispatch). Runner state is always empty, so every CI deploy re-adopts the two services in place — the stateless plan was previewed read-only against the real project (4 tentative creates plus the `VerifyDatabases` action resolving), and the apply-time probe adopts by id, never duplicating. The switch itself deletes the Railway-side GitHub triggers (`serviceDisconnect`), so `alchemy deploy` is the only redeploy path.
- **Auth is environment precedence.** The CLI resolves provider credentials from the environment whenever the provider's declared contract is fully present (`alchemy/src/Auth/Resolve.ts`), so CI sets `RAILWAY_API_TOKEN` — a workspace token, stored as a repo secret — and needs no profile setup.
- **The context is the repo root, filtered by a root `.dockerignore`.** The provider reads `.dockerignore` (never `.railwayignore`, which stays for manual `railway up` runs). It excludes local-only dirs, build outputs, secrets (`.env` files never ride the upload), agent machinery, the eight tracked doc symlinks (the upload rejects any included symlink), and the drizzle per-migration snapshots — 45 of the 73 tracked MiB. `drizzle-kit migrate` reads the journal (kept) and runs from an operator checkout, never in the Railway build. The included set fits the 32 MiB / 10,000-entry caps, and the plan computes the tar and fails loud on a miss.
- **The build is two explicit Dockerfiles** (`docker/server.Dockerfile`, `docker/web.Dockerfile`), pointed at by the service `dockerfilePath` prop — the provider requires a Dockerfile inside a `context:` upload, and Railway's own detection uses it over the Railpack fallback. The server image keeps the Railpack runtime shape (one stage, dev deps included, the service `startCommand` starts it); its `ARG`s carry the Sentry build triplet plus the release commit into the build, because Dockerfile builds see service variables only through `ARG`. The web image is two stages — build the SPA, serve `dist` with Caddy on Railway's injected `PORT` (SPA fallback), because Railpack's automatic static serving is not available to a Dockerfile build. Cache mounts keyed per service id keep `pnpm install` warm.
- **The dirty-tree gate joined** `deployedCommitSha`: a local deploy from a dirty tree fails, because the uploaded working tree is what ships and uncommitted changes would go unnamed by the written commit. CI's checkout is clean by definition and supplies `GITHUB_SHA`.
- **The context walk is a tracked provider patch.** The pinned provider (`@alchemy.run/railway` 2.0.0-beta.87) enumerates a `context:` upload with `readDirectory(recursive)` — it follows symlinked directories and prunes nothing, so pnpm's cyclic `node_modules` symlinks OOM the walk before any filter runs (reproduced with plain Node on this repo; it would OOM CI too). A workspace patch (`patches/@alchemy.run__railway.patch`, pnpm `patchedDependencies`) swaps the enumeration for alchemy's own pruning walker — `walkIgnoring` + `listFileSystemDirectory`, the one `@alchemy.run/docker` hashing already uses — and rejects included symlinks by type instead of `readLink`. Upstreamed as [alchemy-run/alchemy#3496](https://github.com/alchemy-run/alchemy/issues/3496) so the patch can be dropped at the next beta.
- **The deploy wait is in the same patch.** The first context deploy measured the provider's budget: the server finished at 2m45s inside the hard-coded 150-second wait, and the web's build was still BUILDING at 2m51s when the run failed — while Railway kept building and reached SUCCESS on its own. Prod held no outage (the old deployment served until the new one went ready). The patch extends both wait sites to 60 retries × 10 s against a 600-second cap.
- **Accepted cost:** with no persistent state in CI, every push to `main` redeploys both services — including doc-only merges, which a stateful deploy would skip by hash. The Postgres state backend (D3) is the later lever if that gets expensive; it needs no new provider.
- The merge push of this slice is the first context deploy; its CI run is the acceptance evidence for this amendment.
- **Correction, same day: the web image needs its build-time variable declared too.** The slice declared the server's four `ARG`s but no `ARG VITE_API_URL`, so the web build never saw the service variable (Dockerfile builds see service variables only through `ARG`), the `.env` fallback baked `http://localhost:3001` into the prod bundle, and no browser could reach the server — the owner's sign-in broke. The fix ([PR #1793](https://github.com/99Yash/alfred/pull/1793)) adds the one `ARG`; a local build of that image carries `https://api.alfred.beauty` in the entry bundle and no `localhost:3001`. The rule: any variable a Dockerfile build reads must be declared as an `ARG` in that Dockerfile.

## Amendment 2026-11-27 — one bounded retry policy for Railway reads

`deploy-production` failed on 2026-11-27T03:11Z (run #71) when Railway's API edge reset an in-flight HTTP/2 stream (`NGHTTP2_ENHANCE_YOUR_CALM`) during the server service create. The provider turns that reset into a fatal error. In the window from 2026-11-19 to 2026-11-27T03:13Z, 7 of the 59 `deploy-production` runs on `main` ended in failure, and more than one of those runs carries the same reset signature.

- **The retry covers reads only.** `patches/@distilled.cloud__railway@1.0.0-rc.20.patch` repeats a GraphQL query that the edge resets, twice, 2 s and 4 s apart. It covers the response body read as well as the request. A mutation keeps the fail-fast path: a reset stream can still have been processed (RFC 9113 section 8.7), so a repeated create can queue a second build and a second `db:predeploy`. The patch goes away when the provider carries its own read retry.
- **An ambiguous write fails the release.** Nothing repeats `alchemy deploy`. A reset during a create stops the job with a non-zero exit, and the owner re-runs the workflow. A failed run can leave the two services on different releases (run #71 finished the web build and failed the server), so a re-run adopts both again.
- **The build-context upload is not retried.** The `/up` upload is the other reset site. Two uploads of one commit can differ while `.alchemy` runner state sits inside the upload set, so the upload waits for the transport question below. That state gap is older than this amendment.
- **Open, not patched:** alchemy ships an HTTP/1.1 dispatcher for similar resets. A trial in a scratch Railway project must show whether it prevents the upload and the GraphQL resets. Until then this read retry is the whole policy.

## Amendment 2026-11-27 — the upload replay is withdrawn; an ambiguous write stays fail-fast

[PR #1908](https://github.com/99Yash/alfred/pull/1908) added a bounded replay for the `/up` upload. Review withdrew it the same day it merged. The reason is the rule above: a replay of a write without a non-processing guarantee can queue a second deployment, and an ambiguous write fails the release. The changes below carry the review's findings.

- **The reset gives no non-processing guarantee.** RFC 9113 section 8.7 lets a client repeat a reset request only when the server guarantees it did not process it: a `REFUSED_STREAM` with `NO_ERROR`, or a `GOAWAY` whose last stream id excludes the stream. The resets seen here (`NGHTTP2_ENHANCE_YOUR_CALM`) carry no such guarantee. The review's local probe recorded Railway's server taking the full first POST body, then sending the reset before response headers; the replayed POST returned a second deployment id. Two accepted deployments can each run `db:predeploy`.
- **The old repeat gate leaked.** The patch repeated only "a reset before an answer", but the probe sent two POSTs after Railway answered 413 and then reset the body read. A `Retry-After` HTTP-date also fell back to the default wait. Both faults died with the replay.
- **The byte-identity claim was false.** #1908 justified the replay with "one commit's tarball is byte-identical". Two fresh archives of one unchanged fixture carry different SHA-256 hashes, because Alchemy's tar headers hold the current time; retries also reuse the same request body. The `.alchemy` exclusion stands on its own: the runner writes state while the deploy runs, and Alchemy state can hold values that redacted wrappers hide. Which values entered prior images stays unverified.
- **The incident evidence shows overlap, not cause.** In deploy runs #45, #51 and #72, the web failure came 26–77 ms after the server upload started, and the server upload then completed. The timing supports a concurrency trial; it cannot name the cause of the resets.
- **The upload boundary reports two states.** `Railway.DeployUploadFailed` is a confirmed refusal: Railway answered with a status it chose, the status stays the primary failure, and a lost body read rides along as the cause. `Railway.DeployUploadUnknown` is an unproven outcome: no answer reached the client, the 120-second deadline expired after submission, or Railway's 200 body was lost before it named a deployment (a 200 still means a deployment exists; only its identity is lost). No submission is repeated, so the fail-fast rule holds with typed evidence.
- **Plan and apply see one file set.** The plan hash now prunes the `.alchemy` directories the upload set prunes; a tracked input under a nested `.alchemy` otherwise changes the plan while the build loses the input. Residual: a tracked file named `.alchemy` (none exists) still reaches the plan hash.
- **The workflow reports the observed release.** The deploy job runs a report step (`if: always()`) that reads Railway's live API and prints the observed deployment for web and server, with "unknown" when the read cannot prove one. That report is the recovery basis after a stop that leaves the services on different releases. It cannot match a submission to the deployment that submission created — Railway offers no such link.
- **Automatic recovery stays closed.** It needs a Railway-supported idempotency key for `/up`, or a way to match one submission to the deployment it created; a content hash or the latest deployment id alone cannot identify one release attempt. The scratch-project trial of alchemy's HTTP/1.1 dispatcher (the dispatcher negotiates HTTP/1.1 locally; its effect on Railway's edge is unverified) stays the open transport question, and now compares HTTP/1.1 and HTTP/2 with overlapping uploads.

## Alternatives weighed

- **Keep dashboard-only (status quo).** The gap stays. Rejected because the topology is already non-trivial (6 resources + private net + two managed databases), the repo's own style is compiler-carried proofs, and the platform-switch hedge has no story without config-as-code.
- **Terraform/OpenTofu with the Railway provider.** HCL, codegen, no per-PR stage model, no local emulation; the most machinery for the smallest topology. Rejected.
- **Pulumi.** TypeScript, but a state backend + engine + provider stack is overkill for 6 resources on one platform. Rejected.
- **`railway.json` / config-as-repo-files.** Captures per-service build config but not the database/volume/private-net topology, and nothing checks it against reality. Rejected.

## Why not "nothing until Railway actually breaks"

An outage is survived by Railway, not by us — no tool helps mid-incident. What IaC buys is the *decision* to leave: the same program shape has first-class Fly, AWS, GCP, and Hetzner providers, so the hedge becomes an edit to the provider wiring plus an adopted-state migration, not a rebuild from memory. That is the only honest version of "we might switch", and it costs one program and one CLI in exchange.
