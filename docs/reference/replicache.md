# Replicache

`packages/sync` ships the client-side mutators (currently `noteCreate`) and shared key helpers. Server-side push/pull/poke endpoints live at `/api/replicache/{push,pull,events}` (see `packages/http/src/sync/`). Pokes flow over Redis Pub/Sub on `replicache-pokes:u:<userId>` channels and reach the browser via SSE.

## Adding a new synced entity

1. Add one direct entry to `SYNC_MODEL` in `packages/sync/src/sync-model.ts` — `prefix: model("prefix", schema, { key: ["id"] })`. The registry `satisfies` contract keeps the explicit prefix equal to the object key. The ordered string-valued schema fields drive typed identities, `storageKeyFor`, `storageKeyForId`, and the pull CVR id. `IDBKeys` and `SyncedEntity` derive from the same entry. No public key operation returns a bare IDB id-part.
2. Define the read schema in `packages/sync/src/schemas.ts` and export its inferred type there (must include `rowVersion: number`). Register the schema in the `SYNC_MODEL` entry as the entity's owning schema.
3. Add `<entity><Action>Client` mutator + zod arg schema in `packages/sync/src/mutators/<entity>.ts`, register both in `mutators/index.ts` (`clientMutators` + `mutatorArgsSchemas`).
4. Add the matching server-side mutator as an `export async function` in `packages/http/src/sync/write/<domain>.ts` (create the file if the domain is new), and register it as one shorthand row in the `serverMutators` literal in `packages/http/src/sync/write/index.ts`. Write against the supplied `tx` (so it commits inside the push handler's outer transaction) and bump `row_version`. Pokes fire generically from the push handler after commit.
5. Add a fetcher as `export const fetch<Domain> = syncEntity(SYNC_MODEL.<prefix>, { versionQuery, loadQuery, map })` in `packages/http/src/sync/read/<domain>.ts` (create the file if the domain is new), and register it under the same prefix in the `ENTITY_FETCHERS` literal in `packages/http/src/sync/read/index.ts`. The read is two stages over one authored membership:
   - `versionQuery(tx, userId, readAt)` selects the visible set projected down to the model's identity columns plus `rowVersion`. That narrow `Version` type is what `parsePullVersion` needs, not a limit on the select list: when membership is decided in JS (an unreviewable-fact test, an internal-slug test), add only the columns that test reads, and the parser ignores every other key. `Version` is constrained to the model's identity plus `rowVersion`, so a projection that cannot address a row is a compile error. Alias a non-`id` column to the model's identity name (`emailTriage.sourceThreadId` → `threadId`) so the changed-row selector never has to split a joined CVR id.
   - `loadQuery(tx, userId, changedVersions, readAt)` selects full values for the changed projections only, over the same membership. `syncEntity` calls it only when something changed, and passes the same `readAt`, so both stages agree on any window boundary. Share one small predicate for an unbounded set. For an ordered limited set, share one visible subquery that owns the user guard, the order and the limit, and let both stages join to it. Apply the changed-id restriction *outside* that shared set: restricting changed ids inside the limit would let them push visible rows out of the bounded set and would hand the two stages different memberships.
   - `syncEntity` derives `{ id, storageKey, rowVersion, serialized }` from the bound model for each loaded row (`pull.ts` only consumes that row shape), and reports unchanged membership separately as `{ id, rowVersion }` so `pull.ts` can acknowledge a row the client already holds without reading or re-validating it. The mapper stays in the domain file; throw `SerializationError` from `read/entity-row.ts` to skip a row instead of failing the pull. A changed row that fails to load, map, or parse, and a malformed version projection, are all reported in neither list, so they keep no acknowledged version, the delete loop removes any id the previous record still holds, and the next pull retries them. The CVR snapshot shape (`Partial<Record<IDBKeys, ClientViewMap>>`) is generic — no `cvr.ts` change needed.
