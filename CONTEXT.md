# Alfred — Shared Vocabulary

The single glossary of the load-bearing terms. Refine in place when usage drifts; don't re-litigate in chat.

**What belongs here:** the definition of a term and the non-obvious reason it is shaped that way. **What does not:** restated implementation detail, exact thresholds, amendment chronology, or build sequencing. Those belong to the code, the owning ADR, or the plan — a glossary that mirrors them rots independently of them. When a term names a constant, name the constant rather than its current value.

A term that describes something **not yet built** must say so. Design recorded as fact is the failure mode this file is most prone to.

Cross-references: [`decisions.md`](./decisions.md) (snapshot table + ADR index; the ADRs live one per file in [`docs/decisions/`](./docs/decisions/)), [`CLAUDE.md`](./CLAUDE.md) (operational guide).

## Cross-cutting invariants

These three bias every subsystem below. Read them first.

**Propose / dispose.** The boundary that keeps extraction safe: the LLM/boss _proposes_ candidate keys and work-signals (fallible); a deterministic reducer _disposes_ authoritative state. A hallucinated key resolves to nothing — it cannot fake a state. (ADR-0062/0063)

**Absence never closes.** A loop closes only on a _positive_ terminal signal (e.g. a PR `merged`); a missing signal — no webhook, unknown key, API gap — leaves the loop **live**, never inferred-closed. The ADR-0048 source-availability contract, pinned by a contract test. (ADR-0048-D, ADR-0062)

**Demote, never bury.** A false "needs you" is recoverable noise; a false "doesn't need you" is near-fatal. Ranking demotes; it never re-stamps an immutable triage category and never silently drops. (epic #218)

## Core domain

**Skill.** A markdown body + frontmatter the agent mounts into its system prompt. Activated by `@skill:slug` in a brief or chat. Authoritative storage: `skills` + `skill_revisions`. ADR-0017.

**Workflow (row).** A row in the `workflows` table. Holds trigger spec, brief, optional steps DAG, status, allowed-integrations, HIL gates. Source of truth for the _settings UI_ and the _trigger dispatcher_ — not for execution shape.

**Workflow (code).** A `Workflow<S>` object passed to `registerRecipe()` at server boot. Source of truth for _execution_ (steps, initialState, dedupKey). Built-ins live as both a row AND a code object; user-authored live as a row only — registry misses route through a single shared `userAuthoredBriefWorkflow` sentinel only after the checked run resolver verifies `workflows (userId, slug)` exists and `is_builtin=false`. The requested slug, not the sentinel slug, stays the join key on `agent_runs.workflow_slug`; execution shape is shared.

**Run.** One execution of a workflow. Stored as one row in `agent_runs`. Joins back to the workflow via `agent_runs.workflow_slug`. There is no separate `workflow_runs` table — `agent_runs` covers status, timing, cost attribution.

**Brief.** Two scopes, both legitimate:

1. _Workflow brief_ (ADR-0017): the user's natural-language description of what the workflow should do. Stored on `workflows.brief`.
2. _Sub-agent brief_ (ADR-0026): the initial transcript handed to a spawned sub-agent. Stored as the first message of a child `agent_runs.transcript`.
   When ambiguous, qualify: "workflow brief" or "sub-agent brief."

**Trigger.** Discriminated union on `workflows.trigger.kind`: `cron` | `event` | `manual` | `on_signal`. The dispatcher consults `status='active'` before enqueuing a run.

**HIL gate.** A step id listed in `workflows.hil_gates`. The runtime parks the run on `wakeCondition.kind='hil'` when entering the step; user approval flips it back to `runnable`. Only meaningful with explicit `steps`. For brief-only workflows (m13+), HIL is driven by the **user action policy** instead — see below.

**User action policy.** Per-user row in `user_action_policies` storing `default_mode` (`autonomy` | `gated`), `integration_rules` jsonb keyed by integration slug, and `approval_notify_delay_ms`. The tool dispatcher consults it on every tool call; `gated` results land as staged actions awaiting human decision. Default at signup: `gated`, with `system.*` tools seeded to autonomy. The row is **Replicache-synced** (a single entity keyed by `userId`; the web derives each integration's mode from `integration_rules[slug].mode ?? default_mode`), so a policy mutation must invalidate **twice** — bump `row_version` for the web pull _and_ `publishPolicyBust(userId)` for the in-process dispatcher cache across instances. Missing either half leaves one reader stale. ADR-0034.

**Policy mode.** `autonomy` (execute immediately) or `gated` (stage for HIL approval). Resolution at dispatch: **run-scoped auto-mode override → per-tool override → per-integration mode → user default**. Both modes are const-narrowed string unions from `@alfred/contracts`, never open strings. **`gated` gates reads too** — there is no read/write split and no carve-out for the trigger's own document: under a gated integration the boss stages even `gmail.read_message`, including reading past the inline `<trigger_event>` excerpt of the email that fired the run. `riskTier` is a UX hint, never a gating shortcut. The excerpt is the ungated baseline; per-tool overrides are the deferred relief valve. ADR-0034.

**Chat.** The interactive message surface and the module that owns it. The module owns threads, messages, turn admission, attachments, stop behavior, context assembly, summaries, and compaction. The name is `chat`, not `conversations`: the module is chat-only, and the schema (`chat_threads`, `chat_messages`), the contracts, the sync adapters, and the web routes already use `chat`. This reverses the module-structure plan's Phase 6 rename for this module only. See ADR-0089 amendment 2026-08-16.

**Auto mode (chat).** The composer's `autoMode` toggle ("auto mode" / "manual review", `dimension-chat-thread.tsx`). "Auto mode" = a per-thread blanket `autonomy` override captured onto each run and applied at the top of policy resolution; "manual review" = honor the durable `user action policy`. **Server-authoritative** once a run exists (the gate runs server-side and background runs have no browser). The eventual thread/conversation row stores the per-thread default; `localStorage`/global store holds only the new-chat default toggle position (default **manual**) until first send persists it. No riskTier carve-outs — auto mode is full autonomy for the thread (ADR-0034 alt-(f)). Wiring rides the m13 chat→runtime bridge. ADR-0034 amendment 2026-05-27.

**`@alfred/contracts`.** New tiny package (sibling to `@alfred/sync`, `@alfred/env`) holding cross-boundary types + const tables: `INTEGRATION_SLUGS`, `POLICY_MODES`, per-integration `*_ACTIONS` lists, derived `ToolName`, future attribution/signal kinds. Zero Node deps; importable from `packages/db`, `packages/http`, `apps/web` without runtime-bundle leaks. Pure named exports + `as const`; no side effects at import time.

**Tool name.** Canonical form `${IntegrationSlug}.${ActionSlug}` — both halves are const-narrowed unions from `@alfred/contracts`. Per-integration action lists compose via `INTEGRATION_ACTIONS` into a single `ToolName` template-literal type. `system.*` is for internal tools such as exact discovery/loading, current time, and scratchpad operations. Schema columns and dispatcher signatures use `ToolName` exclusively; no open strings, no `string & { __brand }` shortcuts.

**Action staging.** Row in `action_stagings` — one per proposed tool call, gated or autonomy. Gated rows park the run on `wakeCondition.kind='hil'` with `approvalId=stagingId` until user decides (approve / edit / reject); autonomy rows transit `pending → executed` in ms. Idempotent on `(run_id, tool_call_id)` for crash-resume. Carries `row_version` for Replicache, `risk_tier` for UI/email snapshots, and `proposed_input_hash` for retry suppression. The canonical audit record for "what did Alfred try and what happened?" The Replicache fetcher enriches each synced row with read-only derived provenance — workflow name, a **display-only narrowed `trigger`** projection that deliberately never carries the raw payload or document ids, and a server-truncated brief — so the approval card renders "what is this / where did it come from" without a second fetch. ADR-0034.

**Approval debounce.** When a gated staging row lands, SSE pokes the web UI immediately; a BullMQ delayed job is also scheduled using `user_action_policies.approval_notify_delay_ms` (default 5min). If the user decides in-app before the delay fires, the job is removed and no email goes out. If the job fires with the row still `pending`, it calls `notify({ userId, kind: 'approval', idempotencyKey: 'approval:' + stagingId, ... })`, sending one email per staging row. Tracked by `action_stagings.notify_after_at` (scheduled fire time) and `notified_at` (actual fire time). ADR-0034.

**Approvals surfaces.** Two distinct read models. **(1) Live pending queue** (`/approvals`): Replicache-synced (`status='pending' AND requires_approval`), bounded (rows auto-expire at 24h), so pagination + filtering (by integration + risk) happen **client-side** over the synced collection — filter state lives in URL search params; "pagination" is windowing, not server paging. No server query endpoint for this surface. **(2) History** (resolved actions — approved/rejected/expired): _not_ synced, grows unbounded, so it's a separate **server-paginated + filterable** read model (`GET /approvals?status=&integration=&risk=&page=`). **Deferred** (grilling 2026-05-31) — built when the History tab lands. Decided during the Phase 5 approvals-UI polish.

**Rejection contract.** When the user rejects a staged action, the boss's resumed turn receives a structured tool-result: `{ status: 'rejected_by_user', toolName, proposedInput, reason, retryPolicy: 'do_not_retry_identical' }`. The dispatcher _enforces_ the retry policy: a second stage attempt with the same `(run_id, tool_name, hash(proposed_input))` synthesizes another rejection without re-staging or re-emailing. Reject UI exposes two affordances: "Reject and continue" (default) and "Reject and end run" (triggers `cancelRun(runId)` with `reason='cancelled_by_user'`). Reason text is required. Staging cards render a banner with the most recent rejection for the same `(user_id, tool_name)` if one exists in the last N days — so the user (and the boss, on resume) sees why a similar action was rejected before. ADR-0034.

**Tool risk tier.** Const-narrowed enum at tool registration time, declared in `@alfred/contracts`: `no_risk | low | medium | high`. Pure UX hint at v1 — the dispatcher reads only `user_action_policies`, never `riskTier`. Drives integration-card summaries ("Gmail — 12 tools (4 high, 5 medium, 3 low)"), staging-card badges, and email subject prefixes. Staged rows snapshot the risk tier so old approvals don't change copy after a registry edit. Authors classify on registration; trust-the-author at v1, custom lint rule when the registry grows past ~30 tools. ADR-0034.

**User context.** Compact, queryable runtime profile about the user: bio, preferences, current company/projects, important people, known contacts, relationship facts, and eventually saved third-party dossiers. Source of truth stays in Postgres (`user_facts`, `user_preferences`, `entities`, `entity_relations`, `memory_chunks`, later `person_profiles`); Redis may cache a derived slice such as `alfred:user-context:{userId}:v1` for fast reads, but cache loss must only cause a rebuild. Boss/sub-agents access it through `system.read_user_context`, an always-available system tool rather than a loadable `memory` integration. ADR-0042 amendment.

**Write surface.** The set of write/mutating tools (`gmail.send_draft`, `calendar.create_event`, `docs.create`, …) an integration exposes. First-class as of ADR-0043 — _not_ walled off architecturally. Authorization is a three-layer composition: tool registry (does the tool exist?) → declared tool surface bounded by `workflows.allowed_integrations` and connected credentials → user action policy (`autonomy | gated`, default `gated`). As of ADR-0053 the middle layer is **dispatch-enforced**, not exposure-only: `dispatchToolCall` hard-checks the cap plus scope-aware connection health before executing, closing the hole where a qualified call bypassed it. Safety lives in the policy default, not in architecture. ADR-0043 + ADR-0053.

**Publishing posture.** Google OAuth consent screen runs in **Production, deliberately unverified** (not Testing). Avoids Testing's 7-day refresh-token expiry for non-profile scopes; refresh tokens are still revocable and subject to Google's normal token limits. The trade is the unverified-app warning + 100-new-user cap, both fine at single-tenant scale. We never submit for verification, so "Google won't approve it" doesn't apply on this path. ADR-0044.

**Scope tier.** Google's three-way classification that sets the verification bar: **non-sensitive** (`drive.file`, `openid`, `email` — no sensitive/restricted scope review), **sensitive** (`gmail.send`, `calendar.events`, Workspace edit scopes — app verification, no security assessment), **restricted** (`gmail.modify`, full `drive` — restricted verification **+ annual security assessment if restricted data is stored/transmitted through servers**, the real public wall). Alfred requests least-privilege, extends freely into sensitive, and takes exactly one restricted scope (`gmail.modify`) because reading mail is the product. Granted set tracks the registered tool set. ADR-0044.

**Multi-tenant-capable / single-tenant operation.** Alfred is _architected_ multi-tenant (per-user `integration_credentials`, `user_action_policies`, `user_id` partitioning) but _operated_ as one tenant. "Single-user" (ADR-0001) is the current operating mode, not an architectural ceiling — going public is a verification submission + ADR-0009 allowlist removal, not a rewrite. A self-host-per-user model (each user = their own GCP project) is the open third path that avoids a centralized public OAuth client and its restricted-scope security assessment. ADR-0044.

## Compaction

**Transcript compaction.** Executor step inserted between `dispatch-tools` and the next `boss-turn` when the token count crosses `compactionThresholdTokens` of the **smaller** of the boss and compactor context windows — the `min()` is load-bearing, because the two windows are asymmetric and overrunning the _compactor_ is the failure mode. The `compactor` route is Claude Sonnet 4.6 with thinking disabled (deliberately separate from the `cheap` route), with the `compactorFallback` Gemini route behind it; a pre-call guard fails over, or raises `compactor_input_too_large`, when the prior slice exceeds the compactor's window. The stable boss system prompt and tool definitions stay outside `agent_runs.transcript` as `AlfredAgent.turn()` inputs; the compactor preserves the in-flight tail (last assistant message + its tool calls + results) **verbatim** and compresses everything older into the run handoff. Exposed as a reusable primitive: `compactTranscript` in `packages/assistant/src/execution/run-compaction/` **owns model selection and window enforcement**, so a caller supplies only the slice and the threshold trip-wire and cannot forget the policy. Sub-agents do not compact (they fail back to the boss for re-decomposition, ADR-0026); non-looping background workflows — triage, briefing, cold-start — never reach the threshold. ADR-0035.

**Run handoff.** Structured XML `<run_summary>` emitted by the compactor, replacing older transcript content. Sections: `goal`, `user_directives`, `decisions`, `actions_completed`, `actions_rejected`, `actions_failed`, `sub_agent_findings`, `pending_followups`, `key_entities`. A third ephemeral `cacheControl` breakpoint goes after the `<run_summary>` so subsequent turns hit a stable cached prefix until the next compaction. ADR-0035.

**User directives vs decisions.** Two distinct handoff sections by design. `<user_directives>` = pragmatic, mid-run intent statements that bound the agent's future behavior ("trust gmail for the rest of this conversation"), preserved verbatim. `<decisions>` = epistemic, facts/preferences/constraints learned during the run ("Alice is the manager"). The compactor's system prompt enforces "do not paraphrase under `<user_directives>`" — paraphrasing introduces drift on intent grants. **Supersession:** when a later directive revokes/overrides an earlier one, both are kept verbatim in chronological order and the earlier is tagged `<directive superseded="true">` — the marker is metadata (not a paraphrase, so "verbatim" holds), and the boss acts only on non-superseded directives. ADR-0035 (+ amendment 2026-06-01).

## Scratchpad

**Run scratchpad.** Per-run K/V store for sub-agent findings + boss-promoted shared state. **Redis** is the live store during the run (keys `alfred:scratch:{runId}:{zone}.{path}`, 30-day TTL). **Postgres** receives a per-key snapshot via `agent_run_context` at the executor's terminal step (success / failure / cancel), idempotent via `ON CONFLICT (run_id, key) DO UPDATE`. Crash-resume of a lost scratch entry mid-run = re-execution of the producing step (ADR-0014's idempotency). Per-zone single-writer enforced at the dispatcher: only `sub_a` writes `scratch.sub_a.*`; only the boss writes `shared.*`. ADR-0036 (amends ADR-0016).

**`shared.*` vs `scratch.{subId}.*`.** Two namespaces inside the run scratchpad. `scratch.{subId}.*` is sub-agent advisory state (unvalidated; the sub-agent owns it). `shared.*` is boss-promoted canonical state (validated; only the boss writes). Sub-agents read both but write only their own zone. Cross-pollination across sub-agents flows through `shared.*` — the boss is the gate. ADR-0016 + ADR-0036.

**Active tool surface.** `agent_runs.state.activeTools: ToolName[]` is the exact run-local model and execution surface; global registry membership is server capability only. Dispatch rejects disallowed tools before activation; an allowed-but-inactive call activates its exact schema and bounces the model to reissue, rather than validating schema-blind arguments. The always-visible **kernel** is whatever declares `availability: { surface: "kernel" }` in `packages/assistant/src/tool-runtime/internal/tools/system.ts` — the discovery pair (`system.search_tools`, `system.load_tool`) plus the capabilities the chat/boss prompt names by name. The rule, not the count, is the invariant: **a tool the prompt advertises must be eager**, or its first use pays a search/load dance _and_ a mid-run prompt-cache bust. The kernel is returned unfiltered, so the `activeTools → ToolSet` projection (`buildSdkToolSet`) drops what the caller cannot invoke — `requiresLiveChat` and `callers` (boss-only) — which is why a background brief and a sub-agent run each see a smaller kernel than live chat does. Every other system capability is discovered and loaded exactly. ADR-0053 amendments / #407 / #411 / #412.

**Connected summary.** A run-start snapshot of connected ∩ allowed integrations, rendered into the boss/chat preamble as one line per integration (`slug — actions — short desc`, with `(needs reauth)` for unhealthy credentials). In v1 it is **grounding copy**, not the only visibility channel: full schemas for usable connected ∩ allowed tools are declared eagerly. Skip empty-action stub integrations. Source: `integrationCredentials` + slug-specific scope checks. Snapshot into run state; the system resolver only concatenates the frozen string. ADR-0053.

**Connection health.** Per-integration usability, from `integrationCredentials.status` (`active` vs `needs_reauth`/absent) **plus slug-specific OAuth scopes**. One shared helper (`packages/assistant/src/connections/availability.ts`) answers "is this integration usable right now?", consumed by the connected summary and the dispatcher gate, returning a structured `not_connected` / `needs_reauth` code instead of a cryptic provider failure. Google fan-out is scope-aware: a Calendar-only Google credential does not make Sheets/Slides/Drive usable. Multiple Google rows reduce by "any active row with the required slug scopes wins; otherwise needs_reauth if a relevant row exists but is unhealthy/missing scopes; otherwise needs_connect." ADR-0053.

**Dispatch floor.** Plain code in `dispatchToolCall` that, before execute, (a) resolves bare→qualified tool names and refuses to guess when a bare name collides across integrations, and (b) **hard-enforces** `allowed_integrations` plus scope-aware connection health, closing ADR-0043's exposure-only cap hole. The result returned to the boss is always an actionable `{ status, message, … }` envelope — the status vocabulary (`unknown_tool`, `inactive_tool`, `invalid_input`, `not_allowed`, …) lives in `packages/assistant/src/tool-runtime/dispatch.ts`. No v1 auto-activation path is needed, because connected ∩ allowed tools are already declared eagerly. ADR-0053.

**Run grounding.** The run-start snapshot string the `AlfredAgent` system resolver concatenates into the boss/chat system prompt — cache-stable by construction, with no live DB or health reads mid-turn (ADR-0053 + ADR-0026). **Members:** _date grounding_ (today's date + `IanaTimezone`, via `formatDateGrounding`), the _connected summary_, and _standing instructions_ — ambient because they bias every turn. **Standing instructions are dual-delivered:** ambient here for boss/chat, and _pulled_ by the non-boss pipelines (triage `classify`, briefing `gather`) through a dedicated read path. Those pipelines never see run grounding, so a directive that must bias them is consulted at classify/gather time rather than injected into a prompt they don't read — see _Suppression standing instruction_. Facts and people are **not** ambient; they stay pull-on-demand via `system.read_user_context`. So the boss perceives the world through exactly three channels: **run grounding** (ambient prompt facts), **declared tool schemas**, and **`system.read_user_context`** (durable memory). Tool-selection recovery — the dispatch-floor `unknown_tool` envelope — is a recovery concern, not grounding.

**Builtin vs user-authored.** `workflows.is_builtin = true` for alfred-curated workflows seeded from the repo (immutable except `status`); `false` for user-authored (full CRUD). Same table, same toggle UX.

## Runtime primitives

**Tick.** A BullMQ repeatable that fans out per-user. Existing pattern: `briefing.tick` (hourly, `packages/assistant/src/briefings/repeatable.ts`). m12 adds `workflows.tick` (every minute, generic) per ADR-0027.

**Dispatcher.** The piece that turns a trigger into a `createRun` + `enqueueRun` call. Exists implicitly per-feature today (e.g. the briefing tick handler); m12's `workflows.tick` is the first generic dispatcher. Cron fires via the tick; `event` fires via the `emitEvent` bus (below).

**Event bus (`emitEvent`).** The generic `event`-trigger dispatcher (m13 Phase 8a). `emitEvent({ userId, source, type, eventId, payload })` queries `workflows WHERE status='active' AND trigger.kind='event' AND trigger.source=… AND trigger.type=…` and `createRun`s each match with a uniform `input: { documentId, reason, source, type }` + `trigger: { kind:'event', source, type, eventId, payload: { documentId, reason } }`. **One dispatch path:** the email-triage builtin is matched like any other event workflow — its old hardcoded enqueue helper is gone, and the Gmail ingestion worker calls `emitEvent` per freshly-inserted doc instead. Triage's `initialState` still reads `input.documentId/reason` (run behavior byte-identical); only its dispatch trigger changed from imperative to query-matched. ADR-0047 (extends ADR-0027).

**Event source + type.** One record `EVENT_SOURCE_ENTRIES` in `@alfred/contracts`, keyed by source slug; each entry names its `producer` (`in_process` or `inbound_webhook`) and its event-type tuple, and `EVENT_SOURCES`, `EventSource`, `InboundEventSource`, and `EVENT_TYPES_BY_SOURCE` are derived from it (ADR-0097, amends ADR-0047's closed enum). Shipped set: `gmail.message_received`, `gmail.documents_ingested`, `google.oauth.callback.completed`, `learn-skill.completed` (in-process), and `github.{pull_request,push,issues,pull_request_review}` (inbound). An `inbound_webhook` entry must have an `InboundSourceDescriptor` in `packages/assistant/src/connections/ingress/`, keyed `Record<InboundEventSource, …>`, so an entry without a descriptor does not compile; deliveries arrive on `POST /webhooks/inbound/:source`, are verified over raw bytes, stored as one `event_receipts` row, and published on the bus by the `ingress.deliver` job. An entry may land one milestone ahead of its producer (a typed const, unlike the `on_signal` _subscriber_ that was deferred), but no source ships without a committed producer. Which sources a user may subscribe a workflow to stays the curated `AUTHORABLE_EVENT_SOURCES` subset (`gmail` only); the registry lifts the enum ceiling, not the security ceiling. The `webhook|ingest|manual` breadcrumb rides `trigger.payload.reason`, not the type. `trigger.filter` stays on the schema for forward-compat but the v1 dispatcher does **not** evaluate it (API rejects non-empty `filter` writes, like `steps`); the brief-only boss decides relevance itself. ADR-0047.

**`<trigger_event>` message.** For an `event`-triggered brief-only run, the sentinel's `initialTranscript` appends a `user`-role `<trigger_event>` message after the brief carrying a **bounded** trigger context resolved from `documents`: ids, source/type, title/subject, sender metadata, authored time, URL, and a capped raw-content excerpt. Inbound third-party content is never blindly inlined in full — if the boss needs more, it calls the registered provider read tool (e.g. `gmail.read_message`). User-authored outbound content may be inlined in full, because Alfred created it. Raw bodies are **not** persisted in `agent_runs.trigger.payload`; the payload stays a pointer + breadcrumb. A missing or deleted document degrades to an unavailable-trigger message instead of failing run creation. Event runs auto-seed the trigger source's exact registered tools into `activeTools` (∩ `workflows.allowed_integrations`, the same cap rule as `@`-mentions), so a Gmail-triggered workflow has Gmail tools without a redundant `@gmail`. ADR-0047.

**Event idempotency (bounded).** No DB unique index on `eventId`. The Gmail worker fans out only _freshly-inserted_ `documentIds` (insert-once → emit-once) behind the webhook handler's existing 30s TTL dedup, and `emitEvent` does a best-effort non-terminal duplicate check on `(userId, workflowSlug, source, type, eventId, reason)` before creating a run so a retried ingestion job does not normally double-fire. This check has a race and is not a guarantee. A hard `(user_id, workflow_slug, eventId)` constraint is explicitly rejected — triage reuses `eventId=documentId` across `reason`s (e.g. a later reply-retriage), which such an index would wrongly block. ADR-0047.

**`next_run_at`.** Denormalized timestamp on the `workflows` row. Recomputed (via `cron-parser`) at exactly two moments: when `trigger`/`status` mutates, and inside the tick after a successful `createRun`. The tick query is an index lookup, not a scan. ADR-0027.

**`trigger` (on `agent_runs`).** First-class jsonb column on the run, mirroring `workflows.trigger.kind` plus per-kind metadata (`scheduledFor`, `eventId`, `payload`, `signalName`). Source of truth for "why did this run fire?" Replaces ad-hoc `metadata.triggeredBy` stuffing. ADR-0027.

**Scheduled-instant jobId.** BullMQ `jobId = workflow:{workflowId}:scheduled:{nextRunAtIso}`. Idempotency primitive: a retried tick is a no-op via BullMQ's native dedup without consulting Postgres. ADR-0027.

**Per-turn LLM driver.** `AlfredAgent` (ADR-0026, `packages/ai/src/agent.ts`). One `turn()` call = one LLM round-trip = one `api_call_log` row. Composes with the durable runtime; not yet wired into any agent_run.

**Call role.** `CallRole` union (`packages/ai/src/metering/types.ts`): `'compactor' | 'boss' | 'sub_agent' | 'triage' | 'briefing' | 'cold_start' | 'memory_extraction'`. Set on `attribution.role` when calling `meteredGenerateText` / `meteredGenerateObject`; surfaces on `api_call_log.request_meta.role` so a single run's spend can be split between agent surfaces (boss vs sub-agent vs compactor) without adding a column. Phase 7 wires all three boss-workflow roles end-to-end: `'boss'` and `'sub_agent'` on `AlfredAgent.turn()` inside `userAuthoredBriefWorkflow`, `'compactor'` on `compactTranscript`. The remaining roles (`'triage'`, `'briefing'`, `'cold_start'`, `'memory_extraction'`) are typed but not yet wired at their call sites — that's a separate small PR. Query with `request_meta->>'role'` in cost rollups.

**Brief-only execution shape.** Two named executor steps that ping-pong: `boss-turn` runs exactly one `AlfredAgent.turn()` (preserves ADR-0015's one-turn-one-`api_call_log` invariant); `dispatch-tools` calls `dispatchToolCall` for each returned tool call, appends results to the transcript, and either returns `next: 'boss-turn'` or `interrupt` if any call staged for HIL. Compaction (Phase 7) slots in as a third named step. The shared code-side `Workflow<S>` handles every user-authored brief — the slug on `agent_runs.workflow_slug` distinguishes runs, not their execution shape.

**System-tool dispatch contract.** `system.*` tools are registered with the same `liveTool` factory as integration tools, but the dispatcher applies a **structural autonomy override**: `if (integration === 'system') policyMode = 'autonomy'`, ahead of the `user_action_policies` lookup. State-changing system tools such as `spawn_sub_agent` take the full dispatcher path; chatty no-op-side-effect scratchpad tools get a fast-path that skips staging. Tool `execute` remains pure. `system.load_tool` returns an exact successful name, and the `dispatch-tools` step applies that bounded effect to `activeTools` before the executor's atomic state commit. `system.load_integration` is retired; integrations remain auth/workflow filters, never the model-visible activation unit.

## Voice & output

**Agent output purpose.** A required, closed classification of model-authored output: `assistant_response`, `audience_content`, `source_faithful`, or `internal`. The purpose selects presentation defaults, which is what keeps low-level model and metering APIs from having to know anything about Alfred's product voice.

**Voice policy.** The typed `default | none` presentation choice derived from an agent output purpose, with an explicit override for exceptional calls. Custom personas and audience guidance stay in validated request context rather than being promoted into a generic system-prompt constructor.

**Mechanical voice sanitization.** Field-aware deterministic cleanup applied at an owning stream or typed-output boundary (`sanitizeVoice` / `createVoiceStreamSanitizer`). Deliberately separate from prompt composition, so quotations, code, URLs, identifiers, citations, and exact-copy content are not transformed indiscriminately. The prompt asks for the voice; the sanitizer is what enforces it.

## Authoring shapes

**Brief-only workflow.** `steps = null`, `brief != null`. Runtime: a single `AlfredAgent`-driven loop with a stable boss system prompt, the workflow brief as the first user transcript message, and exact tools seeded/preloaded/grown within `allowedIntegrations`. m12 stored and dispatched these but did not execute them; m13 added the sentinel workflow + tool dispatch + `AlfredAgent`→runtime bridge, and #411/#412 replaced integration loading with exact search/load.

**Explicit-DAG workflow.** `steps != null`. Runtime executes deterministically; node kinds: `run_skill | tool_call | llm_call | agent_run | condition | parallel | loop | hil_approve`. The Zod schema exists; runtime support for these node kinds is partial (only `agent_run` is implicit via the executor; the rest are unbuilt).

**Hybrid workflow.** Explicit DAG with embedded `agent_run(brief)` nodes — deterministic outer, LLM-decided inner. Forward-compatible; not v1.

## Privacy posture

**Content-at-rest posture.** No app-layer encryption on user content. The layers that stand in: vendor at-rest crypto on Railway managed Postgres/Redis/object storage, and the fact that `documents.raw` is **not persisted** — re-extraction means re-fetching from the provider. Revisit when a real second-hand party touches the data: a contractor, an analytics pipeline, a backup-export workflow, a compliance regime. ADR-0038.

**Embedding-inversion gap.** `chunks.embedding` is plaintext by design — encrypting it kills pgvector indexing. Published inversion attacks can reconstruct text from vectors plus the embedding model alone. Documented and accepted; the only defense is "trust your embedding provider," which is contractual. ADR-0038.

**Log redaction (central path list — built).** ADR-0038's `SENSITIVE_LOG_PATHS` const lives in `@alfred/contracts` (`log-redaction.ts`), and every sink pulls from it: Pino's `redact` config (`@alfred/logging`) reads the table directly, and Sentry's `beforeSend` / `beforeBreadcrumb` hooks (`apps/server/src/instrument.ts`) run events through `redactSensitiveLogPaths`, which interprets the same paths. Adding a path to the table covers all sinks at once. Alongside the path list, `redactSecrets` (`packages/contracts/src/errors.ts`) scrubs secret-shaped text, `redactCredentialUrl` strips credentials out of URLs on the fetch path, and the `@alfred/http` rule "never log full error objects" stays review-enforced.

## Attachments

**Content format.** The coarse byte-format class a `degrade-text` upload belongs to — `pdf | document | spreadsheet | text` (`contentFormatValues` in `@alfred/contracts`). The name list and the MIME → format map (`INGEST_POLICY`) live in contracts because the browser composer validates against them; the extraction-side owner of "how a format's bytes become text, and what each door's limits are" is the `FORMAT_REGISTRY` + `DOOR_LIMITS` pair in `@alfred/extraction` — tables whose literal + `satisfies` pins make a format missing from either side a type error. A new format is one contracts edit, one registry entry, and one limits row; nothing else changes. ADR-0091.

> **Designed, not built.** ADR-0039's attachment ingestion pipeline is design, not shipped state: there is no `attachments` or `attachment_pages` schema in `packages/db/src/schema/`, and no doc-extraction queue or worker. Chat file uploads (ADR-0065) are a **separate, shipped** path that degrades files at ingest — they do not use any of the vocabulary below.

**Attachment.** A non-text payload arriving alongside a document — PDF, image, spreadsheet. Modeled as its own row in `attachments` (sibling to `documents`, not a row in it), linked back via `parent_document_id`. Carries identity (mime type, filename, size, page count), extraction status, and binary location. Drives a distinct ingestion path because its content shape (typed segments, pages, figures) doesn't fit `documents`'s "flat text body" assumption.

**Attachment page.** One row per page of an attachment in `attachment_pages`. The citation anchor — when the agent surfaces "from receipt.pdf, page 4," it's referencing one of these. Holds the page's concatenated `extracted_text` (for "summarize this page" without rejoining chunks) and an `asset_inventory` jsonb. Page = 1 for standalone image attachments.

**Typed segment / segment `kind`.** Each chunk derived from an attachment carries a `kind`: `text | table | figure_caption | heading | footnote | list`. Drives chunking rules (tables never split mid-row; headings become standalone chunks AND populate `parent_section` on subsequent siblings) and powers retrieval queries that want a specific element type ("find the table on page 3").

**Asset inventory.** Per-page jsonb on `attachment_pages`: `{ tableCount, figureCount, footnoteCount, hasImages, hasLinks, headings: string[] }`. Counted at extraction time. Lets retrieval answer "what attachments have charts" or "which page has the financial breakdown" without re-reading every chunk.

**Doc extraction.** The pipeline that turns a binary attachment (PDF or image) into typed segments + page inventory. Implemented as a Claude call with `document`/`image` content type, prompt-shaped to emit the canonical segment JSON. Metered as `attribution.kind = 'doc_extraction'` so cost rollups bucket it apart from LLM turns / web search / embeddings. Per ADR-0021's vendor alignment and the cost calculus at single-user scale. ADR-0039.

**`doc-extraction-runs` queue.** Dedicated BullMQ queue for attachment extraction, isolated from `ingestion-runs` so Anthropic latency/cost doesn't bleed into Gmail polling. Jobs: `attachment.extract { attachmentId }` (primary) + `doc-extraction.sweep` (hourly repeatable for stuck/failed rows). Worker concurrency 5, 3 attempts, 30s exponential backoff. Terminal failure flips `attachments.extraction_status='failed'` with `last_error` populated — the row IS the dead letter. ADR-0039.

**Attachment cost gates.** Four gates bound extraction spend: (1) MIME allowlist at enqueue (`pdf|png|jpeg|heic|webp`), (2) 20MB size cap at enqueue, (3) 50-page truncation at extraction time (`truncated_at_page` flagged), (4) $5/day per-user soft cap via env `ALFRED_DOC_EXTRACTION_DAILY_BUDGET_USD` — over-budget jobs `moveToDelayed(nextMidnight())`, not lost. Skipped attachments create a row with `extraction_status='skipped'` + `skipped_reason` so the UI can show them honestly. ADR-0039.

**Attachment binary lifecycle.** Binaries land in the Railway bucket on ingest and stay forever — independent of Gmail message retention. Gmail deletion does not cascade to the bucket or the chunks. A future explicit "forget this" UI handles real deletion intent. Inverse of ADR-0038's `documents.raw` posture: there Gmail is the durable copy; here the bucket is, because Gmail attachment availability is bounded by message lifetime. ADR-0039.

## Triage

**`SenderContext`.** Output of the deterministic `extract-sender-context` step that prefixes the triage pipeline. Shape: `{ fromKind: 'person' | 'service' | 'unknown', bodyActor?: { kind, name, handle? }, effectiveAuthor: 'bot' | 'person' | 'service' | 'unknown', botSlug?: BotSlug }`. Consumed by the cheap classifier as a typed input (not raw header text) and by the briefing's email contribution. Lives in `@alfred/contracts`. ADR-0042.

**Effective author.** Derived field on `SenderContext` — the actor who actually "wrote" the email considering both `From:` and body-actor extraction. Drives classifier rule 9a/9b/9c branching and gate condition (iii) on the escalation step. `'service'` is for cases where the envelope is a service (`noreply@github.com`) but no body-actor parser fired.

**Body actor parsing.** Per-service parsers that extract the underlying actor from a service-envelope email body. v1 covers GitHub (`**actor**` markdown), Google Calendar (iCal `ORGANIZER`), and Linear ("Comment from {actor}"). Long-tail sources fall through to `effectiveAuthor: 'unknown'` and the escalation gate's `confidence < 0.7` clause acts as the safety net. New parsers added from observed `triage.classification` log evidence, not speculation.

**Bot allowlist.** Hardcoded const `BOT_SLUGS` in `@alfred/contracts/triage`. Starts at ~10 entries (coderabbit, copilot-review, github-actions, dependabot, renovate, vercel, sentry, stripe-billing, google-security, datadog). Grows from observed log data. DB-backed migration only when the list passes ~20 entries. ADR-0042.

**`SEVERITY_SUSPECT_BOTS`.** Const subset of `BOT_SLUGS` marking bots whose alerts _can_ be genuinely urgent — sentry, stripe-billing, google-security, vercel, datadog. Triage escalation gate fires on this set even when the cheap classifier output `fyi`. CodeRabbit / Copilot / Dependabot / Renovate are deliberately NOT in this set — their messages are advisory in 99% of cases and security-CVE exceptions are caught by classifier rule 9a's text-content escape.

**Deepen step (superseded).** The ADR-0042 boss-agent brief-only run inside the triage workflow, gated by escalation conditions and given a read-only tool surface. **Superseded for triage by ADR-0051** — v3 has no routine boss step; the cheap classifier is made context-rich instead (see _Observation/inconsistency layer_). What survives the supersession: the `dossierRequest` side-effect hook and the `system.read_user_context` surface.

**Dossier cache TTL (designed, not built).** Per-`identity_confidence`-tier expiry on the `person_profiles` row (ADR-0031) that backs cached dossiers. ≥0.9 → 90d, 0.7-0.9 → 30d, <0.7 → 7d. Stale-and-important triggers re-research; cache key is the stable sender identifier — `email` for direct senders, `service:handle` for body actors (`github:coderabbitai`). ADR-0031 amendment + ADR-0042.

**Sender prior.** Row in `sender_priors` keyed `(user_id, sender_key)` — `sender_key` is the exact lowercased sender address or `service:<botSlug>`. Stores a raw category **histogram** (`category_counts`, e.g. `{ newsletter: 12, marketing: 1 }`), not a verdict — it is a **fed signal** to the always-on cheap classifier, never a model bypass. Updated on every classification (so it can't go stale). **Human senders are not cached** (a person's category is per-message); priors are a **bulk-sender** signal. No `confidence`/`locked`/`source`/domain in v1. ADR-0051.

**Account persona.** Per-credential `work | personal` label on `integration_credentials`, auto-detected from the Google **`hd` (hosted-domain)** claim (Workspace → `work`, absent → `personal`), user-overridable on the integration detail page. Fed as a one-line context hint to the triage classifier. v1 is **label + plumbing only**; the rich persona _policy_ (what's work-urgent vs personal-urgent) is a deferred future ADR. ADR-0051.

**Observation/inconsistency layer.** The deterministic "make a cheap model smart" mechanism in triage v3. **(a) Pre-model observations** always fed into the single cheap call: sender-prior histogram, account persona, thread state, known-contact flag, Gmail-native signals, cheap regex content flags. **(b) Conditional second cheap pass** — re-runs the cheap model _only_ on a hard deterministic conflict between its output and a strong expectation, with the inconsistency spelled out, **max once** (the second output is final). No boss. Intelligence via _focused attention_, not a bigger model. The conflict predicate is `detectConflict` (pure), deliberately just two tightly-gated nets — under-classification and over-classification. Its thresholds live in code and are tuned from `triage.classification` logs, not restated here. Gmail-signal-vs-output and the anomaly-catch direction are deliberately _not_ seeded: the always-on model with observations fed in already covers them. ADR-0051.

**Content flags (triage).** The cheap regex `ContentFlags` fed as named observations to the classifier (`observations.ts`): `hasUnsubscribe`, `hasCurrencyAmount`, `hasSecurityKeyword`, `hasCalendarInvite`, `hasInvestorNotice`, `hasPublicEventLanguage`. Flags are **fed to the model and the conflict checker; they never rewrite the category** — ADR-0051 §5 forbids hidden deterministic rewrites, which is why the last two exist as flags at all rather than as the guardrail rewrites they replaced. The broad `hasSecurityKeyword` (sign-in / password / token vocabulary) is distinct from, and much broader than, the override-floor predicate.

**Known-contact flag.** Pre-model observation: is the human sender's lowercased address in the user's `entities.aliases`? Computed by `isKnownContact(userId, address)` (one indexed jsonb-containment query). Only run for `effectiveAuthor: 'person'` senders (bots/services use priors instead); best-effort — any error or empty `entities` yields `false`, never fails classify. Phase 3 (2026-06-05). ADR-0051 §4.

**Triage override floor.** A small, high-precision set of unambiguous severity signals that may **force** a category regardless of model output; the model owns the category everywhere else. Deliberately **not** a large keyword ruleset — that brittleness is what once mis-tagged self-initiated sign-in links as `urgent` — so it stays seeded minimal and grows only on observed evidence. The seed is **one signal**: a secret, API key, token, private key, or password described as exposed, leaked, committed, compromised, found, or detected forces `urgent`. Generic "credential" is excluded from the floor and lives only in the broader security content flag; a bare CVE id and payment-failure-breaks-access are also excluded and go to the model, since a CVE id forcing `urgent` would re-introduce the advisory-bot noise rule 12a tags `fyi`. The floor predicate is narrower than `hasSecurityKeyword` precisely so sign-in and magic links never trip it. ADR-0051 §5.

**Thread state (triage).** Sent-mail-aware observation fed to the classifier — e.g. "you last replied in this thread on `<date>`". Requires `in:sent` ingestion. It is a **fed observation, not a hard rule**: the model owns the resulting category rather than a deterministic "you replied → done/fyi" mapping. ADR-0051.

**Sender relationship.** The **triage-local, directional** observation about a human sender — the answer to "who am I _to this sender_", so the todo rubric can judge relationship-derived stake instead of intrinsic stake only. It exists because cold inbound was minting "reply to X" todos. A resolver folded into `assembleObservations` renders the live graph signals as **one line of prose, not a typed value anything branches on**: the precomputed significance scalar bucketed to words (strong / moderate / weak), the reciprocity shape (one-way inbound / two-way / outbound-only), the same-org-domain flag, and the user's own role from `user_facts`. Example: `Sender relationship: weak · one-way inbound (you never replied) · not same-org · you: "Founder, Acme"`. There is **no `relationType` enum and no self-entity** — `user_facts` remains the single source of truth for who the user is. A sender with no graph row renders `no prior contact on record`, so the rubric degrades cleanly to intrinsic-only behavior. **Consume-not-infer:** consumed only by rubric **16b**, and only to corroborate the _"a real person is waiting on you"_ stake — money, deadline, access, and commitment stakes stay intrinsic and ungated. People are upserted by email alias (`upsertPersonByAlias`), never by display name. Distinct from the _significance score_, which is one scalar with four consumers. ADR-0059.

## Briefing

**Briefing.** One row in `briefings` per `(user_id, briefing_date)`. The canonical record of the day's morning briefing — the email is a render of `breaking_summary`, the in-app view renders `full_briefing`. Composed once per day via a single boss-tier LLM call over a cross-source gather. Idempotent on `(user_id, briefing_date)`; status-machine lifecycle. ADR-0041.

**Breaking summary.** The 4-6 lines of markdown prose sent in the day's morning email. Generated by the briefing composer alongside the full briefing — one LLM call emits both, no drift. Resolves `[[<kind>:<id>]]` placeholders into bold + service icon + anchor per the email HTML renderer.

**Full briefing.** The longer in-app surface for the day: `{ headline, sections: { source, label, body, why?, references? }[], sourcePanels?, auditSummary? }`. Replicache-synced read-only with a 30-day pull window; older briefings reachable via an on-demand `/api/briefings/history` route. Same prose source as the breaking summary — one composer truth, two renderers. The user-facing page shows source-backed inclusion rationale, not raw model reasoning. `sourcePanels` is the normalized display model; raw `gather` remains stored for audit/replay.

**Briefing reference.** `[[<kind>:<id>]]` placeholder in composed prose. Composer emits opaque tokens; a per-surface resolver expands against the gather (email: bold + icon + anchor; in-app: typed `<EntityChip>`; plain-text: fallback label). Prevents URL hallucination and decouples LLM content from presentation. Kinds are a closed enum in `@alfred/contracts`: `activity | meeting | email` — provider specifics (PRs, commits, deployments, incidents, billing notices, security alerts) all live inside `activity`. An unresolved placeholder falls back to its inner label as text _and_ logs to observability, because gather↔composer drift is a real risk worth surfacing rather than hiding. **Resolution home:** the pure resolver lives in `@alfred/contracts`, so the web surface resolves synced prose against the synced `gather` without importing `@alfred/http` (`pnpm check:web-boundaries` enforces this); the email HTML renderer stays server-side but calls the same resolver. One resolution truth, two renderers. ADR-0049.

**In-app briefing surface (ADR-0049).** The canonical scrollable record of a day's briefing at `/briefings` (timeline) + `/briefings/$date` (day detail). Day-keyed: the detail prefix-scans `briefing/{date}/` via `SYNC_MODEL.briefing` and renders **morning + evening stacked** as two slot records. Render posture is **paragraph-first** per ADR-0048 — lead with `breaking_summary`, treat `sourcePanels` as scrollable supporting detail and `sections[]` as secondary/collapsible, never the primary spine. **No special quiet-day mode:** every row renders identically; a quiet morning simply composes to a shorter `full_briefing`, so it _looks_ quiet without special chrome. `suppressed` (morning not emailed) is at most a subtle "Not emailed" metadata line, not a distinct layout. Read-only via Replicache (30-day window); no client mutators.

**Gather source.** A contribution to the briefing's input. Each source registers a `BriefingContributor<T>` exposing `collect({ userId, date, timezone }) → T | null`. v1 sources: `email | calendar | integration_activity | weather | day_of_week`. Future connected providers add activity producers under `integration_activity`; they do not each become top-level briefing sources unless they need a distinct briefing role. Provider names like Vercel, Railway, Cloudflare, Sentry, or Notion are examples, not committed integrations.

**Integration activity.** Normalized operational updates across connected systems, with GitHub as the first planned direct producer and other providers added only when their integrations exist. Items carry a stable `activityCategory` (`work | deploy | incident | account | billing | security | usage | other`) plus provider-scoped `providerKind` strings (for example `github.pr_review_requested`, `some_provider.deployment.failed`). Raw events are rolled up before compose: transient failures followed by success are suppressed unless the cluster is notable (many attempts, long duration, critical severity, or clear user involvement). Email triage can backfill activity with `source='email_triage'` before a direct provider API exists.

**`IanaTimezone`.** Branded `string` type in `@alfred/contracts`, validated at the API boundary against `Intl.supportedValuesOf('timeZone')` (the live IANA list, ~400 zones). Persisted as `text` (no PG enum — IANA mutates per tzdata release). Used wherever the user's timezone has to round-trip through DB + API + Replicache safely, including `briefings.timezone`.

## Todos

**Todo.** One row in `todos`. A user-managed commitment — a checkbox item either captured by the user or proposed by Alfred. The **first persisted materialization of the open-loop model** (ADR-0048 keeps loops ephemeral at briefing compose-time; a todo is a loop the user has chosen to track). Single table, status-driven; Replicache-synced. v1 is **passive** — Alfred authors and assists but never executes (see _Agent-executable todo_). ADR-0050.

**Todo-worthiness rubric.** How Alfred decides an email warrants a `suggested` todo — a judgment **orthogonal to the triage category**, applied by the cheap classifier over the whole email (including secondary and trailing asks) as five ordered tests, stopping at the first failure: **(a) obligation on me** — the action is the _user's_, and the named owner is the user rather than a third party named in the body; **(b) real, external stake** — an identifiable person waiting, money owed or at risk, a hard deadline, lost access, a commitment to a human, or a real-world consequence judged from content (this is where a _bot_ can earn a todo: leaked key, prod down), while **manufactured or ceremonial urgency** (engagement streaks, unread counts, "X viewed your profile", marketing scarcity, save-the-dates) carries no stake and fails here; **(c) memorability** — would the user forget it, or is it self-resolving / mid-flow (this is what kills self-initiated auth mail, as a _consequence_ rather than a patch); **(d) actionability** — a specific item is writable from the email alone; **(e) already-handled** — thread state shows it's done. All five must pass. **Category and todo may disagree:** a `done` closure with a real trailing ask still earns a todo, and the category is never bent to fit. `TODO_INELIGIBLE_CATEGORIES` is a _consistency guard against classifier leakage_, **not** part of the rubric — `fyi` and `done` do go through it. The **bot carve-out is model-judged from subject and content, never a hardcoded `BOT_SLUGS` floor**. Every classification traces its outcome via `todoDecision` into `triage.classification`, so the rubric is **tuned from real misses, not example-patched**; prompt exemplars exist only to anchor dimension boundaries. Authoritative text: prompt rule 16 plus `resolveTodoSuggestion` in `classify.ts`. ADR-0050 amendments.

**Todo status.** `suggested | open | done | dismissed`. `suggested` = Alfred-proposed, not yet accepted (renders in the _Suggestions_ section). `open` = a live todo (user-added, or a promoted suggestion). `done` = completed (`completed_at` set; lingers in sync for 7 days, then only falls out of the pull window). `dismissed` = declined/dropped — on a `suggested` row it's a "no thanks" learning signal, on an `open` row it's "dropped it." Promote (`+`) flips `suggested → open`. There is **no `running`/`interrupted`/`needs_attention`/`error`** at v1 — those are dimension's agent-run states, reserved for the deferred agent-executable path.

**Suggestion (todo).** A `todos` row with `status='suggested'`, **not a separate entity** (unlike dimension's `suggestedMessages`). Rendered in the rail's _Suggestions_ section with a `+` to promote. Authored only by Alfred (`created_by='agent'`). Carries `assist` + `sources` like any todo.

**`created_by`.** `'user' | 'agent'` on a todo. Survives promotion (a promoted suggestion stays `created_by='agent'`), so suggestion acceptance/dismissal is measurable later.

**Todo `executor` / `kind`.** Forward-compat columns. v1 rows default to `executor='user'` and `kind='task'`; the columns are inert until the deferred agent-executable path needs `executor='agent'` and executor-specific variants.

**`assist`.** Optional Alfred-authored text on a todo — a tip on how to approach it, degrading to an honest "I can't act on this (no permission / integration not connected)" when Alfred is clueless. Present even in passive v1; it is _not_ execution.

**Todo `sources`.** `jsonb` array of typed cross-source provenance refs — `[{ provider, kind, id, url? }]` (e.g. a Gmail thread _and_ a Slack thread on one row). Canonical identity is `(provider, kind, id)`; `url` is display/navigation metadata. Multi-source from day one so a todo represents a real-world commitment, not one channel. `created_by`, `agent_run_id`, and `assist` round it out. Single email-only `source_thread_id` was rejected for this reason.

**`system.suggest_todo`.** The source-agnostic write tool by which any agent run proposes a todo (inserts a `suggested` row). **No HIL/approval** — a suggestion has no real-world side effect, so it stays off the `action_stagings` path; audit lives on the todo row (`agent_run_id`, `created_by`, lifecycle dates). Called real-time from a tail step of the `email-triage` run when the classifier emits a `todoSuggestion`, governed by the **Todo-worthiness rubric**. The briefing does **not** call it — its action mentions are ephemeral open loops (ADR-0048). Source-agnostic by design, so future `integration_activity` producers call it from their own ingestion paths. **Idempotent on source-ref overlap:** if an existing `open`/`suggested` todo already references an incoming source it **merges**, appending only the missing refs rather than creating a duplicate. That merge is the v1 cross-channel dedup guard. ADR-0050.

**Agent-executable todo (deferred).** The B-path: a todo marked `executor='agent'` that spawns an `agent_runs` run through the boss runtime, with run-state (`running`/`interrupted`/`needs_attention`/`error`) reflected on the checkbox and tool calls gated via the existing `/approvals` HIL. Dimension ships this; Alfred defers it but shapes the schema (forward-compat `executor`/`kind` columns) so it lands without a database migration. The screenshot's checkmark/camera toggle is this switch.

**Cross-source auto-close.** Closing a todo automatically when integration activity proves the underlying task is done. ADR-0048's "continuous open-loops state machine" — **GitHub design locked (ADR-0052), read-only PR search shipped; poller/reconciler columns deferred**. Future v1 GitHub: a poller produces + reconciles persisted todos from the authenticated API; a _positive_ terminal signal (PR merged, alert dismissed, review threads resolved) flips `suggested→dismissed` / `open→done`, **absence never closes**. Generalizing to every integration (Slack reply closes an email-born todo) still needs cross-surface identity resolution and is deferred; the `sources` array is the watch-list each todo already records. Manual check-the-box remains the universal fallback.

**GitHub loop poller (deferred).** The ADR-0052 job (~10-min BullMQ tick). **Two-tier:** `GET /notifications` (the structured mirror of GitHub's notification emails — PRs, issues, Dependabot alerts, CI, mentions) detects + produces; per-object state endpoints give the authoritative close signal. A **deterministic `reason` gate** (no LLM) decides worthiness; a **cheap LLM** authors the title only for gate-survivors. Produces `suggested`. Email-derived identity is explicitly _not_ used.

**Verified-sender suppression (deferred).** The cross-surface dedup guard (ADR-0052): a DKIM/SPF/DMARC-verified `github.com` notification, when GitHub is connected, makes email triage **skip** minting a todo (the poller owns that loop with native identity). Fail-safe toward surfacing — unverified mail falls through to normal triage. Net-new `Authentication-Results` capture in the Gmail ingest path.

**Todo closure signal (deferred).** `todos.closed_by` (`'user' | 'reconciler'`) + `closed_reason` (`pr_merged | pr_closed | issue_closed | alert_dismissed | alert_fixed | review_threads_resolved`), `.$type<>()`-guarded. One field, three jobs: audit, the evening-recap "loops closed" line (ADR-0048 #5), and the client's auto-dismiss animation (reconciler-closed rows linger briefly in the Replicache pull so the diff is visible).

## Meeting prep

> **Designed, not built.** Every term in this section is locked design, not shipped state: there is no `packages/assistant/src/meeting-prep/`, no `meeting_preps` table, and no registered `system.prepare_meeting` tool. Build sequence in [docs/plans/meeting-prep-v1.md](./docs/plans/meeting-prep-v1.md); decisions in [ADR-0054](./docs/decisions/ADR-0054-meeting-prep-persisted-per-occurrence-packet.md).

**Meeting prep packet.** Alfred's pre-meeting context note for one calendar event: who's attending, the recent threads with them, relevant memory facts, and the open todos that touch the meeting — composed into a short cited note. **MEET-001 scope** mirrors the briefing pipeline end to end: a deterministic **gather** (event + attendees + email threads + memory facts + todos), a **boss-tier compose** into short prose with `[[<kind>:<id>]]` citations, **persisted** and Replicache-synced read-only. The proactive **calendar-watch trigger** is part of MEET-001; the **delivery surface** (pre-meeting email, web augmentation at send) is MEET-002.

**`meeting_preps`.** One row per calendar occurrence, keyed `(user_id, event_key)` where `event_key = ${credentialId}:${googleEventId}` (`singleEvents=true` → per-occurrence). Status machine (`pending|gathering|composing|ready|failed|cancelled`) like `briefings`; `gather` jsonb is the audit/replay record, `note` jsonb the composed cited output, `row_version` drives Replicache. **Upsert, recompute-in-place** — no version history; cancelled calendar occurrences are marked `cancelled` and fall out of active sync.

**Gated recompute.** The deterministic (no-LLM) discriminator on re-running `prepareMeeting`: a `material_hash` over attendees + agenda + location + attachments. No row → full gather+compose; material change → full recompute; **time-only shift → cheap path** (update `event_start`, skip compose); unchanged → no-op. The lever that lets the trigger fire often while keeping boss-tier compose cost down — minimize the _number_ of composes, not the tier.

**Prep horizon + sweep.** Prep _compose_ fires only for qualifying events starting within horizon **H (48h)**. A calendar push preps near-term changed events; a ~20-min cron **sweep** catches events crossing into H that never changed (the webhook-vs-time-passing gap — pushes fire on change, not on time). Event qualification on window-resolution: timed, `attendees ≥ 2`, not declined; an explicit `eventKey` bypasses qualification.

**Calendar watch.** Google Calendar push channel (`events.watch`) — **HTTPS-callback** based, not Pub/Sub like Gmail. State lives in `integration_credentials.metadata.calendarWatch` `{ channelId, resourceId, expiresAt, syncToken, calendarId }` (mirrors Gmail's `metadata.watch`; v1 = `primary` only). **No event mirror** — push handler acts on the `events.list(syncToken)` delta live, sweep/gather read live. Push delta dispatches through the `emitEvent` bus (`calendar.event_scheduled`, ADR-0047). Needs a domain-verified callback URL (GCP) — no localhost in dev.

**`system.prepare_meeting`.** The single entry point all three triggers (chat/boss, calendar push, sweep) converge on. `system.*` → autonomy by default, riskTier `no_risk`. Input `{ eventKey } | { timeMin, timeMax, attendeeHint? }`; resolves the event, runs the gated recompute, gathers, composes, upserts `meeting_preps`.

**Prep reference.** `[[<kind>:<id>]]` placeholder in composed prep prose. Parallel to the _Briefing reference_ but with its **own** closed enum and resolver in `@alfred/contracts` expanding against the prep gather, so briefing's resolver stays untouched. Planned kinds: `meeting` (static, by event key), `email` (→ Gmail thread), `todo` (→ rail). **Memory facts are deliberately not a citation kind** at v1 — they are woven into prose, with ids retained in the gather for a future evidence layer.

## Long-term memory

**Semantic user-memory.** LLM-proposed, confidence-gated, vector-recalled knowledge _about the user_ (`user_facts`, `entities`, `memory_chunks`). The fuzzy half of memory — the structured, reducer-computed half is _object-state memory_ below. (ADR-0056/0057)

**Memory store posture.** The substrate is **Postgres, not a graph DB** (ADR-0058). Two separable layers: the **store** (where memory lives — stays PG: `user_facts`, `entities`/`entity_relations`, `memory_chunks` pgvector) and the **intelligence** (extraction, contradiction, lifecycle — _built_ as logic over the store, not bought). Graph is kept as a **model** (`entity_relations`), never a graph **engine** — the engine's advantage is a node-scale single-user Alfred never hits, and a service (Zep/Mem0/Letta) drags the source of truth off Postgres, breaking the Replicache memory-changelog surface + the ADR-0038 privacy posture. Borrowed: Mem0's `ADD/UPDATE/DELETE/NOOP` taxonomy as the _shape_ of write-time contradiction over `proposeFact`/`supersedeFact`. Revisit only on multi-tenant-at-scale.

**Memory governance.** ADR-0056 posture: Alfred mutates memory **autonomously via `system.*` tool calls**, kept safe by **transparency + reversibility**, not pre-write HIL. Supersedes ADR-0019's confidence-gated accept gate — confidence now gates _notification cadence_ + the `proposed`/`confirmed` _review label_, not the write. Floor unchanged (≥0.7 written, <0.7 dropped); the agent **hedges on low-confidence** facts in prose. Storage substrate adopted as-is.

**Knowledge kind.** The taxonomy spine memory is organized by (not by table): _identity_, _standing instructions_ (first-class), _people & relationships_ (the team graph), _episodic facts_, _style_, _episodic memory_. Each has its own capture source + lifecycle; **lifecycle is per-kind — there is no global TTL.** ADR-0056.

**Criticality tier.** Drives notification, not gating. _Critical_ (identity change, key-relationship change, superseding a ≥0.85 fact, retracting a confirmed fact) → email on a **~5-min debounce, batched** (reuses the approval-debounce). _Subtle_ (new low-stakes/low-confidence facts, additive aliases) → **digest flushed on count-threshold OR weekly, whichever first**. In-app is real-time Replicache, **one-by-one** (`user_facts.row_version`). ADR-0056.

**Rejection cause (designed, not built).** New field on the rejection record: `cause ∈ {user, write_time_contradiction, decay, superseded_by_newer}` alongside the freeform `reason`. Separates _user corrections_ (high-value training signal) from _system self-corrections_. ADR-0056.

**Memory rationale.** A cheap-model **~2-sentence, telegraphic, grammar-optional, token-frugal** "why" persisted per memory write, paired with the `source` evidence pointers. Surfaced through the **SEARCH-001** evidence layer — memory-justification and cited outputs are one mechanism. ADR-0056.

**Loop 1 / Loop 2.** Two self-correction loops a single user correction drives at once. **Loop 1** = fact maintenance (write-time-contradiction supersession + user-authoritative edit/reject; decay deferred → D2). **Loop 2** = system learning (the user-correction misses dataset, seeded by `rejected_inferences`, feeds the eval lane ADR-0055; **no automatic prompt mutation** — humans gate). ADR-0056.

**Passive capture.** Memory capture is **fully passive** — onboarding stays minimal; the team graph + identity facts are inferred from integrations (Gmail/Calendar) and **enriched/corroborated via web search**, written autonomously (ADR-0056), kept fresh by continuous extraction + Loop-1 supersession. No prompted confirmation card; correction is unprompted via the review surface. Teams change → the change shows up in an integration, so no re-interrogation. **Supersedes ADR-0031's review-before-write gate** for dossiers; `person_profiles` (ADR-0042, unbuilt) is the dossier home. ADR-0057.

**Significance score.** A first-class **computed signal over `entities`** — blend of correspondence frequency + recency + reply-reciprocity + same-org-domain + explicit relationship edges. **One source, four consumers:** the web-search dossier-enrichment gate (budget-capped, only above-threshold entities get a dossier; long tail stays name+email), todo personal-relevance significance (ADR-0050 **D1**), triage sender priority, meeting-prep attendee prioritization. Replaces four ad-hoc "who matters" heuristics with one. The score stays a **scalar**; directional richness lives in the _Sender relationship_ resolver, not here. ADR-0057.

**Chat→memory capture.** The explicit-statement write path (vs _passive capture_'s inference). Two paths: **(i) in-band proactive** — the boss recognizes durable intent mid-conversation (not just literal "remember") and calls `system.remember`; **(ii) end-of-thread extraction** (ADR-0019's existing trigger) mines the closed thread for durable facts/prefs stated in passing. Bar to write is low (reversible); behavior-changing standing instructions are critical-tier → notify. **Durable vs run-scoped split:** "for the rest of this conversation" → run-scoped directive (ADR-0035 `user_directives`, dies with the run); "from now on" → durable standing instruction (persisted). The boss classifies on phrasing; only durable hits long-term memory. ADR-0057.

**Standing instruction.** A durable, user-stated **bias on an existing pipeline** (triage / briefing / meeting-prep) — "tag my partner's mail urgent", "stop nagging me about Ben", "keep recruiters out of my brief". A `user_facts` row, `key="standing_instruction"`, consumed by the pipelines as an orthogonal modifier. **Boundary:** a standing instruction _modifies a run that already happens_ — it is **not** a request to _author new scheduled behavior_. "Brief me before the eng standup" is workflow authoring (ADR-0017 + an ADR-0027 trigger), not a standing instruction. The two may share the chat capture entry point, with the boss deciding which artifact to mint, but they are different artifacts with different lifecycles. This boundary is what keeps the feature from drifting into a generic rules engine. The _Suppression standing instruction_ is the first concrete shape. ADR-0060.

**Standing instruction schema.** The `user_facts.value` shape on a `key="standing_instruction"` row. **Shipped is v1** — `STANDING_INSTRUCTION_SCHEMA_VERSION` in `@alfred/contracts` is the authority, and the concrete shape is under _Suppression standing instruction_ below. **v2 is designed, not built:** three cleanly separated concepts — **`directive`** (resolved prose, **always present**, the universal carrier prose consumers apply by judgment), **`target?`** (an optional matchable descriptor keyed by sender address, sender domain, person, category, or topic, serving both deterministic exact-match and prose relevance-filtering; absent for a pure free-text rule), and **`enforcement?`** (optional typed, parameterized actions for the deterministic carve-out — a **registered, not closed** set), with `phrasing` kept verbatim for provenance and UI only. v2 **drops `action` and `surface`**: `directive` carries display intent, `enforcement` carries the contract. The reader handles v1, so the migration is near-free. ADR-0060.

**Instruction application model (designed, not built).** _How_ a standing instruction reaches a pipeline — **prose-first, with a deterministic-enforcement escape hatch** (redirected 2026-06-17, supersedes the earlier per-consumer "effects enum is the contract" framing). The architecture has three parts, central by design so a new feature/integration costs ~nothing:

- **Central store + one retrieval primitive.** All instructions live in `user_facts` (`key="standing_instruction"`). A single `getRelevantInstructions(context)` retriever returns the instructions relevant to whatever a feature is doing (an email, a briefing gather, a meeting, a chat turn). A new consumer _calls it_ — it never extends an enum. **Relevance strategy = inject-all-active** (the set is bounded) **behind a context-aware interface** — semantic/entity relevance-filtering is a deferred swap behind the same signature, triggered by a logged count threshold, never a call-site change. **No-double-application:** an instruction with an `enforcement` is applied by the deterministic consumer that owns that effect; prose-fallback fires only for instructions a consumer hasn't already enforced (so "suppress Ben" is dropped by `gather` and never reaches `compose`).
- **Prose-first application (the default).** The resolved **`directive`** prose is the universal carrier. Agent-driven, compose-time, low-volume consumers (chat, briefing compose, meeting-prep, **every future agent feature**) pull the relevant directives and **apply with judgment** — including flagging conflicts / counterproductive effects ("you also told me to always surface Ben"; "muting all of @oliv.ai hides your manager"). No typed effects, no per-feature maintenance, instruction-awareness for free.
- **Deterministic enforcement (the carve-out).** A thin typed projection (`enforcement`: e.g. `block_todo_suggestion`, `force_category{category}`, `exclude_briefing_priority`) consumed only where a **hard guarantee + cost-sensitivity coincide** and a prompt line is not reliable enough — **triage today** (the cheap, high-volume classifier; ADR-0051 keeps it context-free, the Ben-Book veto proved prose-only is insufficient there). **Keyed on "needs a guarantee," NOT on feature count** — it's a registry, so a _future_ feature that needs a hard guarantee registers an enforcement, but ordinary new features just use prose-pull. The shipped slice's `effects` enum is this layer, scoped down.

The boss picks at capture (resolve-at-write): prose-only `directive`, or `directive` **+** a resolved `target` + `enforcement` when a deterministic guarantee is needed. Likely an **ADR** (architectural, hard to reverse).

**Category override, user-instructed (designed, not built).** Refines the "category stays honest" rule (2026-06-17): **the _model_ never bends the category; an explicit _user_ standing instruction may** — via the deterministic override layer, never by the classifier. Carried by a parameterized **`force_category`** effect (`{effect:"force_category", params:{category:<TriageCategory>}}`). The model still classifies honestly; the override layer re-stamps _after_, exactly like the existing security override-floor in `classify.ts`. **Every override logs an audit breadcrumb** (`overriddenByInstruction: { factId, from, to }`) — non-negotiable: a future debugger must never see a force-stamped category with no trace. Distinguished from the model's own "no bend" rule because the user is the authority, not a hallucination. Reversible (reject the fact → override stops).

**Suppression standing instruction.** The first concrete standing-instruction shape — the "stop emailing me about Ben Book" slice, and the only `effects`-bearing one shipped. A `user_facts` row, `key="standing_instruction"`, whose v1 value carries `action:"suppress"`, `surface:"open_loop"`, a `target` of kind `sender_email` holding the canonical lowercased address, `effects:["block_todo_suggestion","exclude_briefing_priority"]`, the resolved `directive`, and the verbatim `phrasing`. **`effects` is the operational contract consumers branch on; `surface` is the human/product label** — "does `open_loop` include me?" is answered by `effects`, never re-derived. **Sender-scoped and cross-account by default** (`accountId: null` — suppress the _sender_, not one mailbox). `surface:"open_loop"` suppresses the **nag/todo/briefing surfacing, not the email's existence**; the chat reply says so explicitly, because mail still arrives unless the user asks for a Gmail filter. **Persist-until-revoked** — no `valid_until`; a later "surface Ben again" supersedes via `supersedes_id`. **One shared reader** (`listActiveSuppressionInstructions` + `findSenderSuppression`, in `packages/assistant/src/knowledge/standing-instructions.ts`) owns the Zod parse, the `proposed|confirmed` filter, the `valid_until` filter, and the lowercased-email match. Triage `classify` (blocks the `todoSuggestion`) and briefing `gather` (excludes the sender from priority buckets) both call it — an **orthogonal check, not a category bend** — and each logs an audit breadcrumb. Topic-scoped suppression is deferred. ADR-0058; [docs/plans/long-term-memory-v1.md](./docs/plans/long-term-memory-v1.md).

**Instruction precedence, apply-time (designed, not built).** When several non-conflicting instructions match one item (2026-06-17): **most-specific target wins, recency breaks ties** — specificity order `sender_email`/`person` > `sender_domain` > `category` > `topic`; same-specificity → newest (capture's conflict check usually catches same-target contradictions first). `enforcement` stays authoritative over the model's intrinsic judgment for the dimension it touches. **Safety carve-out:** the existing protective override-floor in `classify.ts` (force-`urgent` on exposed-secret / account-compromise) **outranks a user _down-rank_, never a user _up-rank_** — a mute can't bury an irreversible-harm alert; an elevate stacks fine. Named, floor-only, logged like every override.

**Target disambiguation (resolve-at-write).** When the user's words match **more than one** known entity ("Ben" → two people in the team graph), canonical resolution is still a write precondition: the boss **surfaces the candidates and asks which** rather than guessing — the same fragility that made the original boss search "ben book" and hit its own reminder emails. Person/sender targets resolve via the team graph (`upsertPersonByAlias`/`entities`); >1 candidate → disambiguate, 0 confident → one-line clarifying question, exactly 1 → proceed.

**Conflict at capture.** A standing-instruction write is gated on a conflict check, in two flavors. **Structural conflict** — an overlapping `target` with opposing `enforcement`, or a target subset/superset — is detected **inside the `system.remember` tool**, which returns `status:"conflict"` plus the conflicting fact(s) and a machine reason. **The tool never silently overwrites a contradiction**, because relying on the model to notice is the prose-only fragility again. **Semantic or counterproductive conflict** ("mute all of @oliv.ai" hides the user's manager) is the **boss's** job, reasoned from the existing instructions plus `system.read_user_context` before writing. In both cases the boss poses a counter-question or offers options rather than writing through; a confirmed reversal supersedes via `supersedes_id`. **Passive capture** that hits a conflict **holds the write as `proposed`** and surfaces it in the memory changelog — never a silent overwrite. ADR-0060.

**Resolve-at-write.** A standing instruction is **fully resolved at capture time**, so no consumer ever re-interprets prose at read time: `target` holds the _canonical matchable key_ (the resolved, schema-normalized lowercased email — not the name "Ben Book"), `directive` is a resolved prompt-ready sentence, and `phrasing` is verbatim **provenance/UI only, never parsed by a pipeline**. Canonical resolution is a **precondition of the write**: if the boss cannot confidently resolve the target from thread context, it asks a one-line clarifying question rather than guessing. That is the antidote to the original bug, where the boss searched "ben book", hit its _own_ reminder emails, and mis-acted. ADR-0060.

**`system.resolve_todo`.** The capture-path companion to `system.remember`. **Source/sender-resolving, not `todoId`-only** — it accepts a todo id, a sender email, or a source ref, mirrors `system.suggest_todo`'s source-overlap match, and returns `ambiguous` plus candidates when more than one todo matches. For spam and suppression it uses **`dismissed`, not `done`**, because `done` trips the 7-day done-sync / Gmail-label window. This is the tool whose absence let the boss falsely claim "I marked it resolved".

**Standing instructions surface (designed, not built).** A minimal-but-real review panel is **in scope** for the generalized ship (2026-06-17, supersedes the slice's "polished changelog deferred"): a "Standing instructions" list (likely `/settings`, near the Background card) of each active rule's plain-English `directive` + **undo/reject** + **edit**, reading the already-synced facts (`row_version`) and reusing the existing reject/edit mutations — no new sync. Required _because_ positive instructions **actively mislabel** mail (a stale `force_category` distorts triage silently — the exact failure that started this), so audit can't be logs-only. **Notification unchanged (ADR-0056 + slice):** a chat-stated instruction sends **no email** (user witnessed it); only passive/background-captured instructions notify.

**Recurrence-decay (briefing).** The briefing principle that defuses the self-reinforcing nag loop: **un-acted-upon recurrence decays salience — it never escalates it.** An item surfaced across N briefings with no user action is evidence the user _de-prioritized_ it, so it downgrades or drops. This inverts the emergent "survived every briefing, shouldn't survive another night" escalation that `list_prior_briefings` was driving. It ships as a prompt **principle** generalizing the old PR-scoped "don't re-surface stale PRs" paragraph in `briefing/prompt.ts` — a principle, not an exemplar. It is defense-in-depth for _un-suppressed_ items; the deterministic suppression check is what actually closes the loop, because a fix in triage is not a fix everywhere. ADR-0058.

**Cold-start research (v2).** Lifetime-once onboarding self-research from name + email (ADR-0011 lineage). Scope is **the account holder only**: company, role, team, and publicly attested relationship/family facts may land as `user_facts`/`memory_chunks` _about the user_; third parties get at most a one-line relation mention, never recursive research and never their own `entities` row. The team graph is ADR-0057's later passive, significance-gated job. The blocker at onboarding is **not** "no history exists" — a connected mailbox brings years of it — but that the history is **not yet ingested and not readable under the `gated` default**: `gmail.read_message` reads an empty `documents` store at callback, and live reads need the unbuilt run-scoped autonomy override. Population is therefore passive capture's job, not cold-start's. ADR-0059.

**Cold-start v2 shape (designed, not built).** Replaces the stranded Perplexity Sonar Deep Research path with the agent harness: boss identity-resolution seed → bounded parallel aspect sub-agents using `system.web_search` → boss synthesis → the existing `extractColdStartFacts` → `proposeFact`/`writeMemoryChunk`. **v2.0 is web-only** because new users default to `gated`, which would park live Gmail/Calendar reads in a watcher-less onboarding run. **v2.1** may add read-only calendar and Gmail _search_ once the run-scoped autonomy override lands, but `gmail.read_message` stays unavailable at callback time because the `documents` store is still empty. Sub-agent findings are ephemeral; the boss synthesis is telegraphic and persisted as the extractor input. v2 keeps ADR-0019's two-stage extract tail and deliberately does not pull in `system.remember` or the ADR-0056 governance migration. **Relation guard:** attestation, not fame — never infer a relation from a shared surname; hedge or omit low confidence; for minor children, "exists / how many" is enough and individual background is omitted. ADR-0011/0022 amendment, in design.

## Object-state memory

The structured, exact-keyed, reducer-computed sibling of _semantic user-memory_. Lives on Postgres; no vector or LLM in its closure path. (ADR-0062)

**Object-state memory.** A deterministic projection of the _lifecycle state_ of external work objects — GitHub PRs, ClickUp tasks, Claude Code runs. Informally the **awareness layer**: the maintained, durable view of "what's happening across my integrations" that the prod recon proved a gather-time recompute cannot provide.

**Integration object.** One external work object tracked in object-state memory, identified by `(user_id, provider, kind, external_id)`.

**`state_category`.** The normalized lifecycle bucket every provider's native state maps into: `active | resolved | failed | abandoned`. Provider-agnostic consumers read this.

**Native state.** A provider's own state string (`open`/`merged`/`closed`, `in_progress`/`done`, …), retained on the object row for fidelity and audit alongside the normalized `state_category`.

**Key sidecar / key-resolution.** `integration_object_keys`: a `(provider, key_kind, key_value) → object_id` table, so heterogeneous identities (`head_sha`, `run_id`, `task_id`) all resolve to an object uniformly. Raw branch names are repo-scoped, so they are not a v1 key.

**Reducer.** A per-provider, pure, idempotent, replayable `applyEvent(provider, event)` that folds webhook and event deliveries into object-state. The irreducibly per-provider part — there is deliberately no generic reducer.

**Registry (`IntegrationObjectDef`).** The typed, per-provider source of truth in `@alfred/contracts` declaring a provider's object kinds, key kinds, state normalization, and readable surfaces. Enforces at the type/API layer the constraints Postgres cannot. Generalizes the ADR-0053 tool catalog.

**Loop-opener.** The inbound item that starts an open loop in the briefing (v1: a GitHub Actions CI-failure email). It carries a matching key such as `head_sha` but often no direct object id — which is what the key sidecar exists to bridge.

**Loop reconciliation.** Computing, at briefing gather time, whether an open loop is actually closed by consulting object-state, then demoting or recapping accordingly. Bounded by _absence never closes_. (#212, ADR-0048/0062)

**Extraction front-door.** The propose-only capture layer that turns inbound emails and docs into typed candidate keys (→ object-state) and work-signals (→ semantic user-memory). One front-door, two sinks. Architecture deferred. (ADR-0063)
